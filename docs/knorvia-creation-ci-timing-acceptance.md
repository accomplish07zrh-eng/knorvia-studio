# 创作离线测试时序修正

2026-09-28，集成基线 `5167e0d`，调查基线 `947b126`。只改 `packages/services/test/creation-polish.test.ts` 中三种协议共用的失败/重试/超时/取消用例，不改产品实现、模型配置、数据格式或界面。先行规则已在[创作规格](../specs/knorvia-creation-polish.md)中明确。

## 原始证据与修正

GitHub run `36420984594` 首次 Windows 2,094 通过、1 失败：JSON API 取消用例预期第 4 次模拟提交，但只记录到 3 次。同提交单 job 重跑 2,095/2,095；首次失败仍保留，不能由重跑通过认定问题不存在。

服务的 500ms 截止计时从写入 running 状态之前开始，之后还有凭据、参考文件读取。测试原先用 100 次 × 5ms 轮询计数，假定第 4 次请求必已开始；准备慢时，未提交即截止是合法路径，服务应阻止外发。因此延长轮询不能使该假设成立。原失败日志没有终态，无法断言当次经过哪一条路径。

隔离探针使用真实服务、合成凭据门闩和虚拟时间：未提交即截止得到 failed/3 次提交，已提交后取消得到 cancelled/4 次提交，2/2 通过。未证明产品实现存在缺陷。

修正使用两次独立的模拟 fetch 到达信号。超时分支等到提交后推进恰好 500ms；取消分支冻结该时钟，等到提交后调用取消。fetch 同时处理注册监听前已中止的信号。每次使用 finally 恢复时钟，终态仍等待真实状态文件完成落盘。看门狗用捕获的真实时钟、沿用通用诊断的 1,000ms 预算；它替代取消分支原先的计数轮询，在失败时报告任务 ID 和到达计数。业务截止时间、终态分类、提交次数及禁止重试的断言保持。

单一状态所有者仍是 CreationService；测试只控制边界发生的次序。已有 `creation-deadline.test.ts` 另行验证 running/输出写盘期间超时，以及迟到结果不能覆盖用户取消。本批不新增产品 helper、状态缓存或跨模块依赖；services 为 unmanaged，owner unassigned。
