## Concrete findings

1. **Concurrent initial refresh callers can issue two manifest requests and receive different snapshots.** At [manifestFor](https://github.com/accomplish07zrh-eng/knorvia-studio/blob/ffed10195f13f11c0726ae9df5976dd790b9b666/packages/server/src/remote/remoteAssetCache.ts#L346), the no-cache branch starts work with refresh registration disabled (line355). A second overlapping public fetch with refreshManifest=true waits on that task, finds no active refresh and starts another request after the first succeeds (lines358–368). The frozen contract's retained-snapshot/request-sharing section requires concurrent refresh callers to share the initial work as well. This also affects initial content-addressed ensure requests meeting a later refresh caller. This is a static concrete interleaving, not a newly executed test. Preserve the original draft and bind any correction separately.

2. **Published migration enumeration admits symlink siblings.** [Old component migration](https://github.com/accomplish07zrh-eng/knorvia-studio/blob/ffed10195f13f11c0726ae9df5976dd790b9b666/packages/server/src/remote/remoteAssetCache.ts#L668) enumerates names and follows stat through readiness; a prefixed symlink to a ready directory can therefore be selected. [Old release migration](https://github.com/accomplish07zrh-eng/knorvia-studio/blob/ffed10195f13f11c0726ae9df5976dd790b9b666/packages/server/src/remote/remoteAssetCache.ts#L693) similarly admits a version-directory symlink through stat. The packet requires directory-entry admission, excluding symlink siblings. Materialization's entry-symlink rejection does not reject a symlink used as its root. Root reports local correction d326f53 and one counterexample; this review confirms the gap in the published head only and does not claim to review that correction. The component readiness-stat/mtime-stat ordering otherwise agrees with the clarification: readiness failure skips; only the later ranking stat failure propagates.

3. **Staging-directory failure no longer gates artifact network work.** [Component download](https://github.com/accomplish07zrh-eng/knorvia-studio/blob/ffed10195f13f11c0726ae9df5976dd790b9b666/packages/server/src/remote/remoteAssetCache.ts#L761) calls artifactResponse before download creates the archive parent, and creates extract only after checksum validation. The pinned predecessor prepares the staging base/extraction directory before requesting the artifact. With a pinned manifest and an unwritable or conflicting staging path, the predecessor rejects before artifact fetch while the published candidate fetches/logs first, then rejects during local preparation. No network or filesystem counterexample was executed here. The frozen packet described staging paths and cleanup but did not explicitly state this preparation-before-request gate; this is a **curator packet omission**, not evidence that root disregarded a supplied requirement. Functional clarification: local staging-base/extraction preparation must succeed before the artifact request begins; a preparation failure terminates before that request. A correction belongs to a separate post-freeze descendant.

The previously reported max-lines gate 997/400 remains open in the published receipt. This static review does not resolve or retest that gate.
