# Knorvia Studio 性能基线（Windows x64）

2026-09-25，版本 `0.8.0-preview.1`，生产身份构建。原始机器可读结果见 [perf-baseline-2026-09-25.json](perf-baseline-2026-09-25.json)。这是首次记录的基线，没有可比的旧版同条件测量值。

## 条件和复现

- Windows 11 家庭版 build 26200；AMD Ryzen 9 7845HX（24 逻辑核），31.2 GiB RAM；Node 24.14.0；本机 Chrome 154.0.8037.57。
- `KNORVIA_ENV=production node packages/desktop/scripts/bundle.mjs --os win --arch x64` 完成；打包后运行时依赖与 500 MiB 包体积审计通过。
- `node scripts/perf-baseline.mjs --executable <便携目录/Knorvia Studio.exe> --artifact <安装包.exe> --portable-dir <便携目录>` 使用本机 Vite 回环地址和无头 Chrome，向真实 Studio 时间线组件注入 10,000 条合成消息。桌面启动使用一次性独立数据根，等到首次引导出现；不读取现有便携 `data`，不调用模型、已登录 CLI 或远端服务。
- 记录连续 180 个 `requestAnimationFrame` 的回调间隔和视口中最大挂载行数，再检查离底追加、加载 100 条旧页及显式回到底部。空白系统缓存与独立物理显示器帧率未测。

## 便携交付与限制

覆盖前确认桌面便携程序未运行。`scripts/deliver-portable.ps1` 排除 `data/` 复制程序，复制前后对其中 360 个文件、52,456,669 字节逐项比较 SHA-256，全部相同；构建目录中 118 个程序文件与交付目录逐项 SHA-256 相同。交付程序以独立配置成功启动到首次引导，便携标记仍指向 `data`。安装包 SHA-256 为 `6DA73F0BF07A8C6FB54E9A6B16B281A23E34D17B1E31C13046C660E2E1BBE22B`，签名状态 `NotSigned`。

未做人工目视复核、真实模型或 CLI 消息发送、真实 SSH、10,000 条真实持久历史的内存测量，也未验证安装向导。长会话虚拟化只改变 Studio Runtime 时间线可见行的挂载；原生 V4 时间线仍沿用其既有虚拟列表。后续若优化启动或内存，应在相同机器、显示条件和脚本口径下重新记录，再比较回归。

历史没有丢失：优化后脚本反复点击“显示更早运行”直到按钮消失，面板重新挂载 **101/101** 条运行、**808/808** 个步骤行（101 条 = 100 条夹具 + 刷新时新增的 1 条）。窗口始终是时间倒序的连续前缀，正在复核的运行与 `queued`/`running`/`waiting` 的运行即使被新运行挤出首屏也仍然渲染。

### 桌面冷启动分阶段（打包程序 `win-unpacked`，未重新打包）

冷启动到首次引导出现的 4 次独立样本：6,413 / 6,430 / 6,135 / **5,904 ms**（最新一次运行的中位数 6,002 ms，3 个样本 5,904–6,113 ms，离散度约 ±2%）。热启动 6 个样本：6,627 / 6,276 / 5,900 / 5,946 / 6,113 / 6,002 ms。**热启动并不明显快于冷启动**，说明这份开销每次启动都要重付，不是首次建库特有。建议的 `<3 秒` 目标本轮**仍未达到**。

最新一次运行的冷启动分阶段（相对**进程创建** T0；`process.getCreationTime` 与应用 launch marks 对齐，时钟对齐误差 4–6 ms）：

| 阶段                                       |         耗时 | 说明                                               |
| ------------------------------------------ | -----------: | -------------------------------------------------- |
| Playwright 附加/握手                       |       982 ms | 与 main 模块求值重叠，属测量开销，不是用户可见启动 |
| 进程创建 → main 模块开始执行               |       817 ms | Electron 启动 + main bundle 求值                   |
| main 模块 → `app.whenReady`                |        73 ms |                                                    |
| app ready → 主窗口 `loadURL`               |       339 ms | 设置读取、协议/网络策略、菜单与 IPC 注册           |
| `loadURL` → renderer bundle 开始执行       |       803 ms | renderer bundle 求值到首屏脚本                     |
| renderer 开始 → React 首次 commit          |        20 ms |                                                    |
| 首次 commit → Host utilityProcess 派生     |         4 ms |                                                    |
| **Host 派生 → 首次可交互（首次引导可见）** | **3,843 ms** | 占 T0→首次可交互 5,899 ms 的 65%                   |
| 合计                                       |     5,899 ms | 首次可交互（首次引导）                             |

Host 侧归因来自应用自己的生产日志（Host 日志经 main 转发，时间戳是 main 的接收时刻，有毫秒级转发偏移）：`dom-ready` 2,046 ms、Host 派生 2,056 ms、Host “initializing local services” 5,478 ms、“local services ready, all channels registered” 5,722 ms、首次可交互 5,899 ms；同一次启动的 `[database-startup] terminal` 为 `status=ready, durationMs=2843`（3 次运行分别为 2,843 / 3,045 / 2,884 ms）。也就是：Host 的存储准备（迁移/建库）约 2.8–3.0 s，加 Host Node 引导与通道注册，是首次可交互的主要阻塞点；这段代码属于 `packages/desktop/src/host/*` 与 `packages/services` 的存储层，**不在本轮写入范围**。

“可发送”测量单独跑一次：跳过首次引导（3 次跳过 + 关闭首次运行引导）后，`[data-testid="v4-composer-input"]` 在首次引导出现后 **1,513 ms** 可用，即从启动器起点约 **7,491 ms**。这个数字包含脚本化的跳过交互时间，不是纯启动阶段。

空闲进程树（冷启动后等 1.5 s）：7 个进程，工作集求和 1,159.9 MiB，私有提交 1,144.8 MiB（4 次运行范围：1,152.1–1,172.6 MiB / 1,137.9–1,151.9 MiB）。打包目录 660,144,096 字节 / 118 文件（排除 `data/`；与首次记录的 660,206,104 字节 / 122 文件是不同构建，不可直接比较）。

### 生产日志检查（长会话）

冷启动到可发送期间的隔离配置日志：17,761 字节 / 98 行，`[debug]` 0 行，`rpc:call` 11 行；内容只有进程与会话生命周期、通道注册、RPC 计时、临时目录下的工作区路径和 provider 注册表哈希，没有凭据、真实用户数据或逐 chunk 的原始流。需要注意：`packages/rpc/src/logging-middleware.ts` 把**每一次** RPC 调用与事件订阅都记在 info，只有 `agent.backgroundBashOutputV4 OK` 在 `packages/desktop/src/host/rpcLogLevel.ts` 里降为 debug；这不是原始流，但长会话下会按调用次数增长。该文件不在本轮写入范围，已记录为风险，未改动。

### 本轮未验证

- 内核/CLI 探测开销：本机没有检测到本机安装的 CLI 内核（Host 日志为 `Knorvia agent binary path: <not found>`、`providerCount: 0`），而内核探测本来就是首屏之后的 renderer 行为；`packages/services/src/studio-runtime/adapters/kernels/README.md` 记录的“约 20 s 握手、每次刷新重复”在本机无法复现，因此没有改动 `kernelRegistry.ts`。

- 桌面侧源码改动（若日后要做）必须重新打包后按同样命令重测，本轮的数字不能用于验证打包改动。

## T10 后续：并行准备两个数据库（6e1b4f2）

### 证据与改动

只读复核确认启动链里 2.8–3.0 s 的存储准备由两段组成，且**串行**执行：`prepareHostStorage`（tasks-index，`<configDir>/tasks-index.sqlite`）先被 await，之后才是逐个 cwd 的 `prepareSessionStorage`（CLI 会话库，`<dataRoot>/cli/db/db.sqlite`）。两者是不同文件、不同 WAL，互不依赖，串行只是把两段固定成本相加。

改动（`packages/desktop/src/host/hostDatabaseStartup.ts`）：两库并行准备，同时保持原有可观察行为——阶段通知仍按 `preparing_host_storage → preparing_session_storage → starting_services` 顺序发出（会话阶段先缓冲、tasks-index 结束后补发），失败优先级仍按同一顺序判定；tasks-index 失败时不补发缓冲通知，直接进入 failed；会话库的拒绝先挂空处理器避免未处理拒绝。

明确**不做**（复核报告列为禁止项）：不删除第 2/3 个工作目录的会话库准备（相对 `sessionDbPath` 按各自 cwd 解析，删掉会让某个库静默未准备）；不跳过迁移前快照、backfill 与账本校验；不在 `prepare` 完成前释放端口或挂载服务。

### 结论（如实）

- 收益约 **250–300 ms**（总冷启动约 5 %、存储准备约 9 %），三个独立指标方向一致；落在复核预估 0.3–0.8 s 的下沿。
- **`<3 秒` 仍未达标**（改动后约 5.5 s）。该区域的固定成本（15.9 MB CLI 包启动、SQLite 建库/WAL/fsync）无法靠存储层改动消除；要达标必须把「首次可交互」与数据库就绪解耦，这属于产品/架构决策，本轮没有擅自改动。
- 对比的两个构建是不同提交、不同时间点测量，条件已逐项对齐（同机、同命令、同脚本、独立临时数据根）；不把该差值当作跨机器结论。
