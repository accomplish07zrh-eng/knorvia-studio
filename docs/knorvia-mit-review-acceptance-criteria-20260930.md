# MIT 来源复核的可执行验收标准

来源暴露是必须披露的事实，不是永久拒绝独立来源结论的规则。行为兼容测试、不同文件名或新的摘要也不是版权/许可结论。本项目继续保留适用的 Apache 和第三方声明，逐文件通过以下复核后才可增加摘要绑定的来源决定；不以分类数字作为目标。

1. 固定实际候选文件摘要、上游原路径/commit/blob 和保留第三方来源。提交链明确谁创作/修改，确认贡献许可链和用户授权覆盖；未知第三方或其他贡献者权利不能由本任务猜测。
2. 提供在生产变更之前形成的行为规格/黄金反例及实际新实现的设计依据。对照固定上游检查表达：区分公开 API、线格式、标准算法常量、错误兼容约束和受保护的具体实现；标明仍继承的片段。不能把逐行改写、拆文件或改名列为独立替换。
3. 新表达由独立复核者逐文件检查并记录依据。源码曾被阅读的作者可以提供设计/提交/表达对照，但需要复核实际表达，不将“曾阅读”一律当作权属不可能，也不把作者自述当成出版者授权。
4. 仍存在继承表达时，选择保留原适用许可/来源，取得所需权利，或按已冻结合同继续实质替换。合法第三方保留本身不要求重复重写；混合文件必须准确区分本地和第三方部分。标准许可正文及功能配置可走已有 retained-nature 流程，不能给整包授予 MIT。
5. 依赖、资产、生成器、缓存和实际交付包核对来源闭包，保留原通知。八份彩色图标需具体权属/许可材料或获授权替代，黑白图标声明不覆盖它们；其他未决材料继续通过出版者/固定源构建补证。
6. 将最终结论按现有 `licensing/reviews.json` 模型绑定实际摘要、非空 basis/evidence、适用 license，并运行冲突/失效门。产品保持 source/dist、真实消费者、数据循环和平台验收；最后验证交付产物没有绕过已审源码重新引入旧实现。

本恢复分支当前产物已有提交链、旧源摘要、黄金输出、新算法/所有者和构建绑定，缺的是上述逐文件表达/作者许可/保留片段复核与全库/交付闭包。source-exposed 重实现目前保持 Apache 是过渡状态，不代表未来必须重复重写全部新代码。可先审查本组行首索引、目录帧、协议 CRC/分片及 session 投影，明确哪些是新表达、哪些是兼容约束；收到有证据的结论后再更新来源决定，无须为 11% 的文件指标盲目重写。
