# Complete background resource owner: observable rules

Implement BackgroundTaskTracker (api.d.ts) and cohesive private modules if needed, in core/src/tool/executor. Private decomposition, names and representation are author choices. No new generic framework, duplicate state owner, cache of port capabilities, retry/notification/termination policy or extra permission behavior. Dependency bodies are not supplied and must remain unchanged. All fixed public output/model/log strings are retained compatibility facts, not new prose.

## Admission and ownership

The constructor retains deps by reference. One tracker deduplicates all tool names by task ID. Only plain records admitted by the existing isRecord predicate are launches. output.status='backgrounded' admits any name; 'async_launched' admits only existing Agent/Task aliases. Choose backgroundTaskId if it is a string (even empty), otherwise agentId if string. Empty/absent IDs or already tracked IDs are no-ops with no port/timer/event effects. This public method is native async even on no-op paths.

Reserve the ID synchronously, call unchanged registerRuntimeBackgroundTask(deps,call,id,launch,turnId), then publish BackgroundTaskStarted with status running and launch metadata. Registration exceptions propagate without removing the reservation. Started payload/publication failure removes reservation, calls unchanged removeRuntimeBackgroundTask and rethrows; removal error itself is not swallowed. No later stage runs before the started event await settles. Ports/logger/registry remain live deps, not constructor copies.

After Started, query snapshot-source availability then direct-wait availability independently (each resolves lifecycle capabilities anew), then info-log tracking.started. With neither: log tracking.lost/missing_snapshot_source, registry update lost, attempt notification with original launch metadata, await Completed/lost, release ID and return. That path has no finally cleanup on publication failures. Preserve partial effects rather than repair them.

## Providers and identity

Resolve provider behavior anew for each capability query, cancellation decoration and actual read. No global provider cache.

| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| Agent/Task                                                            | truthy subagentPort.getTask, captured method called with the live deps.subagentPort receiver         | none (even if that port has a waiter)                                                                              | Boolean(subagentPort.stopTask)              |
| CreateWorkflow/AmendWorkflow/ResumeWorkflowRun via existing predicate | when dynamicWorkflowRunPort is not undefined, call that captured port's getTask method               | same captured port if typeof waitForTask==='function'                                                              | typeof captured port.cancel==='function'    |

Direct wait/read calls pass task ID only: no signal/options, no cancellation subscription. Each actual read has its own native async function boundary returning the optional provider call (including absence), as do direct-wait and event emission. Preserve receiver binding and the phase in which dependencies are read. A provider can return undefined or reject/throw; do not normalize new errors or insert guards.

## Live resource lifetime

An admitted live attempt has independent overlap controls for snapshot poll and terminal publication, a stopped fact, last-running-signature initially empty string, interval handle and optional max-runtime handle. This owner alone manages these resources; registry remains a separate unchanged owner.

For Bash only, runtimeScope exactly subagent, subagentBackgroundBashMaxMs not undefined, and a truthy executionPort.cancelBackgroundTask: create one timeout with that exact delay (including 0). At firing warn max_runtime_exceeded, reread executionPort/cancelBackgroundTask and invoke it with task ID and its method receiver. Promise.resolve only wraps its returned value; returned rejection logs cancel_failed. A synchronous cancel throw escapes the timer callback. Timeout does not stop tracking or force a synthetic terminal state. Do not unref this timeout.

If there is a snapshot source: create a 1000ms interval whose callback fire-and-forgets one poll; optional interval.unref is called with its receiver. Await one immediate poll before starting any detached waiter. Poll no-ops when another poll is in flight, stopped, or no initial snapshot source. Otherwise mark in-flight, await native snapshot read, handle undefined/terminal through terminal publication or running through update publication, catch and warn polling failure, clear in-flight in finally. No new guard after awaiting the port: a previously admitted read may still return a running snapshot after another completion; preserve that running update. Future polls are gated by stopped.

Running signature is JSON.stringify with exactly {pid,stderrBytes,stderrTail,stdoutBytes,stdoutTail}; fields use `in` presence checks, undefined fields are omitted by JSON. Ignore all other fields/status for signature. Equal signatures do nothing. New signature is committed before registry update running, then await Updated event. Thus an event rejection does not roll back signature.

Terminal publication no-ops if stopped or already publishing. Otherwise mark publishing before effects and clear that flag in finally. Undefined snapshot: log snapshot_missing; update lost; attempt notification using original launch metadata; await Completed/lost; mark stopped and cleanup. Running snapshot from direct waiter: update running once, then run ordinary running publication (which may update running a second time); if no snapshot source, mark stopped/cleanup after that await; with a source remain active. Agent/Task terminal snapshot with type='local_agent' and notified===true: log already_handled, stop/cleanup, with no terminal registry update, notification or Completed event. Other terminal snapshots: log terminal; update registry with raw status/snapshot; attempt notification without launch-output fallback; await Completed using original launch metadata for event decoration; stop/cleanup. Cleanup clears truthy interval then truthy timeout, empties handles and deletes the shared ID. Failures before stopped/cleanup leave prior effects intact; no proactive retry is introduced.

If a direct waiter exists and the initial poll did not stop the attempt: launch one detached native async waiter, do not await it from trackBackgroundTask. It awaits the native provider-wait boundary then terminal publication. Rejection at any of those stages logs wait_failed; without a snapshot source, stop/cleanup, otherwise existing polling continues. Preserve no-op awaits, native Promise settlement and original failure boundaries. Do not add generations or suppress otherwise accepted late running publication.

## Event projection

Payload computes input via existing isRecord, then unchanged backgroundTaskOutputMetadata(snapshot,launch). Key order and explicit undefined presence:
taskId, toolCallId, toolName, taskKind, childSessionId, cancellable, command, description, status, pid, startedAt, completedAt, outputPath, stderrPersistedOutputPath, stdoutPersistedOutputPath, outputBytes, outputTruncated, outputTail, stderrBytes, stderrTail, stdoutBytes, stdoutTail, terminalId.

taskKind: Agent/Task→subagent; dynamic dispatch→workflow; everything else (including legacy Workflow)→bash. cancellable is false unless status==='running', which then queries current provider. command only string input.command. Dynamic description uses workflow subject below; otherwise string input.description, else present snapshot.description. pid uses snapshot `in` test; startedAt/completedAt are raw optional snapshot values. Metadata fields map respectively childSessionId/outputFile/stderrFile/stdoutFile/outputBytes/outputTruncated/outputTail/stderrBytes/stderrTail/stdoutBytes/stdoutTail. terminalId always task ID.

Event emission is native async and awaits deps.emitEvent with key order {id:crypto.randomUUID(),sessionId:live deps.sessionId,turnId,type,timestamp:new Date(),traceId:traceContext.traceId,sequenceNumber:0,payload}. Its caller also awaits this boundary; preserve original asynchronous settlement. No actual external events are sent while authoring.

## Notification authority and publication

If enqueue port absent, debug queue_unavailable and return before any suppression/claim. Superseded workflow terminal: claim unchanged registry notification first (ignore returned bool), log suppression/workflow_run_superseded, return without policy/format/enqueue. Otherwise optional policy receives {runtimeScope,status,taskId,toolName,traceContext}; only strict false suppresses and logs, without claim. Policy exceptions propagate to the existing caller boundary.

Then format text. Empty/undefined text logs skipped/empty_message and returns. Then claim; false logs already_handled and returns. Only after a true claim enter a synchronous enqueue try. Build origin metadata and enqueue {optional originMeta,taskId,text,toolName,traceContext}. Bash origin is {backgroundSource:'bash',title,workId}; dynamic origin described below; legacy/other omit origin. Any origin-building or enqueue throw releases claim, warns enqueue failed, returns; release/warn throws are not newly swallowed. Success info-logs enqueued. Do not await an enqueue return, add retry, notify Agent again or broaden policy.

Formatting dispatch: Workflow or dynamic→workflow; Bash→bash; all other names→undefined. Normalize status completed→completed; cancelled/timed_out/killed/stopped→killed; everything else→failed. Bash summary subject is string input.description ?? string input.command ?? 'Bash background command' (empty strings preserved). Prefix `Background command "${subject}"`; lost suffix ` failed because its in-process state was lost`; completed suffix ` completed` plus optional ` (exit code ${exitCode})`; failed suffix ` failed` plus optional ` with exit code ${exitCode}`; killed suffix ` was stopped`. Use existing formatTaskNotification with key order {description,outputFile,status,summary,taskId,taskType:'local_bash',toolUseId}. Bash origin title independently trims description then command and picks first truthy of those, tool name, task ID.

## Workflow output and manifest

Workflow subject: first non-nullish string from input.description, present snapshot.description, present snapshot.name, record output.name, input.name, input.scriptPath, then task ID. Empty strings count. The 'output' for subject/legacy response is record snapshot.output if present and isRecord, otherwise launch fallback. RuntimeString accepts string only; stringField reads one property and accepts string only.

Terminal facts: snapshot declared runStatus among completed/errored/stopped wins; otherwise raw status completed→completed, failed→errored, cancelled→stopped; all others yield no terminal facts. stopReason is included only for stopped and one of user/model/provider/interrupted/superseded. A record snapshot.failure is included (unchanged object reference). Formatting stopReason falls back to deps.runtimeTaskRegistry.get(taskId)?.stopInitiator only when raw status cancelled and no terminal stopReason.

Workflow summary prefix `Workflow "${subject}"`. Lost→` failed because its in-process state was lost.`; errored→` errored: the script failed.`; stopped or normalized killed: user→` was stopped by the user.`, model→` was stopped by you (TaskStop).`, provider→` was stopped on a provider error.`, interrupted→` was stopped: the process that owned it exited.`, superseded→` was stopped and superseded by an amended run.`, otherwise→` was stopped.`. Other completed→` completed.`, all others→` failed.`.

Dynamic result calls unchanged serializeWorkflowArtifact on snapshot.output raw if present, never launch output. Legacy result is string output.response, allowing its own launch fallback. Dynamic reports use Array.isArray snapshot.reports else undefined then existing report-notification helper. Dynamic artifacts use existing toPublishedArtifactSummaries only if snapshot.artifacts is present, then existing artifact-notification helper with existing MAX_LINES. Dynamic script path is string nonempty snapshot.scriptPath; if so existing describeWorkflowScriptPath(path,deps.getWorkingDirectory()). Legacy uses none of these dynamic-only additions.

Call existing formatTaskNotification with key order: description; dynamic-only deliveryGuidance:true; optional scriptPath; error (string snapshot.error only); optional reports; optional artifacts; result; normalized status; optional runStatus; optional stopReason; optional failure; summary; taskId; taskType:'local_workflow'; toolUseId. Preserve explicit error/result undefined and omission of optional dynamic fields.

Dynamic enqueue origin: subject again from call/snapshot/output; build terminal manifest then {backgroundSource:'workflow',title:subject,workId:taskId,optional workflowNotification}. Manifest exists only when raw status is completed/failed/cancelled AND snapshot is present. It starts {kind:'terminal',status:declared/normalized terminal fact,optional stopReason,summary:subject.slice(0,500)}. Use raw snapshot.output and existing serializer; defined result is clipped at 4000 with resultTruncated:true only if longer; resultForm='prose' for string raw output otherwise 'json'. String snapshot.error clipped at2000. Reports use existing manifest helper; artifacts use existing manifest helper and include artifacts plus artifactsTruncated:true only when helper says so. durationMs added last only when startedAt/completedAt are instanceof Date and difference is finite >=0. No usage/tokens are invented. Construction order: terminal facts/initial fields, result/resultTruncated/resultForm, error, reports, artifacts/artifactsTruncated, duration. This is persisted projection safety, not a new schema.

All log facts include existing traceContextToLogContext(traceContext), fixed module:'core.tool.executor', taskId; add toolName when the event catalog says so; polling/wait/cancel/enqueue failures use errorMessage = Error.message else String(error). Tracking-start includes booleans hasDirectWaiter/hasSnapshotProvider; terminal-observed includes raw snapshot status as taskStatus; queue/suppression/enqueued records include raw status as taskStatus. Do not swallow logger errors beyond original catch boundaries, or rename any strings.
