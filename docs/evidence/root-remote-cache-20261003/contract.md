# Remote asset cache: author behavior contract

Implement only `packages/server/src/remote/remoteAssetCache.ts`. The accompanying declarations are the complete public surface; dependency declarations identify existing collaborators to import, not replace. This packet contains curator-derived behavior, API and wire/storage constants, not inherited function bodies, test bodies, implementation pseudocode or explanatory source commentary. The curator has read the inherited implementation. The author should not read that implementation, its history or its tests before freezing a complete draft. No author architecture, helper layout, loop form or private identifier is prescribed.

## 1. Public values, normalization and ownership

Manifest parsing returns a fresh plain manifest with own keys in this order: schemaVersion, appVersion, platformArch, components. Each accepted component is a fresh plain object ordered id, version, sha256, artifactPath, mount. Unknown input properties are dropped. Supplied `manifestRef` objects are trusted snapshots: do not reparse, clone, freeze or silently repair them. Component selection with no effective filter returns the original manifest.components array; filtered selection creates an array in manifest order containing the original component references. Neither operation mutates the manifest.

An absent componentIds option, empty array or all-whitespace array means all components. Otherwise trim each id, discard empty strings and deduplicate in first-seen order. Valid ids match lowercase ASCII letter/digit initially, then lowercase ASCII letters/digits/hyphens. Selection reports all missing requested ids in request order, separated by comma-space. Required release paths pass through the existing relative-path normalizer with label `requiredReleasePath` and are deduplicated in first-seen order.

CDN bases come from resolveRemoteCdnBaseUrls(options); version, platformArch and remoteCacheDir are trimmed. Public manifest fetch returns null when any required field/base list is missing. Public ensure rejects instead (exact strings in messages.md). Validate appVersion then platformArch as nonempty single path segments: slash/backslash forbidden, exactly dot/dot-dot forbidden. Then call existing CDN/version guard. Only ensure normalizes componentIds and requiredReleasePaths at admission; public manifest fetch does not inspect them.

The fallback cache path is Node path.join(Node os.tmpdir(), `knorvia-remote-assets-cache`), without filesystem work. Manifest candidates are a new one-element array: `manifest-${platformArch}.json`; that public helper does no input trimming/validation. Component cache-version normalization examines the suffix after the last plus: remove that plus and suffix only if the suffix is 12–64 ASCII hexadecimal characters, case-insensitively. Other strings are returned unchanged (including whitespace and earlier plus signs).

Content-addressed ids are `server-bundle` and `knorvia`. Compatibility edge: the public membership predicate also reports true for inherited Object.prototype property names; it is not presently an own-property-only predicate. Preserve or explicitly flag this observed edge rather than silently claiming strict equivalence after hardening it. Parsed ordinary component ids use the table in section 2; the inherited `constructor` name is an anomalous valid-pattern id that reaches a native TypeError at mount resolution after its other fields validate. It is not a supported component.

## 2. Manifest parser and dependency boundaries

Read response.text() once, then JSON.parse. A response-text rejection propagates unchanged. Wrap JSON syntax failures with the source URL and String(error). Require a nonnull non-array object; schemaVersion must first be a finite number, then integer exactly 1. Read/trim appVersion and compare to expectedAppVersion exactly (do not trim expectations); next read/trim platformArch and compare exactly. components must be a nonempty array. Validation is ordered and stops at its first error.

For each component in input order, require nonnull non-array object; read/trim id; validate pattern; reject duplicate id before checking support. Unknown ordinary ids are skipped without validating their other fields, but still reserve their id for duplicate detection. Thus a nonempty raw array containing only unknown ids returns an empty accepted component array. For supported ids, validate in order: trimmed version and safe-segment check; trimmed/lowercased sha256 exactly 64 hexadecimal characters; trimmed artifactPath normalized with its field label; trimmed mount similarly; expected mount normalized with label `expected mount for ${id}`; exact mount equality. No implicit mandatory component set is imposed.

| id | exact mount for platform P | component root under cache C |
| --- | --- | --- |
| server-bundle | server | C/components/server-bundle |
| node-runtime | node/P | C/components/node-runtime/P |
| node-pty | node-pty/P | C/components/node-pty/P |
| knorvia | knorvia/P | C/components/knorvia/P |
| bfs | tools/P/bfs | C/components/bfs/P |
| ripgrep | tools/P/ripgrep | C/components/ripgrep/P |
| ugrep | tools/P/ugrep | C/components/ugrep/P |

Use existing CDN helpers for candidate ordering, encoding, path normalization and version mismatch errors. Their declaration file has all required signatures. `fileExists(...parts)` is asynchronous joined-path access existence (any access error becomes false; it does not require a regular file). `extractTarGzArchive(archivePath,targetDir)` is the existing asynchronous extractor; await it and propagate its errors, without reimplementing archive policy. `resolveRemoteAssetFetch(network)` yields the injected fetch or global fetch bound to globalThis. Preserve the injected fetch and avoid importing other-lane implementation. Standard Node crypto/fs/fs-promises/path/os/stream/timer APIs and global Response/AbortSignal remain available.

## 3. Manifest requests, errors and retained snapshots

The public signal factory defaults to 10,000 ms, rejects anything other than a positive safe integer with the specified Error, and returns AbortSignal.timeout(timeoutMs). Platform-specific factory errors propagate. Each manifest CDN candidate receives a fresh signal and fetch(candidate, {signal}); signal construction occurs outside request-error aggregation. Candidate requests are sequential. HTTP 404 contributes no error. Other non-ok responses contribute `URL -> HTTP STATUS`; thrown fetch errors contribute `URL -> String(error)`. A successful response is parsed before acceptance. A parser/body failure aborts the whole operation immediately unless its request signal is already aborted, in which case record it as that candidate's error and try the next. No all-candidate retry pass, implicit old archive fallback or additional timeout is introduced. All-404/no-candidate returns null; any accumulated errors without success reject with the aggregate message.

Successful parsed results emit one downloading log for the chosen manifest URL after parsing. The winning source's release base (trailing slashes removed, longest matching nonempty URL prefix with slash boundary) is placed first in component base candidates; remaining candidates equal to that selected normalized base are removed, others retain order. If none matches, preserve the original candidate array reference. Result own keys are manifest then releaseBaseCandidatesForComponents. The manifest-only public wrapper returns that same manifest reference, or null.

Manifest cache identity comprises absolute resolved cache directory, trimmed app version, trimmed platformArch, timeout identity (`default` when nullish, otherwise String(value)), then ordered normalized CDN bases, joined with `::`. Component filter, network object, forceRefresh and logger are not part of this identity. Successful results remain cached in memory for module lifetime; no disk manifest read substitutes for a fetch and no eviction timer exists. Null/rejected results are removed if still current, so a later call can retry.

Concurrent calls share the active work. A caller first joins an active refresh, including one begun while it awaited a prior request or made an asynchronous refresh decision. Refreshes for the same identity share one task and publish the same snapshot. refreshManifest is honored by public fetch/ref fetch: refresh a retained nonnull result; an already-running refresh is joined. A refresh failure replaces/evicts the prior cache task, not a stale-success fallback. A normal caller after a completed refresh sees its retained result. Sharing is about work/result references, not guaranteed identity of the async public wrapper Promise objects. Logger and network used by a started request are those of the initiating operation.

## 4. Release selection, paths and cache admission

Base release directory: Node join(C, `releases`, version, P). Append content segments in fixed order server-bundle then knorvia when explicitly requested and selected: `server-content`, server SHA; `knorvia-content`, knorvia SHA. An all-components request includes only the selected knorvia content segment, preserving historical full-release layout. No available matching selected component means no segment for it.

A ready full release is a directory, then accessible `server/knorvia-server.cjs`, then accessible `node/P/node`, then accessible `.ready` or `.remote-assets-ready`, in that precedence. Additional required paths must exist by stat, not necessarily be regular files. Any stat failure counts as absence. Component readiness requires a directory and one of those markers, then stat existence for its relative required paths. Marker contents are not validated for readiness. Required-path resolution normalizes with label `required cache path`, resolves beneath the base and rejects lexical escape; no new realpath/symlink expansion is added at this step.

Ensure may reuse the base ready release before manifest resolution only when not forceRefresh and the effective explicit selected set contains neither content-addressed id. All-components counts as content-addressed for this decision. This fast path can bypass a supplied null manifestRef because it already has a valid ordinary release. The fast-path readiness check is repeated for the initiating internal operation. After choosing a manifest/content path, any ready release satisfying required paths can be reused unless forceRefresh; this includes content-addressed paths without rehashing cached contents.

After an outer fast-path miss, warn that a release download is required before joining/starting its work. Outer release work identity: resolved base release directory; sorted normalized requested ids joined by comma or `<all>`; pinned content segment identity when applicable and a truthy manifestRef supplies it, otherwise `<unpinned>` (or `<missing-manifest>` for null); `force`/`reuse`; timeout identity. Fields are joined with `::`. CDN bases, required paths, network, refreshManifest and the complete ordinary manifest are not included. Concurrent waiters join this work; rejection propagates unchanged. On success each waiter rechecks its own required paths (not the full ready predicate). Missing paths produce the locked-release warning and require another attempt rather than returning an incomplete directory. Work identity is released after success/failure.

## 5. Pinned manifests and ensure refresh policy

A truthy supplied manifestRef bypasses fetching and uses its manifest and component base candidates by reference. Explicit null means manifest absence already pinned for this transaction: after applicable ordinary fast paths it rejects manifest-not-found without a request. Undefined fetches normally. `refreshManifest` is not passed through by ensure; its direct effect belongs to the public fetch APIs only. `forceRefresh` skips release/component cache reuse and migration but does not by itself request a new manifest.

For unpinned content-addressed ensure, a cached manifest refresh is requested only if selection under that cached snapshot yields content segments and a stat finds `manifest-P.json` at that resulting content-addressed release path. The existing marker/content validity is not part of that refresh trigger. First-time fetches also participate in active-refresh sharing. A null manifest result rejects manifest-not-found; do not probe historical monolithic archives.

Selected components are obtained in manifest order. Each selected component is ensured before any release materialization begins, preserving sequential download settlement. Required component paths are the normalized release paths strictly below `component.mount/`; strip that prefix. An exact mount path or a path outside that mount adds no component-level requirement.

## 6. Component reuse, downloads and integrity

Append to the component root from section 2 the component sha256 for server-bundle/knorvia, otherwise the normalized component version. SHA is archive identity; do not replace it with unpacked-content hash. Components are shared across app versions when their directory identity matches. Non-whitelisted supplied component ids reject when resolving their component root.

Concurrent component work is keyed only by resolved component directory (not forceRefresh, required paths, URL, logger or network). Existing active work is joined even by forced callers. After joining, recheck component readiness plus this caller's required relative paths; if incomplete warn and attempt again. A rejected active task rejects its waiter. Remove the task on settlement. Before creating work, non-forced ready components return immediately, and readiness is checked again inside the initiating task.

Forced work emits its force warning and bypasses migration/reuse/removal of the old ready component until replacement. Non-forced work with a ready marker but missing required paths warns and recursively force-removes that cache directory before migration/download. Non-ready contents are not pre-removed; later atomic replacement handles them. For ordinary ids only, first attempt old hash-version component migration, then old release migration. After either migration, verify this caller's required paths; if missing, warn/remove and continue toward the next source/download. Do not migrate content-addressed ids or forced work.

Build artifact candidates using the existing component URL helper. Try candidates sequentially with fetch(candidate), with no request options or added manifest timeout. First response.ok wins. Non-ok statuses (including 404) and thrown errors are aggregated. An accepted response's later body/checksum/extraction failure does not fall through to another CDN. Log the chosen URL, stream its body into a staging archive, calculate SHA-256 of the actual archive bytes, compare exact lowercase computed hex to component.sha256, then extract and require at least one extraction-root entry. Write `.ready` only after successful extraction/nonempty check, atomically commit to the component cache, then return its path. A downloaded archive is not separately checked against required paths before this initiating caller proceeds; these checks govern cache reuse/migration/waiters, not new-download acceptance. Preserve this limitation explicitly.

Streaming requires nonnull response.body or rejects `response body is empty`. Create parent dirs, open archive for overwrite and pipeline Node Readable.fromWeb through byte progress accounting into the file. Pipeline failures propagate and do not emit a forced successful-final progress snapshot. Component staging lives under C/staging with name `remote-component-ID-P-VERSION-PID-UUID`, archive `component.tar.gz`, extraction child `extract`. Cleanup recursively force-removes the outer staging directory in finally; cleanup failure can replace success or a prior failure.

## 7. Migration compatibility

Old component-cache migration inspects the current component root; a readdir failure means no migration. Consider ready directory siblings whose names begin normalizedVersion plus `+`, excluding the target's resolved path. Choose the greatest stat.mtimeMs (stable prior directory enumeration order for ties). No archive SHA or content hash verification is performed for this migration. Stat failure for a candidate is not ignored. Source label in success log is `legacy component cache VERSION`.

Old release migration requires the component version's last-plus suffix to be 12–64 hex characters; lowercase it as expected unpacked-content hash prefix. A releases-root readdir failure means no migration. Consider directory versions other than the current app version in descending localeCompare name order. Require a ready full release for P and a directory at the normalized contained component mount. Compute the existing unpacked-content digest protocol below; digest errors produce a skip warning and advance to the next candidate. Choose the first matching digest prefix; source label is `legacy release VERSION`. A matching candidate's later migration error propagates rather than trying a different candidate.

Migration materializes source contents to C/staging/`remote-component-migrate-ID-P-VERSION-PID-UUID`/component, requires a nonempty resulting directory, writes `.ready`, atomically replaces the target component, emits the success log, and finally removes outer staging. Do not remove the source cache/release. Hash-version migration precedes release migration even if its content would not match the latter's hash protocol.

Unpacked-content SHA-256 byte protocol (necessary stored identity, not an implementation prescription): start with UTF-8 `root:dir\n` for a directory or `root:file\n` for a file. Within directories use entry-name localeCompare ascending depth-first ordering. Before a directory's descendants append UTF-8 `dir:RELATIVE_POSIX_PATH:MODE\n`, where MODE is stat.mode masked to 0777 rendered in decimal. For each regular file append `file:RELATIVE_POSIX_PATH:MODE:SIZE\n` then its exact raw bytes. A file root uses relative name `root-file`. Root-directory mode is not included. Directory hash includes marker files; there is no materialization-style marker exclusion. Unsupported entry types (including symlinks encountered as entries) reject. Root stat follows symlinks, as does other stat-based existence logic. Digest is lowercase hex.

## 8. Release materialization and filesystem commit

After all selected component caches are ready, serialize materialization by resolved final release directory. A later queued job runs even if its predecessor failed. Locks clear only if still current. Create the release directory; materialize each selected component into its mount in manifest order; write UTF-8 compact JSON.stringify of the complete supplied manifest plus newline to `manifest-P.json`. For an explicit selected set, return without validating a full release or adding a release marker. For all-components, validate server/runtime paths and then write `.ready`. A partial operation may preserve an existing marker; it does not proactively remove one. Empty selected arrays are possible through a trusted/unknown-only manifest. All-components still validates full readiness prerequisites after writing the manifest.

Each mount is staged separately under C/staging/`remote-release-component-ID-P-PID-UUID`/component, populated, checked nonempty, then atomically replaces the contained mount path. Whole-release publication is not atomic: earlier committed mounts remain if a later mount/manifest/marker fails. Existing unrelated release entries persist. There is no final requiredReleasePaths validation after initiating materialization.

Materialization copies directory structure while omitting entries named `.ready` or `.remote-assets-ready` at every depth. Reject symlinks and unsupported entry types. For regular files try hard linking first; fall back to exclusive copy only for EXDEV, EPERM, EACCES or EMLINK. Other errors propagate; never overwrite an existing target file silently. Recreated directory modes follow mkdir defaults; files linked/copied keep platform API behavior. Cache and release files may therefore share an inode: no promise of byte isolation after external writes is added.

Atomic directory commit creates the destination parent. If stat says the destination exists, rename it to `${targetDir}.backup-${pid}-${uuid}` before promoting staging. If promotion fails, restore that backup; when restoration also fails reject the combined commit/restore Error. Otherwise rethrow the original promotion error unchanged. After success remove backup best-effort. Rename retries use waits 50, 100, 200, 400, 800, 1600, 3200 ms only for EPERM, EBUSY, EACCES, ENOTEMPTY; terminal failure propagates. Best-effort backup removal has the same delays/error-code policy but discards its terminal error. Ordinary outer staging removal is not best-effort/retried. There are no cross-process locks, fsync guarantees or recovery scans for stranded backups.

## 9. Progress, markers and observable errors

Ready-marker writes are UTF-8 decimal Date.now() plus newline. Public readCachedRemoteAssetMarker tries `.ready` then `.remote-assets-ready`, returns the first successful UTF-8 read unchanged (including empty text), ignores any read error and returns null only if neither can be read. It does not check directory validity first.

Progress uses actual transferred chunk.byteLength. Parse content-length by base-10 parseInt; missing/empty, nonfinite or <=0 means unknown total. MB is bytes/(1024*1024); mean speed uses max((Date.now()-start)/1000, 0.001). Known percent is min(transferred/total*100,100). Reporting is eligible when at least 1000ms since last log, at least 5 percentage points since last logged percent, or known percent >=100; successful pipeline completion forces a report. Initial last-log timestamp/percent are zero, last transferred is -1. Suppress a forced report when byte count is unchanged and percent is unknown or no greater than the last logged percent. Do not suppress non-forced repeated 100% reports by that rule. Update last-log state only after a successful log call. Emit exact formats in messages.md (one decimal percent/MB, two decimals MB/s).

All log calls are synchronous property calls on the supplied logger object; do not await returned values or swallow exceptions. Logger exceptions can stop work. Default errors from filesystem, crypto, streams, dependencies and trusted malformed inputs propagate unless a specific recovery/aggregation rule above applies. No new cancellation policy, parallel downloads, timer eviction, disk-manifest fallback or retries outside the stated policies is implied.

The packet describes ordinary typed inputs plus stated compatibility edges. It does not require emulating arbitrary monkeypatched Node APIs or exotic property-getter timings not specified here. Keep reference-sharing, gate ordering and cache identity observable behavior. Any uncertain boundary discovered during authoring should be reported before a compatibility claim.
