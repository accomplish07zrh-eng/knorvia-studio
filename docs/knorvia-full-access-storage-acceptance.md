# 完全访问授权提交协调验收

固定基线 `fd4bc58`，按先行 `specs/knorvia-full-access-storage.md` 将持久提交表达为同步动作程序和唯一 SQLite 事务 owner。动作只表达 receipt 查询、队列读写准备、固定条目处理和 entry 写入，不持有第二份权限或队列状态。Runtime 的固定集合、内存模式、传输和恢复逻辑未改动。

## 来源限定

已接触旧源码，不作无接触声明。本批独立判断限于新动作程序、操作解释和事务准入/终止协调，不以拆文件、命名调整或测试通过单独判断。固定字段、错误文案、SQL 条件和平台事务语义是兼容约束，不主张为原创发明。

只读来源复核指出，旧 JSON 解析、两字段遍历和 mode 投影仍基本沿用原表达。因此该部分明确放在 `permission-full-access-payload.ts`，继续标注 **Apache-2.0**，不计原创或独立替换。其原路径、固定 blob 和摘要见 [载荷来源记录](../licensing/evidence/full-access-payload.md)，人工分类为继承的第三方代码；新路径不等于无来源。新程序依赖此保留投影，不能声称完全访问授权链已经全部独立。

根 Apache-2.0、0.8.0-preview.3、原 SessionStorePort/facade、saveSessionEntry、JSON/codecs、迁移、Runtime、公共 schema、UI、安装/便携和官网保持适用原边界。本批没有访问真实用户数据库、模型、浏览器或设备；最终整仓 MIT/稳定发行仍未完成。

## 修复与兼容

真实新建内存 SQLite 的 UPDATE 触发器执行 RAISE(ROLLBACK) 后，旧版再次 ROLLBACK 会用“没有活动事务”覆盖原始队列失败。新 owner 只在自有事务仍活动时清理；已自动回滚直接传播首因，清理再次失败则 AggregateError 保留两因。BEGIN 失败不执行程序或回滚，同连接已有事务不接管。

已有事务的显式守卫有意将错误从 SQLite 的 ERR_SQLITE_ERROR/errcode=1 改为应用 Error；事务保护保持，但不能把诊断字段写成完全一致。其他两个有意失败变化是自动回滚首因与双失败聚合。

取消先于输入 session 校验；receipt 同 session 重试直接提交返回，不重新选取或扩大目标。固定队列按原顺序逐项处理，仍要求同 session 且 admitted；未知载荷、其他输入和已有缺席/非对象 intent 保留。两份 entry 沿原唯一写路径依次保存，touchSession 及时间戳保持，提交后 Runtime 才能继续原内存和事件发布。

## 测试与有限复核

先行 19 项旧版 **17 通过、2 预期失败**，失败分别为自动回滚首因和回滚双失败；首稿修复后 19/19 通过。随后新增 live session 读取回归先失败：计划提前捕获 scope，改变原 read/write 各一次的读取合同；固定旧版探针确认六次读取，修复为动作携带原输入、各阶段惰性读取。该有限 getter 反例不描述为普通 Runtime 现场故障。

只读复核再发现受控 StatementSync 替身下，内联投影让 write.run getter 先于坏 JSON 解析，掩盖原 SyntaxError。新用例先红（10 通过、1 失败）后修，现先解析/投影、再取得写方法，序列化仍在原参数阶段。receipt 同样在 SELECT 准备后才读取 ID；prepare 先失败时不提前读取后续 getter。复核未代替跨进程或最终编译验收。

最终新增 **21 项**合同通过，含原审批准备/失败重试组合共 **30/30** 通过。覆盖成功原子写、固定队列、同 receipt 重试、跨 session 冲突、缺失/非 admitted/坏 JSON、第二条队列及 execution/receipt 写失败回滚、取消、已有事务、BEGIN/COMMIT 失败和两类清理失败。

源码及编译分别通过 **243 个有限场景**、各使用 486 个独立内存库：载荷对象/数组/标量/坏 JSON、三种目标列表、receipt 三种状态、正常/队列失败/提交失败。比较完整存储行、真实 SQL 写观察、微任务轨迹及结果，并对正常案例另断言确已成功、写数量符合预期。初版对照脚本的变长 SQL 观察函数未声明 varargs，不能作为成功路径证据；已修正并加入成功/写数量断言后全部重新运行，以 source-final 和 compiled 日志为准。
