## Finding 1: phase lifetime needs explicit functional clarification

Draft line **114** captures `options.phase` once, before `createActivityId`. Later trace attributes, active/completed/failed activities, artifact metadata, runner input, prompt generation, expansion-record publication and the draft's own events use that local value (lines 125, 144, 161, 186, 201–202, 222, 232, 242, 250, 280, 297 and 307). Corrected `39cc7b5` and the publisher instead read `options.phase` at these observations, including after awaited publication ports.

A concrete static trigger uses ordinary mutable records: start with phase `phase-a`; let the first `writeSnapshot` port change the shared options' phase to `phase-b` before it resolves. The predecessor's subsequent `planner_started` event, runner phase and prompt phase observe `phase-b`. This draft continues using `phase-a`. Its final `emitExpansionEvents` call still receives the original options reference and that dependency reads the current phase, so one attempt can also split its completion and expansion events across different phases. A synchronous `createActivityId` mutation creates an even earlier difference in trace and active-activity phase. No getter, proxy, invalid schema value or monkey-patched built-in is needed.

The public options interface declares a writable `phase: string`, and the direct scheduler consumer forwards its options reference unchanged at `scheduler.ts` lines 73–78. That does not prove a current production caller intentionally mutates phase; this is a statically established compatibility difference under an allowed mutable input, not a reproduced user failure. The frozen packet uses “phase” as shorthand at many observations and does not explicitly contrast a live property with an attempt-entry capture. Record that specification ambiguity rather than silently amending its bytes or assigning all responsibility to the author.

**Functional clarification needed:** phase is read from the original run-options object at each specified trace, activity, prompt, runner, artifact, record and event observation. A mutation during an earlier callback or awaited port is visible to later observations; phase is not an immutable attempt fact. Preserve the explicitly captured numeric run count, start time, child trace and failure count/exhaustion facts separately. This clarification describes observations only; it does not prescribe a private implementation or provide a patch. If root instead excludes all such option mutation, that is an explicit compatibility-scope decision, not evidence that this draft preserves the wider source behavior.

## Finding 2: result aggregation imposes an argument-count limit

Draft line **99** calls `addedNodeIds.push(...outcome.addedNodeIds)`. Corrected `39cc7b5` planner line **72** appends IDs individually. Both preserve order and duplicates for ordinary short arrays, but the draft turns the number of returned IDs into a JavaScript call's argument count. A sufficiently large valid returned array can therefore reject the sweep at aggregation after the attempt's publications have already completed. The corrected loop does not impose this argument-count bound. The precise engine threshold was not measured here, and no large-graph or runtime test was run.

The public planner-result schema at `workflow/index.ts` lines 336–343 uses an array of nodes without a maximum length, and the pinned expansion owner maps that result without a node-count cap. The packet supplies no small-array guarantee. The publisher itself uses argument-spread at line 124: this is a common idiom and a convergence with the older implementation, but the integration target is the corrected behavior at `39cc7b5`. Do not use a match to the publisher to dismiss that target difference.

**Functional clarification needed:** aggregate all returned IDs in order, including duplicates, without an additional limit based on the JavaScript function-argument budget. This is a bounded static integration concern; it is not evidence of a new broad-suite failure, nor a reason to invent a product node limit. Root can resolve it in a separately bound descendant and its direct owner checks.
