# dynamic-workflow-02 调用方（callers.md）

v1。目的：重写时不得破坏这些调用方依赖的**模块路径、导出名与签名**。逐文件原始清单见机器生成的 [`callers-raw.txt`](callers-raw.txt)（`tests/scan-callers.mjs` 输出，本文所有计数都由该脚本与 `tests/gen-interface.mjs` 的解析结果产生）。

## 扫描口径

- 本包 **40 个范围文件 / 537 项导出**的符号级 `findReferences`（`pnpm dep:refs` 同款逻辑）在本机内存溢出（V8 OOM，见 `acceptance.md`）。因此 callers.md 用两层扫描覆盖 import 面：
  1. **语法级 import 扫描**（`tests/scan-callers.mjs`）：全仓 11,427 个源文件（`.ts/.tsx/.mts/.cts/.mjs/.cjs/.json`，跳过 node_modules/dist/build/coverage/out/.git/third-party）的 `import` / `export … from` / 动态 `import()` 说明符，聚合出「谁以哪个说明符导入了哪些名字」。这层覆盖全部静态可见的调用方。
  2. **字符串路径扫描**：按 `new URL("src/engine/…")` 这类字符串拼出的模块路径单独人工核对（dep:refs 与语法扫描都看不到）。**本包范围内核对结果为零**：全仓没有任何脚本或测试夹具按字符串路径指进 `src/{engine,facade,lowering,schema}/*` 或 `dist/{engine,facade,lowering,schema}/*`，也没有任何 sha256 基线 pin 这 40 个文件。唯一 pin 到 `dynamic-workflow/src/**` 的基线是 `core/test/causality-order-strands-baseline.json`，指向 `analysis/`，属 dynamic-workflow-01（其 K10）。
- 范围文件之间的互相 import **不算调用方**（是实现细节）：脚本按 `tests/scope.mjs` 的 40 文件集合排除。

各消费方依赖的兼容面形状：

1. **adapters（8 个文件）＝ 纯记录类型 + Journal 端口**。只引用 `engine/types.ts` 的 12 个名字（`JournalStorePort`、`RunRecord`、`NodeRecord`、`ActorRecord`、`StoredEvent`、`RunEvent`、`RunSettlementRecord`、`RunStatus`、`RunStopReason`、`NodeKind`、`NodeRecordStatus`、`WorkflowErrorJson`）。SQLite 仓储的列编解码把**字段名当表 schema 用**（`dwf_run`/`dwf_node`/`dwf_actor`/`dwf_event` 四张表），所以这些记录的字段改名、改可选性、改枚举取值都会直接破坏既有持久化行——B1–B4（记录形状）与 B24（journal 端口）就是为这一面而设。
2. **bootstrap（37 个文件）＝ 驱动侧 + 展示侧 + 上限常量**。`workflow-driver*.ts` 一组只用 Boundary B 词汇（`WorkflowDriver`、`SubmitVerdict`、`InstanceRef`、`ActorRef`、`PersonaSpec`、`AskMessage`、`AskLastTool`、`WorkflowReportSink`、`refToString`、`WorkflowError`）；`dynamic-workflow-run-*.ts` 一组用记录类型 + 编译/lowering/schema 管线（`createWorkflowProgram`→dw01、`lowerWorkflow`、`collectSites`→dw01、`buildAskSpecs`、`synthesizeAskSchemas`、`validate`、`deriveActorSubmitProfilesFor`）；`workflow-{world-read,artifact-publish,concurrency-governor}.ts` 用 facade 上限与并发控制器。
3. **dynamic-workflow-runtime（2 个文件）＝ Boundary B 的唯一真实 driver**。`harness.ts` 引用 `WorkflowEngine`、`WorkflowDriver`、`lowerWorkflowScript`、`Caps`、`AskSpec`、`ValidateFn`、`ImportedRunCache`、`RunSettlement`、`WorkflowError`、`WorkflowReportSink`、`ActorId`；`protocol.ts` 只用注册表的 op 联合类型（`WorldReadOp`、`ArtifactContentOp`、`ArtifactPresetOp`）。`harness.ts` 决定脚本抛错时编码成 `DriverError`——B4 的结算约定据此钉住（本包合同夹具不能反过来假设别的码）。
4. **core（4 个文件）＝ facade 文本进模型提示词**。只引用 `FACADE_DTS` / `SNIPPET_FACADE_DTS`：工具描述逐字把这两份 .d.ts 贴给写脚本的模型。这是 facade 资产必须逐字节锁定的直接原因（见 `README.md`「facade 资产的锁定口径」与 `known-differences.md` K9）。

## 其它兼容边界

- **exports map 只有两项**：`.` → `./dist/index.js`（types `./dist/index.d.ts`）、`./projections` → `./dist/projections.js`。包外无法按子路径 import，所以「包外兼容面 = 两个入口桶的再导出面」。本包范围**含这两个桶文件本身**（`src/index.ts`、`src/projections.ts`，即 scope 的 `""` 桶 2 个文件；dw01 把它们写成「不重写」，实际归属本包）。重写可以重组桶的内部实现，**但再导出的名字集合与来源模块路径是冻结面**（`surface.test.mjs` 的导出面录制逐条比对）。
- **projections 桶的浏览器安全不变式**：dw01 的分析符号经 projections 进 core 工具，projections 桶不得引入任何 node-only 依赖（renderer 侧要能打包）。本包重写 `projections.ts` 时如果把 engine/facade 侧的 node-only 实现再导出进去，即破坏该不变式——`surface.test.mjs` 有专门断言。
- **零消费者的入口导出**：`artifactFamilyOf`、`formatViolations`、`serializeSchema`、`synthesizeWorkflowSchemas` 由入口桶再导出，但全仓（`apps` + `packages`）**没有任何引用点**；`knip --include=exports,nsExports,types,nsTypes -W @knorvia/dynamic-workflow` 输出为空（入口文件的再导出按公共 API 处理，不计未用导出）。本包按「保留 + 登记」处理：`interface.md` 照列、B30 照钉，是否删除留给替换阶段决定（见 `known-differences.md`）。
- **dist 布局**：`tsc` 把 `src/**/*.ts` 逐个 emit 成 `dist/**/*.js`，本包契约测试的 dist 入口（`KNORVIA_DW02_ENTRY=dist`）与 `interface.md` 的深层模块路径都按这个布局寻址。重写若引入构建期生成文件或目录改名，`tests/entry.mjs` 的 `importDeep()` 会先失败。
