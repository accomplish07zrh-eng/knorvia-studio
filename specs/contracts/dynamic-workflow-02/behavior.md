# dynamic-workflow-02 行为规格（behavior.md）

版本 v1 · 2026-10-19 · 旧门提交见 `gate-old.json` 的 `commit`。

本文描述 `apps/cli/packages/dynamic-workflow/src` 下 `.`、`engine`、`facade`、`lowering`、`schema` 范围内继承文件的可观察行为，是重写依据。编号 B1–B30，发布后不重用。每条九项：输入、输出、错误语义、时序与并发、幂等、资源释放、平台差异、状态所有者、日志级别；测试未覆盖的方面写“合同不约束”。条目→测试对照见 `README.md` 末尾。状态所有者按职责描述，不约束重写后的内部命名。

### B1 实例身份 = 站点 × 每站点序号

- 输入：宿主六个入口（`ask` / `createActor` / `worldRead` / `report` / `publishArtifact` / `declareArtifact`）首参给出的站点 id 文本，加上引擎构造时注入的 runId、caps、askSpecs、driver。站点 id 文本由降层产物给出，引擎既不生成也不校验其唯一性。
- 输出：`(siteId, ordinal)` 结构化实例身份，ordinal 从 1 起、按 siteId 各自递增，串形为 `siteId@ordinal`；六个入口都经引擎内唯一的分配点，序号在宿主调用的同一个同步步骤内铸造。用例钉住：同一站点第二次调用是 `@2` 而不同站点各自从 1 起（`engine-ask.test.mjs`「同一站点的第二次调用是 @2，不同站点各自从 1 起」）、六个入口共用同一个计数器但站点 id 互不消耗（「createActor / world / report / artifact 共用同一个计数器，但站点 id 互不消耗」）、阶段名与站点 id 分属两张表（「阶段名不消耗站点序号，也不被站点序号消耗」与 `engine-observation.test.mjs`「阶段名与站点 id 各数各的：同名互不消耗对方的序号」）。同一站点文本被跨 kind 第二次占用时序号继续往上加，合同不约束（无用例直接钉住）。
- 错误语义：本条不产错误。B3 的两条准入硬错误在判定 return 之前不消耗序号、不落节点行（用例只钉住那次调用没有产生节点行；不消耗序号这点合同不约束）；resume 重放里哈希不符的失败调用已经消耗了一个序号、只是该 run 随即终结因而外部不可观测，合同不约束。
- 时序与并发：同一站点第 n 次与第 n+1 次调用之间没有身份复用，已结算实例的串不会被后续调用再次认领。两张计数表都按单个引擎实例划分、不跨实例延续；resume 的新世从 1 重新铸造，靠命中既有行的位置接续（细节归 B13）。
- 幂等：非幂等接口——每次调用都消耗一个新序号；同一 `(siteId, ordinal)` 只有在 resume 重放时才复用。
- 资源释放：无（两张计数表随引擎实例而生、随其被回收）。
- 平台差异：无（纯整数计数与字符串键，不触路径、环境变量或编码边界）。
- 状态所有者：引擎实例持有的每站点序号表（按 siteId 计数）与另一张独立的阶段计数表；driver 与调用方都不持有份数。
- 日志级别：无——本包不写任何日志，实例身份的可观察面就是事件与行里的那个实例串。

### B2 actor 身份、persona 规范化与重名

- 输入：`createActor(siteId, name?, persona?)`，`persona` 可为字符串或 `{name?, system?}`。
- 输出：一个不透明句柄串（即该实例的实例串），同时落一条 `dwf_actor` 行与一条 `actor-created` 事件。persona 规范化：字符串实参 ⇒ 只带 `system` 键的对象；对象实参 ⇒ 原样浅拷贝，键与键序按调用方给的顺序；`persona.name` 缺席且 `name` 实参在场 ⇒ 把 `name` 追加进 `persona.name`；`persona.name` 在场则压过 `name` 实参、不被覆盖（用例「字符串 persona 即 system prompt；名字缺席时由 name 实参补上」同时钉住这四点）。有效名即规范化后的 `persona.name`；事件与行上的 `name` 字段是原始实参而非有效名，合同不约束（无用例断言该字段）。
- 错误语义：有效名非空即在 run 内唯一；重名 ⇒ 同步抛出 `WorkflowError`，码为 `DuplicateActorName`，同时 run 级失败（`status()` 变 `errored`、最后一条事件是 `run-settled{status:"errored", error}`、run 行写 `failure`），因为没有可拒绝的 promise 所以只能抛。用例「同一个 run 内两次非空有效名 ⇒ DuplicateActorName 让整个 run 失败并同步抛出」钉住抛出形态、`errored` 状态、`run-settled` 载荷，以及 message 里点出的前后两个实例串（该文案另被 golden 逐字录进回放，见 `known-differences.md` K10）。败者不产生 `actor-created` 事件、不落 actor 行。名缺席或空串 ⇒ 从不查重、任意多个合法（用例「匿名 actor（名缺席或空串）不查重，任意多个都合法」）；纯空白串是非空有效名、两次即 `DuplicateActorName`，合同不约束（该用例的第三种写法正是纯空白串，但它断言的是合法而非撞名）。run 结算后再次 `createActor` 抛出的是该 run 的原始错误而非 `Cancelled`，合同不约束。
- 时序与并发：`createActor` 全同步——写序是 actor 行写入 → `actor-created` 事件 → 返回（用例钉住的是两次 `actor-created` 的载荷形状，写序本身由源码顺序支撑）。序号铸造发生在查重之前，但重名即刻让 run 失败，该消耗外部不可观测。匿名 actor 因此没有 amend-resume 的导入缓存资格（见 B14）。
- 幂等：查重表是引擎实例的纯内存表、不落 journal，因此逐字节相同的脚本在全新引擎实例里重放同一串 `createActor` 不会与自己撞名（用例「resume 逐字节重放同一串 createActor 不会把自己当成重名」钉住）。落库的表反而会在 resume 时自撞，这是它必须留在内存的理由。
- 资源释放：无。actor 行的 `sessionId` 值由 driver 产出、`resolvedModel` 值由宿主侧写，引擎从不产出二者；两笔 `putActor` 写入都由引擎做，每次写入前从既有行读回并原样带过。
- 平台差异：无（名字是纯字符串：不做大小写折叠、不做 locale 归一、也不 trim，前导空格的名与不带空格的名是两个名字）。
- 状态所有者：引擎实例持有的有效名认领表（有效名 → 实例串）；调度器里的 actor 注册表与 actor 运行态；`dwf_actor` 上两列的值分归 driver 与宿主、写入归引擎。
- 日志级别：无——可见面是那条 `actor-created` 事件与那一行。

### B3 ask 准入的两条硬错误

- 输入：`ask(siteId, actorId, instructions)`；三道闸按固定顺序检查：run 是否已结算 → `actorId` 是否在 actor 注册表里 → 构造时注入的 `askSpecs` 是否含该 `siteId`。
- 输出：合格才进入准入（B1/B6/B7），返回脚本可 await 的 promise；不合格时不产生节点行、不发 `node-queued`，也没有任何执行类 driver 效应（用例钉住一次派发都没有发生；`driver.emit` 与恰一次 `driver.dispose` 仍会走，这点合同不约束）。
- 错误语义：两条都是 run 级且 promise 同时拒绝——`UnknownActor`（句柄不存在）与 `MissingAskSpec`（站点表缺该 ask 站点），都先 `failRun` 再返回 rejected promise：`status()` 立刻 `errored`，run 行写 `failure{code,message}`，事件轨以 `run-settled{status:"errored", error}` 收口。用例分别钉住两码：「未知 actor 句柄 ⇒ UnknownActor，run 级失败且 promise 拒绝」「站点表缺这个 ask 站点 ⇒ MissingAskSpec，不降级成 untyped」。`MissingAskSpec` 刻意不降级成 untyped：缺席只可能是两份编译产物被拼在一起，降级会把 typed 站点变成结果永远合法的站点。两者同时成立时 `UnknownActor` 优先、结算后再 `ask` 回吐首个 run 错误、正常 `complete` 之后拒绝为 `Cancelled`（message 文本 `Run already settled.`），三点合同均不约束。
- 时序与并发：判定与拒绝都在 `ask()` 的同步回合内完成，没有微任务窗口。run 级失败顺带中止在飞节点：它们的 promise 以同一个 run 错误拒绝，不补 `node-settled{outcome:"cancelled"}`、`dwf_node` 行留在 `running`、已派发的节点收到一次 `driver.cancelAsk`（中止细节归 B18/B19；该形状合同不约束）。
- 幂等：first-wins——同一次判定只第一次生效，后续调用一律回吐首个 run 错误，第二次 `failRun` 无副作用。
- 资源释放：引擎不自己释放什么；run 结算路径统一调一次 `driver.dispose`（B19）。
- 平台差异：无。
- 状态所有者：actor 句柄注册表归调度器；`askSpecs` 站点表由调用方在构造时注入、引擎只读且从不补全；run 结算位与 run 失败错误归引擎实例。
- 日志级别：无——错误一律以结构化 `code` 呈现，流程判断不匹配错误文本。

### B4 typed ask 的 submit 裁决（repair 预算）

- 输入：driver 回报 `askSubmitAttempted(instance, payload)`，payload 是模型提交的结构化值或字符串；校验器 `validate(schema, value)` 返回违规数组、由调用方注入；`schema` 是站点表里透传的结构，引擎不解读，只交给注入的校验器与 driver 的 `startAsk` 载荷。
- 输出：三态裁决经 `respondToSubmit` 下发（`accept` / `reject{violations}` / `nudge`，nudge 见 B5），下发的是一条只带裁决种类的 accept 记录。合法即 accept：用例「首次合法 ⇒ accept：respondToSubmit 先于 node-settled，结果原样兑现」钉住下发给 driver 的恰是一条 accept 裁决、事件轨上 node-queued → node-dispatched → node-settled、以及 promise 兑现值与送入值深相等。校验与解码次序：先按原样校验，原样通过即不解析、原值兑现；原样不过且 payload 是字符串则 JSON 解码后再校验一次，解码通过 ⇒ 兑现解码后的结构化值（用例「payload 是 JSON 字符串时解码后再校验：解码合法即 accept 结构化结果」）；解码抛 ⇒ 回报解码前的违规，解码后仍不过 ⇒ 回报解码后的违规，两点合同不约束。非字符串且不过 ⇒ 直接用原始违规走 repair。
- 错误语义：常量 `REPAIR_ATTEMPTS` 的值为 3（该断言在 `engine-ask.test.mjs` 的 describe「B4 typed ask 的 submit 裁决」内，也在 `pure.test.mjs`「引擎侧的散常数各有其名」里），计数逐节点实例。第 1..3 次违规 ⇒ `reject` 加一条 `node-repairing{instance, attempt, violations}`，节点不结算、行仍 `running`、不重新 `startAsk`（用例「违规在预算内 ⇒ reject + node-repairing(attempt 递增)，节点不结算」钉住三条载荷、三条 reject 裁决与第 4 次的 `cancelAsk` + `ValidationFailed{violations}`，run 仍 `running`）。第 4 次越线 ⇒ 预算耗尽：不再发 `respondToSubmit`，节点以 `ValidationFailed` 结算 failed，行内错误与 `node-settled.error` 都带最后一次 violations，脚本 await 到同码可 catch 拒绝。attempt 只按违规次数递增，合法提交既不消耗也不返还预算，合同不约束。
- 时序与并发：裁决全同步（driver 回报即判即发）；结算后从在飞表移除、归还槽位并重新放行队列（B6）。判定通道只看该实例是否在飞且未结算：untyped 站点上的 submit 尝试什么都不做（用例「对 untyped 站点的 submit 尝试不做任何事」）、幽灵实例与已结算实例的迟到回报是惰性 no-op（用例「对不存在的实例回报 submit/turn 是惰性的（不结算、不发事件）」）。已准入未派发的节点照样接受裁决并走满预算，合同不约束。
- 幂等：每次违规消耗一格预算，因此重复回报同一非法 payload 不幂等（第三次之后即终局）；终局之后的重复回报是幂等 no-op（用例钉住行不变、零新事件）。
- 资源释放：终局路径统一调 `cancelAsk` 一次，让 driver 停掉仍在烧 token 的 turn；节点行整行覆盖为 failed。
- 平台差异：无（JSON 解析与字符串语义跨平台一致）。
- 状态所有者：每节点剩余 repair 计数、在飞节点表与节点 settled 位都在引擎调度器里；`validate` 与 schema 由调用方注入；payload 与是否再试一次归 driver／模型。
- 日志级别：无——裁决与预算的可观察面是 `node-repairing` 事件与下发给 driver 的裁决记录。

### B5 untyped 结算与 typed 的 nudge 预算

- 输入：driver 回报 `askTurnEnded(instance, finalText)`（一轮 turn 结束且模型没有提交结果时的末轮文本）；站点表的 `typed` 位决定走哪条通道，该位由调用方注入。
- 输出：`untyped` 站点 ⇒ 直接以 `finalText` 结算 completed，只发一条 `node-settled{outcome:"ok"}`，既无 `respondToSubmit` 也无 `cancelAsk`；行的 `result` 就是那段文本，脚本 await 到的也是它（用例「untyped ask 由 turn 结束结算为末轮文本」）。`typed` 站点 ⇒ 一次 nudge 或终局。
- 错误语义：`typed` 节点结束而未提交时先 nudge 一次——节点仍在飞、行仍 `running`、不 `cancelAsk`、不重新派发。第二次 `askTurnEnded` 仍未提交 ⇒ `cancelAsk`，节点以 `ResultNotSubmitted` 结算 failed，`error.finalText` 带最后一次回报的文本，脚本 await 到同码可 catch 拒绝，run 仍活着。用例「typed ask 结束未提交 ⇒ 先 nudge 一次，再结束才 ResultNotSubmitted 且带 finalText」钉住常量 `NUDGE_ATTEMPTS` 的值 1、nudge 裁决与 `node-nudged` 载荷、终局的 outcome 与码。nudge 之后仍可被一次合法 submit 救回，合同不约束。
- 时序与并发：与 B4 同一次派发——nudge 不重新 `startAsk`，模型在同一次派发上重试。结算之后的迟到 `askTurnEnded` 被忽略（用例「结算之后的迟到 turn 结束被忽略」钉住事件数不变）；未命中在飞节点的回报惰性 no-op。nudge 与 repair 两条预算互不扣减、按尝试次数计且引擎不读时钟（无超时概念），两点合同不约束。
- 幂等：typed 与 untyped 的结算都只此一次；终局之后重复回报无副作用。
- 资源释放：typed 的 missing 终局经 `cancelAsk` 释放该 turn；untyped 的正常结算无需取消动作。两条路径都把节点移出在飞表并归还槽位。
- 平台差异：无（文本只作载荷，引擎不解析 `finalText`）。
- 状态所有者：每节点剩余 nudge 计数与 settled 位在引擎调度器；`typed` 位归调用方注入的站点表；末轮文本归 driver／模型。
- 日志级别：无——可见面是 `node-nudged` 与 `node-settled` 两条事件。

### B6 每 actor FIFO、actorSeq 与并发上限

- 输入：B3 合格后的准入请求；构造时注入的 `caps.maxConcurrency`；driver 的 `createActorSession` 与 `startAsk`。
- 输出：准入即释放——`dwf_node` 的 running 行与 `node-queued` 事件（带 `actorSeq`）都在 `ask()` 的同一同步步骤内产生，与是否派发无关。`actorSeq` 是每 actor 的准入序号、从 0 起，`node-queued` 的先后即 actorSeq 的先后。派发另受两道闸约束：每个 actor 至多一个在跑节点，且已占用槽数还没到上限才放行。派发给 driver 的 `startAsk` 载荷带 instructions、typed、schema 三键，键集合合同不约束。
- 错误语义：driver 建会话失败 ⇒ 该节点以 `DriverError` 结算（用例「driver 建会话失败 ⇒ 节点以 DriverError 结算，run 不受影响」钉住拒绝码、message 含 cause 原文、`status()` 仍 `running` 与行 `failed`）。message 是固定前缀加 cause 的有界描述：cause 为 Error 时取其 message、否则转文本，两端去空白，空白结果换成 `unknown error`，超过 300 个码元就截断并接省略号；该形状由源码支撑，前缀文本本身合同不约束（无用例与 golden 钉住）。此路无 `node-dispatched`、无 `startAsk`、无 `cancelAsk`，actor 行的 `sessionId` 缺席；同一 actor 的下一条 ask 也失败但每个节点拿到各自的 `DriverError` 实例，后半句合同不约束。
- 时序与并发：一次干净 typed ask 的写序是 putNode:running → appendEvent:node-queued → createActorSession → putActor（带上 driver 给的会话 id）→ appendEvent:node-dispatched → startAsk → 回报裁决后 respondToSubmit → putNode(终态) → appendEvent:node-settled（源码顺序；用例分别钉住其中的 actorSeq 顺序、派发时刻与会话铸造次数）。同一 actor 的第二条只落 running 不派发；全局上限只放开 N 个不同 actor，多余的一律等位（用例「同一 actor 的第二条 ask 排在其后：queued 顺序即 actorSeq 顺序」「并发上限只放开 N 个不同 actor：多余的一律等位」）。`maxConcurrency` 为 0、负数或正小数时的行为、以及引擎每次放行判定读的是调用方 caps 对象的当前值（run 行上的 caps 只是建 run 那一笔的快照），合同均不约束。driver 上报的 `concurrencyChanged` 只落一条观察事件、不改变这道闸门（用例只钉住该事件的载荷形状）。
- 幂等：会话每 actor 至多铸一次，同一 actor 的第二次 ask 复用（用例「会话只在首次 live 派发时铸一次，同一 actor 的第二次 ask 复用」钉住铸造次数；失败路径同样复用那份被缓存的 rejected promise，合同不约束）；槽位只在结算的节点正是该 actor 的在跑节点时归还，重复回报不二次扣减。
- 资源释放：结算把节点移出在飞表并重新放行所有已注册 actor 的队列；run 结算时的在飞中止归 B18。
- 平台差异：无（调度只数整数与队列长度，不读时钟、不起定时器）。
- 状态所有者：每 actor 的下一个 actorSeq 计数、待派发 FIFO、在跑位与缓存的会话 promise 都在引擎调度器的 actor 态里，全局占用槽计数亦然；`caps.maxConcurrency` 由调用方注入（对象仍属调用方），driver 会话本身归 driver。
- 日志级别：无——等待与派发以 `node-queued` / `node-dispatched` 事件与行状态呈现。

### B7 ask 的 journal 行与事件序列

- 输入：准入时刻的指令文本、actor 身份、站点表；driver 的回报（B4／B5／B10）；journal 存储端口。
- 输出：`dwf_node` 行两世写。running 行带 runId、siteId、ordinal、kind（恒 `ask`）、actorSiteId、actorOrdinal、actorSeq、inputHash、status 九个字段；终态行是同一 `(siteId, ordinal)` 键上的整行覆盖写，身份字段逐字保留，追加 `result`（成功）或 `error`（失败），`stats` 只在该节点回报过用量才在场（用例「running 行携带身份与 inputHash，completed 行整条替换后仍保留身份」钉住九字段逐字段相等、终态 status、result 为送入值、终态的 actorSeq 与 inputHash 等于 running 行的值）。ask 行不带指令文本：端口面的 `NodeRecord` 只有 `inputHash`（`input` 只给 world 节点），完整指令列 `dwf_node.input_json` 属宿主 SQLite 侧、不在本包行为内。`inputHash` 覆盖原样指令文本（不去空白），值为规范化 JSON 上的 32 位 FNV-1a 十六进制串（见 B21）。事件序列上一次干净 typed ask 到 run 结束恰为 run-started → actor-created → node-queued → node-dispatched → node-settled → run-settled，repair 在 queued 与 settled 之间插入 `node-repairing`、nudge 插入 `node-nudged`，未派发就结算则没有 `node-dispatched`。`node-queued` 带 `instructionsHead`：取准入时刻的指令、两端去空白、截到常量 `INSTRUCTIONS_HEAD_MAX_CHARS` 的值 240、不加省略号，去空白后为空时整键缺席（用例「node-queued 带 instructionsHead（准入时刻、去空白、≤240 字符），空指令整键缺席」）。实例出生在任一 `phase()` 标记之后时该类事件末尾追加 `phaseName`（用例「出生阶段随事件向前携带：actor-created 与 node-queued 带 phaseName，标记之前出生则缺席」）。
- 错误语义：resume 重放命中同一 `(siteId, ordinal)` 而本次指令哈希与行上记录不一致 ⇒ `InputHashMismatch`，run 级大声失败并以该错误拒绝本次 `ask`，错误带结构化 `mismatch{expected, got}`（用例「指令文本变了就是 InputHashMismatch：run 大声失败并结构化报出两侧哈希」钉住拒绝码与两侧值）。既有行零触碰、本次不发 `node-queued` / `node-dispatched`，合同不约束（由源码顺序支撑）。
- 时序与并发：每个事件在同一个同步步骤里先 `appendEvent` 落 journal、再交给 `driver.emit`，两侧拿到同一个事件对象；用例「journal 事件轨与 driver.emit 实时轨拿到同一序列」钉住两条轨序列深相等与六个事件 `type`，引用同一性合同不约束（内存端口落库时深拷贝）。写入次序恒为行先于事件；`sequence` 由存储分配、从 0 起连续递增。引擎无时钟：顺序的唯一来源是 journal 的 sequence，`timeCreated` 由存储层注入、不参与任何引擎判定。`types.ts` 把 unique(runId, actorSiteId, actorOrdinal, actorSeq) 声明成端口契约，本包的内存实现只按 `(siteId, ordinal)` 存行、不校验该约束，SQLite 侧的强制在包外。
- 幂等：行是 upsert 语义，同实例第二次写只覆盖不新增；一次 ask 全程节点行数恒为 1、`node-settled` 恰一条（用例钉住）。迟到的 `askSubmitAttempted` / `askTurnEnded` / `askFailed` 一律零新事件；迟到的 `askStats` 不在这条通道上，它回填既有行并可补发 `usage-updated`，归 B8。
- 资源释放：无额外释放动作；节点的清理就是在结算时移出在飞表（B6）。
- 平台差异：文本截断按 UTF-16 码元而非码点，对 astral 字符（emoji）可能在代理对中间切开；trim 用 JavaScript 的 Unicode 白空格定义，与宿主 locale 无关。代理对是否被切开合同不约束。
- 状态所有者：`dwf_node` 行与事件序列归 journal 存储（按 runId 分桶）；行内容的构造归引擎侧的 ask 行投影；`sequence` 与 `timeCreated` 归存储；引擎只搬运不改写。
- 日志级别：无——行与事件轨就是它的日志面。

### B8 ask 的进度与用量观察

- 输入：两个 Boundary B 回报方法，都同步、无返回值。`askProgress(instance, progress)` 的 progress 是 `{turn, toolCalls, lastTool?}`，`lastTool` 是 `{name, target?}`；`askStats(instance, stats)` 的 stats 是 `{tokens, toolCalls, turns, worldToolCalls?}`。用量起点另由 `EngineConfig.inheritedTokens` 给出。引擎核心不读时钟、不做 I/O：进度与用量都是调用方在某个时刻注入的数字；事件时刻由存储端口实现盖戳。
- 输出：`askProgress` 恰好一条 `node-progress` 事件，载荷是 `type`、`instance` 加 progress 的原样展开，经唯一漏斗依次交给 `appendEvent` 与 `driver.emit`；不写节点行、不改调度、不进 `inputHash`、replay 不比对它（用例「askProgress 纯透传：逐条落事件、载荷原样、不改调度也不写行」）。`lastTool.name` / `lastTool.target` 的 64／120 只是常量值，截断归宿主 driver，引擎不切（用例「askProgress 不加工载荷：上限归 driver 所有，引擎切了就是替 driver 兜底」以 200／400 字符载荷钉住原样落轨）。`askStats` 三笔且顺序固定（源码顺序）：①实例在飞则暂存为该节点的 `lastStats`、结算时由投影写进节点行的 `stats`，实例不在飞但该行存在则读改写整行补 `stats`，两者都不成立则无痕；②内部累计量加上本次 tokens 后立即 `updateRunUsage` 写 `dwf_run.spent_tokens`；③紧跟一条 `usage-updated`，列值与事件载荷出自同一同步步骤、永远相等（用例「askStats：先写 spent_tokens 列、再发同值事件，两条写入路径永远一致」）。构造期：全新 run 把归一后的 `inheritedTokens` 直接写进 `createRun` 的 spentTokens，resume 世忽略 `inheritedTokens`、从行读回；只要起账大于 0 就紧跟 `run-started` 补发一条 `usage-updated`，零不发（用例「继承的用量在建 run 那一世就起账并补发一条 usage-updated；脏值归一」与标题以「inheritedTokens 归一」打头的四条循环用例）。归一只作用于 `inheritedTokens`：非有限值与负数按缺席记 0，小数下取整（12.9 → 12、负数／NaN／Infinity → 0 由用例断言；-0.4、2.999、-Infinity 的取值合同不约束）。
- 错误语义：两个方法都不抛错、不拒绝、没有失败通道——进度与用量是观察面而非控制面，任何载荷都不让 run 失败。唯一的门是 run 结算：结算后 `askProgress` 整体丢弃（零事件、零行），`askStats` 账照入、节点行照回填、列照写，只是不再发事件，`run-settled` 恒在该世事件流的最后一条（用例「结算后到达的迟到 stats：账照入、节点行回填，但不再发事件」「结算后到达的迟到 progress：只丢事件，不给已完结的 run 长尾巴」）。实例身份一律不问：从未铸造过的 `(siteId, ordinal)` 照样落事件、照样入账（用例「askProgress 不问实例是否还活着：引擎唯一的门是 run 结算」）。`stats.tokens` 不做归一也不校验，非数字或负数会原样进列，而协议侧要求该列为非负整数——这条冲突当前无用例钉住，合同不约束。
- 时序与并发：全部同步；`askProgress` 与 `askStats` 之间的先后由 driver 决定，引擎只按到达顺序落轨。`updateRunUsage` 恒早于同值的那条 `usage-updated`，两者之间不插别的写入（用例钉住写入序列形状）。用量观察与调度正交：把 stats 落在飞的 ask 上不会让它结算，run 状态仍 `running`（用例断言值）。同一次 turn 内 progress 先于 stats 是类型面写给 driver 的读面契约，引擎不执行它。
- 幂等：`askProgress` 无去重（两次调用两条事件）。`askStats` 是累加语义、非幂等：同一份 stats 报两次就记两次，重复上报归 driver；节点行的 `stats` 是最后一次整体覆盖而非合并。
- 资源释放：不涉及；两条观察不关闭、不注销任何东西，写入面只到 `dwf_run` 与 `dwf_node`。
- 平台差异：无（无路径、无编码、无进程；数字与键集合跨平台一致）。
- 状态所有者：累计量归引擎实例私有字段、一世一份（新建取归一后的 `inheritedTokens`，resume 从 `dwf_run` 行读回）；`dwf_run.spent_tokens` 列是它唯一的持久所有者；`lastStats` 归调度器持有的在飞节点对象；节点行的 `stats` 归 journal 存储；载荷形状与三个上限常量归本包类型面；64／120 的截断与上报时机归 driver，240 的截断归引擎（B7）。
- 日志级别：无——这两条通道本身就是宿主可读的观察面。

### B9 展示通道与 run 级观察

- 输入：两组面。Boundary A（脚本够得着）：`log(message)`、`enterPhase(name)`。Boundary B（driver 报上来）：`askWaiting(instance, info)`、`askExecuting(instance)`、`askMutating(instance)`、`concurrencyChanged(change)`、`runStalled(info)`、`stopRun(error)`。全部同步、无返回值。注入的数字分两族，不可混称时间量：时间量是 `AskWaitInfo` 的 delayMs／retryAfterMs、`ConcurrencyChange` 的 cooldownMs、`RunStallInfo` 的 sinceMs；并发数字是 `ConcurrencyChange` 的 previous／next／lastGood／lastBad 与 `RunStallInfo` 的 cap（后者是 provider 桶的 cap，不是时长）。引擎核心不读时钟，什么时候算停滞、退避多久、cap 该是多少都不由引擎判定；cap 的判据与常量归本包 `ConcurrencyController`（B24），宿主侧治理器只喂信号与 `now`。
- 输出：`log` 一条 `log{message}` 事件，空串照发，无站点、不消耗序号、不写节点行（用例「log 只发事件：无 site、无 dwf_node 行」）。`enterPhase` 先 trim 名字，修剪后为空则整体忽略（不计数、不改当前阶段、不发事件），否则在自己那张按名字的表里递增 ordinal、把当前阶段置为它、发一条 `phase-entered{name, ordinal}`，每次求值都发、同名再入即 +1（用例「enterPhase：trim 名字、空名整体忽略、每次求值都发、ordinal 按名字计数」）；此后铸造的每个实例记下出生阶段，事件漏斗只给三条出生事件补 `phaseName`（`actor-created`、`node-queued`、命中缓存时代替 queued 的 `node-settled{cached:true}`），第一个标记之前出生的实例整键缺席、`node-dispatched` 与普通 `node-settled` 永不带（用例「出生阶段随事件向前携带：actor-created 与 node-queued 带 phaseName，标记之前出生则缺席」）。`askWaiting` / `askExecuting` 的门是 run 未结算、且该实例在飞且未 settled，通过则发 `node-waiting{instance, ...info}` 或 `node-executing{instance}`，不写节点行。`askMutating` 同一道 live 门，通过后关导入缓存——门一次置真、永不重开，且只在本次确有 importedCache（修订 run）时发一条 `import-cache-closed{instance, cause:"mutating-tool", actorName?}`，actorName 取该节点 actor 的有效名、缺席或空串则整键不发；非修订 run 只置标志、零发声。`concurrencyChanged` / `runStalled` 的门只有 run 结算，载荷对象原样展开，引擎不解释也不裁剪。`stopRun` 把 error 经 enrich 之后走 `stop("provider", …)`，落进 B19 的 stopped 路径（终态 `stopped` + stopReason provider，不是 `errored`）：enrich 只在四件事同时成立时重铸错误对象（带 providerStop 明细、明细带 subagent 实例串、明细尚未带 phase、出生阶段表查得到该实例），补的是该实例的出生阶段而非停止时的当前阶段（用例钉住），不碰时原样转发同一对象。
- 错误语义：这一族自身不抛错、不拒绝、不使 run 失败；`askMutating` 触发的关门是状态变更而非错误，`stopRun` 是让 run 停下来而不是让 run 失败。`reason` 的五值词汇（rate_limited / provider_overloaded / offpeak_queued / recovered / idle_reset）与停滞 reason 的开放字符串都由 driver 侧给，合同不校验其取值。ghost 实例调用 `askMutating` 是纯 no-op、不会误关门，该点合同不约束（用例只钉住 ghost 的 submit／turn 惰性）。
- 时序与并发：全部同步、无外部往返。出生阶段的写入只发生在铸造点、读取只发生在事件漏斗与 `stopRun` 的 enrich，因此同一 tick 里先 `enterPhase` 再 `createActor` / `ask` 一定带得上这个阶段名，而 `node-queued` 可能被 hold 规则推迟到下一个标记之后才发。`log` / `enterPhase` / `concurrencyChanged` / `runStalled` 都不碰调度器与 journal 行，落轨顺序即到达顺序，也不消耗站点序号。一次 `askMutating` 的门翻转与它那条唯一事件在同一同步步骤里完成；`world.run` 的关门先于派发（用例）。这些观察都不改变在飞／准入状态。
- 幂等：`log` / `enterPhase` / `concurrencyChanged` / `runStalled` / `askWaiting` / `askExecuting` 无去重，重复调用即重复事件，`enterPhase` 还额外推进 ordinal 与当前阶段；阶段计数表一世一份，resume 的第二世同名阶段从 1 重数，前缀重复由投影侧按单调归约消化，该归约在本包之外。关门幂等：`closeImportCache` 见门已关直接返回，一个 run 至多一条 `import-cache-closed`（用例「askMutating：只在 live 节点上关门，一个 run 最多一条 import-cache-closed」）。`stopRun` 经 first-wins 幂等；run 已结算后的 `stopRun` 被整体忽略，该点合同不约束。
- 资源释放：无。这些通道不释放任何东西；`driver.dispose` 只在 B19 的结算收尾里跑一次。
- 平台差异：无（纯内存表与事件载荷，无路径、终端、进程依赖；测试侧用 setImmediate 排空派发，Windows 与 POSIX 同结果）。
- 状态所有者：当前阶段与按名字的进入计数是引擎实例私有、一世一份；实例到出生阶段那张表归引擎，唯一写入点是序号铸造、唯一读取点是事件漏斗与 `stopRun` 的 enrich；导入缓存的门归引擎，跨世只从 `import-cache-closed` 事件恢复；live 判定与 actor 有效名归调度器的在飞节点表；cap 的判据与常量归本包 `ConcurrencyController`，喂信号与 `now` 归宿主治理器（本包之外）；何时算 waiting、executing、mutating、停滞的时刻与 `ProviderStop` 明细除 phase 之外归 driver。
- 日志级别：无——本包不写日志，这些事件就是给宿主与 GUI 的展示面。

### B10 driver 侧不可恢复错误结算该 ask

- 输入：driver 回报 `askFailed(instance, error)`，error 是 driver 构造的节点级 `WorkflowError`。
- 输出：命中在飞且未结算的节点 ⇒ 节点以该错误结算 failed：整行覆盖写带 `error`（`code`、`message` 加在场的结构化明细，`cause` 不落库），发一条 `node-settled{outcome:"failed", error}`，脚本 await 到同一个错误对象的拒绝，因此脚本侧 try/catch 能看到 driver 给的原始码；`status()` 仍 `running`——run 活着，只有这一个节点结清。
- 错误语义：引擎不校验 `error.code`，原样搬运；不在合同码表里的自造码也照样落行、进事件、成为脚本侧的拒绝理由，合同不约束（无用例钉住码表外取值）。实例不在飞（站点／序号对不上任何在飞节点、节点已结算、run 已结算）⇒ 完全惰性：零事件、零行写入，合同不约束（用例只钉住同一实例重复回报不产生第二条事件）。run 级不可恢复错误不属于本条：driver 的确定性模型侧错误走 `stopRun`，让整个 run 停在 `stopped(provider)`，见 B19。
- 时序与并发：不调用 `driver.cancelAsk`——报失败的正是 driver 自己，无需再让它取消；该点合同不约束。未派发的节点也能被 `askFailed` 结清，此时事件轨只有 node-queued 与 node-settled。结算照常归还槽位并放行同 actor 的下一条。
- 幂等：settled 位守住，同一实例重复回报是幂等 no-op，每个实例最多一条 `node-settled`（用例「askFailed ⇒ 节点 failed + 可 catch 的拒绝，run 仍活着」钉住行 status、行内错误与拒绝同源、run 仍 `running` 与重复回报不产生第二条事件）。
- 资源释放：节点从在飞表移除；driver 侧的会话与 turn 由 driver 自行收尾，引擎不通知。
- 平台差异：无。
- 状态所有者：在飞节点表与节点 settled 位归引擎调度器；错误对象与其码归 driver。
- 日志级别：无——可见面是那条带 error 的 `node-settled` 事件与失败行。

### B11 世界读取：准入、结算与 replay

- 输入：`worldRead(siteId, op, args)`，`siteId` 由降层生成，`op` 为操作名（`WorldReadOp`），`args` 为脚本调用点的位置实参表；driver 的 `executeWorldRead(op, args)`；journal 存储；可选的修订 run 导入缓存 `importedCache`。
- 输出：返回脚本可 await 的 promise。live 成功兑现 driver 返回值；replay 命中 completed 兑现行内 `result`；导入缓存命中兑现导入条目的 `result`。journal 行：live 在准入时落 running 行，结算时整行覆盖为 completed/failed；导入缓存命中在未落行时直接写入 completed 行。节点行字段：`siteId`、`ordinal`、`kind`（op 为 `"run"` 时恒为 `"world-run"`，其余恒为 `"world-read"`）、`status`、`inputHash`、`input`（`{op, args}`，有界化见 B12）、成功带 `result`、失败带 `error`（仅 `code` 与 `message` 键），不带 actor 字段与 `artifactId`。事件轨：live 依次发 `node-queued`（`world.run` 的 queued 载荷携带 `kind: "world-run"`）、`node-dispatched`、`node-settled`；replay 与导入缓存命中不发 queued 与 dispatched，只发一条 `node-settled{outcome, cached: true, instance, error?}`。修订 run 中 `world.run` 派发前关导入门，发 `import-cache-closed{cause: "world-run", instance}`。
- 错误语义：准入阶段实参若带环抛 `RangeError`，带 BigInt 等不可规范化 JSON 值抛 `TypeError`（用例「带环 / 不可序列化的实参在准入即抛（世界读没有 report 那样的序列化探针）」钉住；世界读取无序列化安全探针，准入即抛、不落行、不发事件）。run 结算后调用直接以 run 的结算错误（如 `Cancelled`）拒绝，不调用 driver、不落行（用例「结算之后的世界读取直接以 run 的错误拒绝，不落任何行」）。driver 抛 `WorkflowError`（如 `WorldReadCapExceeded`）时原样保留抛出，不折进 `DriverError`（用例「driver 抛 WorkflowError 时原样保留，不折进 DriverError」）；driver 抛普通错误时包装为 `DriverError`，message 格式包含 `World read failed: <op>`，cause 丢弃不入库也不外露（可序列化形态仅留 `code` 与 `message` 键），节点以 `failed` 结算，脚本可 catch 拒绝，run 仍为 `running`（用例「driver 拒绝的普通错误包成 DriverError：节点失败、可 catch，run 仍活着」）。replay 命中 failed 行时按行内记录重建错误对象拒绝，发 `node-settled{outcome: "failed", cached: true}`（用例「replay 命中 failed：cached 的失败结算，错误从行里重建」）。
- 时序与并发：世界读取不受 actor FIFO 与 `caps.maxConcurrency` 约束，可与在跑的 ask 并发执行（用例「同一 op 第二次调用是 @2；世界读取不受 actor FIFO 与并发上限约束」钉住）。同一站点第 n 次调用序号为 `@n`。replay 命中 running（崩溃残余）时重新 live 执行并覆盖为终态（用例「replay 命中 running（崩在执行中）：重新 live 执行并覆盖成 completed」）。`world.run` 在派发前关门，非修订 run 不发关门事件（用例「world.run 单列一种 kind（效应不是读），并在派发前关掉导入缓存」与「非修订 run 的 world.run 不发关门事件（没有表可关）」）；关门后同 run 后续调用不再消费导入表（用例「关门之后不再问导入表：同一哈希的下一条导入条目不再被消费」）。
- 幂等：live 执行非幂等（每次调用分配新序号并产生 driver 效应）。replay 命中终态行时幂等兑现或拒绝，零 driver 往返；导入缓存命中按哈希匹配后消费该条记录，队列耗尽或关门后转 live（用例「导入缓存命中（journal 无行）：写一行 completed + cached 事件，绝不调 driver」）。
- 资源释放：无。引擎不持有外部资源句柄，driver 侧执行与清理归 driver 自行负责。
- 平台差异：合同不约束。
- 状态所有者：每站点序号分配、出生阶段与导入缓存门状态归引擎实例；节点行与事件序列归 journal 存储；操作执行、元数与实参校验归宿主 driver；导入缓存映射归调用方注入的导入表。
- 日志级别：无——可见面为 journal 节点行与事件序列。

### B12 世界读取的有界输入

- 输入：`worldRead(siteId, op, args)` 在准入时待审计的载荷——`op` 操作名与位置实参表 `args`；常量 `WORLD_READ_INPUT_MAX_BYTES`（数值为 4096，属 B22）作为判定序列化字节数是否超限的门槛。实参的合法元数与参数形状归 driver 校验，引擎不校验。
- 输出：journal 节点行上的 `input` 字段（`WorldReadInput`）。未超限 ⇒ 原类型原样落库（保持数字、嵌套对象等结构），`truncated` 键整键缺席（用例「序列化后不超限：原类型原样落库，truncated 键缺席」钉住）。超限 ⇒ 置 `truncated: true`，`args` 替换为至多保留 8 项的字符串预览数组：超长实参切在第 400 个字符并追加一个省略号 `…`（总长 401 字符且以 `…` 结尾），非字符串实参先转为紧凑 JSON 文本后再切至 400 字符加省略号（前缀计入 400 字符内），未超长实参保留原字符串（用例「超限：逐项字符串预览、至多 8 个实参、置 truncated」与「预览对非字符串实参取 JSON 文本（同样切到 400 字符 + 省略号）」钉住）。
- 错误语义：输入超限并非错误——不抛错、不拒绝、不产生错误码，仅影响节点行内的 `input` 审计投影。读取结果超上限的 `WorldReadCapExceeded` 属于节点级可 catch 拒绝（B11），与输入的有界化正交。
- 时序与并发：`input` 与 `inputHash` 在同一准入写操作（`putNode: running`）中落库，后续结算更新整行覆盖时原样带过。有界化计算为全同步纯逻辑，不引入额外事件或 driver 往返，不改变节点派发与结算的时序。
- 幂等：有界化是 `(op, args)` 的确定性纯投影；超限状态唯一由序列化后是否超过阈值决定。身份与一致性判定由覆盖完整未经截断载荷的 `inputHash` 保证（`row.inputHash === inputHash({ op, args })`，args 为原始实参表），审计截断不影响 replay 匹配与哈希一致性判定。
- 资源释放：无。有界副本仅用于写入 journal 节点行审计，driver 收到的是原始完整的实参表，引擎不持有额外缓冲区或持久资源。
- 平台差异：合同不约束（测试载荷均为 ASCII 串与通用 JSON 结构，截断按字符数与单个 Unicode 省略号处理）。
- 状态所有者：有界输入的结构投影由引擎在准入写行时单方面构造并写入 journal；外部读面与事件序列不含截断视图；driver 收到完整实参表并拥有操作的执行与元数校验职责。
- 日志级别：无——本条不发事件、不写日志，可见面仅为 journal 节点行中的 `input` 与 `truncated`。

### B13 resume：同一 runId 的第二世

- 输入：传入包含既有 run 记录的 journal（相同 `runId`）；引擎构造配置（含 `scriptHash`、`caps`、`askSpecs`、`driver` 等）；脚本在第二世执行的各入口调用；既有 journal 中的 `dwf_run`、`dwf_node`、`dwf_actor` 行与事件轨。
- 输出：不重建 run（不调用 `createRun`），仅调用 `updateRunStatus(runId, "running")` 将 run 状态翻转为 `running` 并清空上一世的结算残影（`stopReason`、`failure`、`supersededBy`、`result` 整体清空，K5）；既有元数据（`args`、`name`、`scriptHash`、`scriptText`、`resumedFrom`）与用量 `spentTokens` 原样保留（用例「不重建 run：只做一次 running 翻转，并把上一世的结算残影清干净」钉住）。事件轨跨世拼接：从新一世的 `run-started` 开始继续追加，`sequence` 单调递增紧接上一世末尾（用例「事件轨跨世拼接：新一世从自己的 run-started 开始」）。重放节点按 `(siteId, ordinal)` 寻址命中：①命中 `completed` 行 ⇒ 兑现行内 `result`，不建 driver 会话、不派发，不发 `node-queued`/`node-dispatched`，只发一条 `node-settled{outcome: "ok", cached: true}`，历史行只读不写（用例「completed 行命中：兑现行里的结果，只发 cached 的 node-settled，一次都不问 driver」）；若此时处于某阶段内，该事件作为出生事件携带 `phaseName`（用例「命中的 cached 结算就是它的出生事件：phaseName 随它携带」）；②命中 `failed` 行 ⇒ 按行内 `error` 重建错误对象拒绝 promise，脚本可 catch，run 仍为 `running`，发 `node-settled{outcome: "failed", cached: true, error}`（用例「failed 行命中：按记录重新拒绝（不是复验），run 不受影响」）；③命中 `running` 行（崩溃残余）⇒ 重新 live 派发，走完整 queued → dispatched → settled 并覆盖写为终态（用例「running 行命中（崩在执行中）：重新 live 走完整一遍并覆盖成终态」）；④未重放到的历史节点行（如本世提前收工）原样保留、零触碰（用例「站点身份跨世稳定：同一脚本重跑到同一 (siteId, ordinal)，没重放的行零触碰」）。
- 错误语义：两道哈希防线均给出致命大声失败。其一为构造期脚本哈希校验：当构造实参给出了 `scriptHash` 且库中 run 行记录了非空 `scriptHash` 时进行比对，若不一致 ⇒ 同步抛出 `WorkflowError`，码为 `ScriptHashMismatch`，携带结构化 `mismatch{expected, got}`；该错误阻止第二世启动，run 行状态保持上一世终态、结算残影不清空、事件轨与节点行零触碰（用例「脚本哈希不一致：同步抛出，这一世根本不开（行、状态、事件零触碰）」）。比对要求两侧在场，任一侧缺席则跳过校验（老行缺席不拒新实参，实参缺席不抹除记录的哈希，用例「比对要求两侧在场：任一侧缺席即不判（老行没有 script_hash）」）。其二为运行时指令哈希校验：重放命中既有 `completed`/`failed` 行时比对指令哈希，若输入改变 ⇒ `InputHashMismatch`，携带 `mismatch{expected, got}`，本次 promise 拒绝且整个 run 立即 `errored` 失败（run 行写 failure，发 `run-settled{status: "errored", error}`），历史节点行不被改写（用例「命中的行与本次指令哈希不符 ⇒ InputHashMismatch：run 大声失败，行零触碰」）。
- 时序与并发：站点序号每世各自从 `@1` 重新铸造。`actorSeq` 从既有行续账：同 actor 下未记录的全新 ask 不得越过已记录的排队前缀；若某 actor 在前一世已有处于 `running` 等状态的记录行，本世若先调用全新 ask 站点，该全新 ask 将被暂扣不发 queued/dispatched，直到脚本重放到位排齐前缀后，才按递增的 `actorSeq` 依次排队与派发（用例「actorSeq 从行里续账：fresh ask 不得越过已记录的排队前缀」钉住）。命中 cached 结算的节点同步进入兑现/拒绝，无外部 I/O 阻塞。
- 幂等：resume 重构具有纯状态等价性；命中 `completed`/`failed` 行幂等复用历史事实，不触发二次副作用；未访问到的历史行只读不动。
- 资源释放：命中的节点未向 driver 申请会话，无须额外释放；第二世最终结算时统一触发一次 `driver.dispose`（B19）。
- 平台差异：合同不约束。
- 状态所有者：持久历史数据（run/node/actor 行与事件轨）归 journal 存储；每站点序号分配表、重放命中比对、`actorSeq` 续账排队水位与出生阶段表归引擎调度器与实例私有；driver 仅在命中 running 行或执行 fresh ask 时介入会话。
- 日志级别：无——可见面为第二世新追加的事件序列与持久行状态。

### B14 amend-resume 的导入缓存

- 输入：修订 run 在构造配置中注入的导入缓存 `importedCache`，含按有效名索引的 `actors` 表（规范化 `persona`、顺序条目表 `entries`、`transcriptSourceSessionId`、承袭的 `resolvedModel`）及按哈希索引的 `world` 队列表；脚本调用的 `createActor`、`ask`、`worldRead`；关门观察信号（`askMutating` 或 live 执行的 `world.run`）；既有 journal 事件轨中的 `import-cache-closed` 事件。
- 输出：导入缓存命中（journal 尚无该行）：①ask 命中 ⇒ 直接写一行 `completed` 的 `dwf_node` 行，完整拷入 `result`、`stats` 与 `messageBoundary`，一次都不调用 driver（不建会话、不派发），仅发一条 `node-settled{outcome: "ok", cached: true}`（用例「命中即落一行真 dwf_node：结果 / 用量 / 转录边界整体拷来，且一次都不问 driver」）；②world 命中 ⇒ 亦直接落 completed 行并发生 `node-settled{outcome: "ok", cached: true}`。分歧后首个 live 会话种子：向 driver 调 `createActorSession(actor, persona, seed)`，`seed` 携带 `{ messageCount, resolvedModel, sourceSessionId }`，其中 `messageCount` 取最后一条真正被消费条目的 `messageBoundary`，若一条未消费则 `seed: undefined`（用例「分歧后首个 live actor 的会话种子 = 最后一条被消费条目的边界 + 承袭的模型 pin」与「一条也没消费 ⇒ 没有种子：全新会话、不带 pin」）。关门事件：在有导入表且尚未关门时，首次 mutating 触发一条 `import-cache-closed{instance, cause, actorName?}`（见 B9/B11）。
- 错误语义：分歧与比对落空不是错误——不抛错、不拒绝、不使 run 失败，仅使后续节点降级为 live 派发。persona 比对：以有效名为键查候选，候选 persona 与当前 persona 经 `canonicalJson` 规范化比对（键序与值为 undefined 的成员无关，多一个有值成员即视为另一身份）；比对不一致 ⇒ 直接放弃整个 actor 候选，后续全部 ask 全新 live 重跑且种子为 undefined（用例「persona 不一致即弃整个候选（改 prompt 的意图本来就是重跑）」与「persona 比对是规范化的：键序与 undefined 成员无关，多一个有值成员就是另一份身份」）。匿名 actor（名缺席或空串）无缓存身份键，永不附着导入缓存，始终全新 live（用例「匿名 actor 永不附着：名字就是缓存的身份键」）。
- 时序与并发：分歧单调性：一旦发生分歧，后续即便哈希对上也不得复活，同 actor 的后续 ask 全部 live（用例「分歧单调：后缀即便哈希对上也不复活」）。关门规则：门一旦关闭永不重开；关门后仅纯条目（`worldToolCalls === 0`）允许继续命中，碰过外部世界的非纯条目（`worldToolCalls > 0`）以及无用量记录的老条目（保守按碰过处理）即使哈希一致也必须转 live（用例「关门后只有纯条目还能命中；碰过外部世界的即便同哈希也转 live」与「没有用量记录的老条目按「碰过」保守处理」）。`world` 队列按出现序出队消费，队列耗尽即转 live（用例「world 队列按出现序消费：第 n 次同一 {op,args} 对第 n 条记录，耗尽即转 live」）。跨世分歧与关门恢复：崩溃后 resume 据 journal 中是否存在 `import-cache-closed` 事件恢复关门状态（用例「关门状态从 import-cache-closed 事件恢复：门已关 ⇒ 非纯条目转 live」与「没有那条事件 ⇒ 门是开的：非纯条目照样导入（关门是唯一事实来源）」）；重推分歧点时依据事件轨识别历史中真实 live 派发的步骤，不将同哈希的 live 步骤误算作已消费，种子边界按真实消费位截断（用例「resume 据行重推分歧点：哈希对得上、但当时是 live 跑的那一步不得算成已消费」）。
- 幂等：关门操作幂等（门关后重复收到信号为 no-op，一个 run 至多一条关门事件）；条目消费单向递进，已消费或已出队的条目不可重复出队。
- 资源释放：命中缓存的节点未分配 driver 资源；分歧后转为 live 的 actor 会话在 run 结算时由 B19 统一调 `driver.dispose`。
- 平台差异：合同不约束。
- 状态所有者：外部导入数据由调用方注入；导入门开关状态、各 actor 候选的消费游标与分歧标志、world 队列游标归引擎实例私有；节点行与 `import-cache-closed` 事件归 journal 存储；转录截断与会话复制归 driver 的 `createActorSession` 执行。
- 日志级别：无——可见面为 `import-cache-closed` 与 `node-settled`（带 `cached: true`）事件及持久节点行。

### B15 report 的发布路径

- 输入：`report(siteId, item, artifactId?)`，同步、无返回值；`siteId` 由降层给出，`item` 为待发布的中间结果，可选 `artifactId` 为关联的预置产物标签；常量 `REPORT_CAPS`（单 run 256 条 `maxItemsPerRun`、单条 32KB 序列化字节 `maxItemSerializedBytes`，属 B22）；预置产物声明表（由 `declareArtifact` 写入，B17）；journal 存储。
- 输出：即发即忘、无返回值、无 driver 往返。live 发布写入一行 `status: "completed"` 的 `dwf_node`，字段为 `siteId`、`ordinal`、`kind: "report"`、`status`、`result: item`、`inputHash: inputHash(item)`，带合法标签时记 `artifactId`，不带 actor 字段、不带 `input`（有界输入为世界读专属）；事件轨同步追加一条 `report{instance, item, artifactId?}` 事件，不产生任何节点生命周期事件（无 `node-queued` / `node-dispatched` / `node-settled`，用例「一次发布：一行 completed、一个 report 事件、没有节点生命周期事件」钉住）。标签合法时行与事件均带 `artifactId`（用例「标签合法：行与事件都带 artifactId（看板 = journal 的投影）」）。replay 命中且哈希一致时静默跳过（零新事件、不重写行、不重复扣减配额）。
- 错误语义：`report` 返回 `void`，无节点级拒绝通道，所有错误均为 **run 级大声失败**（`failRun`，状态变 `errored`，写 run 行 `failure`，发 `run-settled`，K8）：①非 JSON 基本值（`undefined`、函数、`symbol`）⇒ 以 `DriverError` 失败，消息含 `is not a JSON value`，不落行（用例「item 不是 JSON（undefined / 函数 / symbol）⇒ failRun DriverError，不落行」）；②带环对象 ⇒ 经序列化前的环探针拦截，以 `DriverError` 失败，消息含 `cannot be serialized to JSON`，不落行（用例「item 带环 ⇒ failRun DriverError（探针先于 canonicalJson，否则是爆栈而不是一次可读失败）」）；③单条序列化字节数（含 JSON 引号）超过 32768 字节 ⇒ 以 `ReportCapExceeded` 失败，上限论字节而非字符（用例「单条超过 32KB ⇒ ReportCapExceeded 让整个 run 失败（上限论字节，不是字符）」）；④单 run 累计超过 256 条（第 257 条）⇒ 以 `ReportCapExceeded` 失败（用例「第 257 条 ⇒ ReportCapExceeded（条数上限是 run 级的）」）；计数跨 resume 连续累加，历史 report 行照样计入（用例「上限计数跨 resume 连续：journal 里已有的 report 行照样计数」）；⑤标签非法（未声明或指向 file/markdown 等内容产物）⇒ 以 `ArtifactUndeclared` 失败，不落行（用例「标签必须指向已声明的预置产物，否则 ArtifactUndeclared 让 run 失败」与「标签指向内容产物（file/markdown）同样非法：只有预置成员能被认领」）；⑥replay 命中既有行但 `item` 哈希改变 ⇒ 以 `InputHashMismatch` 失败；标签不进哈希，换标签不触发哈希违规（用例「replay 命中但 item 变了 ⇒ InputHashMismatch 让整个 run 失败（防御性比对）」与「标签不进哈希：同一 item 换个标签在 replay 时不算纯度违约」）。
- 时序与并发：同步执行，写序为校验（探针/字节/条数/标签）→ 落 completed 行 → 发 `report` 事件。序号按站点各自计数（同站点第二次调用为 `@2`，不同 report 站点互不消耗，用例「同一站点的第二次调用是 @2（序号是 run 级计数，report 站点之间互不消耗）」）。run 结算后到达的调用被静默丢弃，零事件、零写行（用例「结算之后不再受理：report 与 log 同规」）。
- 幂等：live 发布非幂等（消耗单 run 256 条额度与站点序号）；replay 命中时完全幂等跳过（零事件、行只读、不重复消耗额度，用例「replay 命中：静默跳过——不发事件、不重写行、不动上限」）。
- 资源释放：无。不持外部资源与驱动句柄。
- 平台差异：上限以 UTF-8 序列化字节数计算，中文与多字节文本按真实字节计入，跨平台一致；哈希计算跨平台一致（B21）。其余合同不约束。
- 状态所有者：累计已 report 条数计数、每站点序号表归引擎实例私有；已声明预置产物标签表归引擎内部产物注册表；节点行与 `report` 事件归 journal 存储。
- 日志级别：无——可见面为 `report` 事件与持久节点行。

### B16 内容族：发布是效应

- 输入：`publishArtifact(siteId, op, args)` 的两个内容成员——`markdown`（`args = [id, content, opts?]`）与 `file`（`args = [id, path, opts?]`）；装配侧 driver 的可选效应方法 `executeArtifactPublish`（缺席即命名失败）；journal 里既有产物行提供版本账与 replay 命中依据；上限取值与归属归 B22。内容族的定位是「发布」：请求下发给 driver，由它驱动真实字节搬运。
- 输出：成功路径四条事实被逐字钉住。（一）脚本拿到 `{id, version}`。（二）driver 恰收到一条请求：markdown 形态为 `{content, id, op, ordinal, runId, siteId, version}`（用例整条 deepEqual；无 opts 时该键整键缺席），file 形态为 `{id, op, ordinal, opts, path, runId, siteId, version}`（opts 原样透传、第二个实参就是 path）；`ordinal` 是站点实例序号、`version` 是本次产物版本。（三）journal 落一条 `kind:"artifact"`、`status:"completed"` 的行，带 `artifactId`、`inputHash = inputHash({op, id, args})`（args 是原样实参表、含 id 那一项）与 driver 返回的整条记录（bytes/contentType/uri 等由 driver 给）。（四）事件轨在 run-started 之后恰一条 `artifact-published{artifact: 记录, instance, type}`。版本号由引擎按 journal 派生并下发：首个版本 1；同 id 再发布是下一版（换站点调用也照样）；resume 后从既有 completed 行续（两版之后下一版是 3）；命中 running 行重执行时版本不跳号。primary 由引擎盖章且粘着：带 `{primary:true}` 发布的 id，两版行上的 `result.primary` 都是 true（后一版不再写也仍是 primary）。产物站点全程不发节点生命周期事件（queued / dispatched / settled 三类一个都没有，成功与失败两例都断言）。
- 错误语义：失败通道按族分裂（K8），内容族有可拒绝的 promise，所以下列失败都是节点级。（一）确定性实参护栏逐条钉住：id 必须非空串、markdown 的 content 必须是字串、opts.primary 必须是布尔，违反即以 `DriverError` 拒绝、message 分别匹配 `id must be a non-empty string` / `content must be a string` / `opts.primary must be a boolean`；不落行、不发事件（事件轨只有 run-started）、零 driver 调用。（二）driver 普通错误包成 `DriverError`（message 含 `Artifact publish failed: markdown "notes"`）：该站点行 failed、事件 `artifact-failed{error:{code,message}, id, instance, op}`、run 仍 `running`；driver 抛 `WorkflowError` 时原样保留（拒绝码与行内错误同码，样本 `ArtifactTooLarge`）。（三）装配没有发布能力 ⇒ `ArtifactStoreUnavailable`（大声的命名失败，不是静默空产物；行 failed；该例未断言 run 状态与事件载荷，合同不约束）。（四）一个 id 属于一种成员：markdown 成功后按 file 发同 id ⇒ `ArtifactKindMismatch`（run 仍 running、该站点行 failed）。（五）第二个 id 想当 primary ⇒ `ArtifactPrimaryConflict`，排在上限判定之前，message 含 `"notes" is already this run's primary artifact`。（六）同一 id 第 17 版 ⇒ `ArtifactVersionCapExceeded`（message 含 `already has 16 versions`）；第 33 个新 id ⇒ `ArtifactCapExceeded`，复用已有 id 不受上限影响（照样下一版）。这两个上限例只断言拒绝码与文案，行与 run 的可观察形态未断言，合同不约束。（七）结算之后再发布 ⇒ 直接以 run 的错误拒绝（stop 后为 `Cancelled`），零 driver 调用。
- 时序与并发：发布是一条外部效应——引擎把请求交给 driver，脚本的 promise 由该效应兑现或拒绝；不经过调度器（不占并发槽、不排 actor FIFO），全程不发节点生命周期事件。用例的观测点是 `await tick()` 排空一次微任务与宏任务之后的行与事件；成功与失败两路都在那之后可观察。护栏在效应之前判定（零调用、零行被钉住）；条数与版本上限也在效应之前判（B22 的口径，用例只断拒绝码）。同一 id 两次并发发布的竞态无用例，合同不约束。
- 幂等：发布本身非幂等（每次调用一条效应、推进版本）。replay 命中是幂等的三种：命中 completed ⇒ 直接返回记录里的 `{id, version}`、不过 driver、不再发事件；命中 failed ⇒ 按记录错误重新拒绝（`toJSON()` 与录制逐字段相等；resume 是崩溃恢复、不是复验）；命中 running ⇒ 重新执行且版本不跳号。id 的成员归属与 primary 认领跨版本粘着（同 id 的下一版不会把它变回去）。
- 资源释放：无独立释放动作——不占槽、不建会话、不发节点事件；每次发布恰一条 driver 效应，`driver.dispose` 不在本条（run 结算收尾归 B19）。上限与护栏都在下发之前判定，因此拒绝路径没有半途写完的产物。
- 平台差异：无平台分支——引擎只做字符串形态校验与 journal 记账；真实字节搬运与文件系统语义归 driver（`file` 的 path 原样透传），driver 侧的路径与编码差异合同不约束；用例只碰 ASCII 文本。
- 状态所有者：id 的成员归属、primary 认领、版本账（按 journal 的 completed 行派生）、条数与版本上限的判定、输入身份哈希（`inputHash({op, id, args})`）归引擎；真实产物记录（bytes/contentType/uri）与发布能力的有无归 driver；行与事件归 journal 存储；脚本只持有返回的 `{id, version}`。
- 日志级别：无——可见面是 `artifact-published` / `artifact-failed` 事件与那一行。

### B17 预置族：声明不是效应

- 输入：`declareArtifact(siteId, op, args)` 的四个预置成员（`chart` / `table` / `metrics` / `board`），`args = [id, spec]`；spec 由引擎校验（形状约束加序列化上限）；返回 void——没有 promise 可拒。装配里 driver 完全不参与：合法声明与全部失败路径都不调 driver（用例断言 `artifactCalls` 为空）。预置族与内容族共享同一份 id 账与行/事件形状，但定位是「声明」：只记账，不发生外部效应。
- 输出：一次合法声明 ⇒ journal 一条 `status:"completed"` 的行，带 `artifactId` 与预置记录 `result = {id, kind: 成员名, spec, version: 1}`（table 例逐字段相等），加一条 `artifact-published{artifact, instance, type}` 事件；spec 里的 `title` / `description` 提到记录顶层（chart 例钉住这两个字段与 version 1）；行的 kind 字段与其余成员未被直接断言，合同不约束。同 id 同 spec 再声明是幂等 no-op：不落新行（第二个站点没有行）、不发新事件（事件轨仍只有 run-started 与首条 artifact-published）。replay 命中同哈希时静默跳过（不重写、不再发事件），但认领照旧发生——resume 后换 spec 仍是 `ArtifactRedeclared`。
- 错误语义：全是 run 级失败（void 家族没有拒绝通道，K8），错误经 `engine.settled` 可读。（一）spec 非法（空 `columns` / title 超上限）⇒ `ArtifactSpecInvalid`，不落行。（二）spec 序列化超 8KB ⇒ `ArtifactSpecInvalid`（形状合法也不放行）。（三）同 id 换 spec ⇒ `ArtifactRedeclared`（message 含 `already declared with a different spec`）；旗子进 canonical spec——只改 primary 旗子也算换 spec，得 `ArtifactRedeclared` 而不是 `ArtifactPrimaryConflict`。（四）同 id 换种类 ⇒ `ArtifactKindMismatch`（不看 spec）。（五）第二个 id 想当 primary ⇒ `ArtifactPrimaryConflict`（message 含 `"dash" is already this run's primary artifact`）。（六）第 33 个 id ⇒ `ArtifactCapExceeded`（前 32 个声明后 run 仍 `running`）。（七）replay 命中但 spec 变了 ⇒ `InputHashMismatch`。（八）结算之后不再受理，与 report / log 同规（零行、零新事件）。跨族同 id（例如先声明 table 再发布 markdown）无用例，合同不约束；失败路径的事件轨形态与各错误文案的完整文本未被断言，合同不约束。
- 时序与并发：全部同步——校验、落行、发事件都在 `declareArtifact` 的同一回合内完成（用例调用后直接读行与事件；失败后直接 await `engine.settled`）；没有 driver 往返、不发节点生命周期事件、不占调度槽、不排队。
- 幂等：同 id 同 canonical spec 幂等（第二次零行零事件，对象引用不同也命中）；replay 同哈希幂等跳过。非幂等面是错误：换 spec / 换种类 / 超上限都让 run 失败（first-wins 之后其余声明不再受理）。预置版本号在用例里恒为 1，升版本路径未被覆盖，合同不约束。
- 资源释放：无——预置声明不产生外部效应、不占槽、不换会话；失败路径没有部分写入（不落行），没有需要释放的东西。
- 平台差异：无平台分支；上限一例按 canonical JSON 文本长度构造越线（用例只碰 ASCII），字节与字符切分的差异合同不约束。
- 状态所有者：预置族的校验、id 认领（种类 + canonical spec + primary）、版本 1、replay 哈希（`inputHash({op, id, args})`）归引擎；行与事件归 journal 存储；driver 完全不持有预置族（字节与 uri 只属内容族，B16）。
- 日志级别：无——可见面是 `artifact-published` 事件、那一行与 run 结算错误。

### B18 结算时对在飞 ask 的中止

- 输入：一次 run 结算发生时（`complete` / `stop` / `fail`，终态语义归 B19）调度器里的在飞 ask（已派发与已准入未派发两种）以及 driver 的 `cancelAsk`；测试以 untyped ask、`maxConcurrency:1` 的装配钉住分野。
- 输出：complete 与 stop 两路——对每个**已派发**的在飞节点下发一次 `cancelAsk`（排队未派发的不发：driver 那里还没有东西可取消），所有在飞节点的 deferred 都以 `Cancelled` 拒绝，并为每个在飞节点（含排队的）补一条 `node-settled{outcome:"cancelled"}`（两节点排队的例子事件顺序是 ask#1@1、ask#2@1 各恰一条）。fail 路——在飞 deferred 以**同一条 run 错误对象**拒绝（用例用 `===` 全等钉住，不折成新错），`cancelAsk` 照发（已派发的那个），但**不**补任何 `node-settled(cancelled)` 事件。
- 错误语义：complete / stop 的中止错误是新铸的 `Cancelled`（码是合同；message 只有两种形态之一，用例以 `in-flight subagent tasks were abandoned|Run stopped` 匹配）；fail 的中止不铸错误。中止只负责把节点结清并唤醒脚本，run 的终态与结算袋由结算路径（B19）决定。结算之后迟到的 `askSubmitAttempted` / `askTurnEnded` 是惰性 no-op：零新事件、零 `respondToSubmit`（用例钉住事件条数不变与 replies 为空）。
- 时序与并发：中止在结算调用内同步走完（cancelAsk、事件、拒绝的铸造），脚本侧随后 await 到拒绝；每个在飞节点恰一次 `cancelAsk`（仅派发过的）与恰一条 cancelled 事件（fail 路为零条）。中止与节点自身迟到回报之间不需要额外防护——节点随中止进入 settled，迟到的提交与结束被忽略。
- 幂等：中止随 first-wins 结算只发生一次（第二条终态路径整体被忽略，B19）；重复的迟到回报惰性；随中止 settled 的节点不会二次结算。
- 资源释放：`cancelAsk` 是 driver 侧 turn 的释放动作（已派发的才需要）；排队节点没有外部资源可放；整个结算收尾另调一次可选的 `driver.dispose`（B19）。
- 平台差异：无。
- 状态所有者：哪些节点已派发、哪些仍在排队归调度器的在飞表；取消指令由引擎发出、driver 执行；被中止节点的 cancelled 事件归事件轨；run 终态与 first-wins 归 B19 的结算路径。
- 日志级别：无——可见面是精简的 `node-settled(cancelled)` 事件与脚本侧的拒绝。

### B19 三条终态路径

- 输入：宿主结算面三个方法——`complete(artifact)`（产物可为 `null`）、`stop(reason, error?, supersededBy?)`、`fail(error)`；读面 `engine.settled` 与 `engine.status()`；driver 的可选 `dispose`。三路互斥，first-wins。
- 输出：四组逐字形状。（一）complete ⇒ 结算对象 `{artifact, status:"completed"}`；run 行 status `completed`、result 为产物、failure 缺席；事件 `run-settled{status:"completed"}`（事件不带产物）；产物与状态同一笔落库。（二）stop(user) ⇒ 结算对象 `{reason:"user", status:"stopped"}`；run 行 status `stopped`、stopReason `user`、failure 缺席；事件 `{stopReason, status:"stopped"}`；终态不是 errored，run 可 resume。（三）stop(`superseded`, error, nextRunId) ⇒ 结算对象带 `reason` / `supersededBy` / `error`；run 行的 supersededBy 与 failure（`error.toJSON()`）同一笔落库；事件 `{error: toJSON, status:"stopped", stopReason:"superseded", supersededBy}`。（四）fail(error) ⇒ 结算对象 `{status:"errored", error}`；run 行 failure 与 `engine.status()` 都是 `errored`；它是逻辑终态而不是伪装成 cancel。
- 错误语义：`fail` 与 `stop(superseded)` 把错误的 `toJSON()` 写进 run 行的 failure；`complete` 与 `stop(user)` 不写 failure，first-wins 例钉住后到的停止原因不会漏进已 completed 的行（run.stopReason 保持缺席）。first-wins：第二条、第三条终态路径被整体忽略——结算对象与 run 行保持第一条、`run-settled` 恰一条、dispose 恰一次。结算之后一切面不再受理：`log` / `enterPhase` / `report` / `concurrencyChanged` / `runStalled` / `askProgress` / `askStats` 均零事件（不抛错——用例无防护直接调用后只断言事件轨）；在飞的 ask 在结算点就被中止（归 B18）。结算之前这些面照常（结算前的 `log` 事件在场即证据）。
- 时序与并发：结算在调用内完成——行与事件同步写、`settled` 立即兑现；无论之后再调几次终态方法都不会出现第二条 `run-settled`。可选的 `driver.dispose` 恰一次，属于结算收尾（complete / stop / 三路竞争三例都断言计数 1；fail 一例未断言）；没有 `dispose` 的 driver 照样结算。`dispose` 与 `run-settled` 事件的先后合同不约束。
- 幂等：first-wins 让三路整体幂等（重复调用零副作用），`settled` 承诺同一个结算对象；事件轨与行不会因重复结算再变化。
- 资源释放：结算收尾统一调一次可选的 `driver.dispose`（存在才调）；在飞节点的 `cancelAsk` 是其前置的节点级释放（B18）。
- 平台差异：无——纯内存状态、事件与 journal 写入。
- 状态所有者：run 的终态位、结算对象与 first-wins 判定位归引擎实例；`dwf_run` 行的 status / result / failure / stopReason / supersededBy 归 journal 存储；`dispose` 的有无归 driver 装配。

### B21 确定性哈希（canonicalJson / fnv1a / inputHash）

- 输入：三个纯函数，都在根桶上（同时是测试侧深路径 `engine/hash.js` 的内容）。`canonicalJson(value)` 与 `fnv1a(input)` 各吃一个值，`inputHash(value)` 就是二者的组合（用例逐值钉住 `inputHash(v) === fnv1a(canonicalJson(v))`）。三者不读时钟、不做 I/O、不接受配置或上限参数，也不知道「谁在调我」：指令文本（B7）、世界读载荷 `{op,args}`（B12）、预置 spec 的重复声明比对与规格字节数（B16/B17）、修订 run 的 persona 比对（B14）、actor profile 的内容去重（B27）都是各自的调用方决定何时算、算哪一份。
- 输出：`canonicalJson` 给一段可 parse 的紧凑 JSON 文本，且与输入同内容（用例对含嵌套数组/对象的样例、`[]`、`{}`、串、数、布尔、null 逐个 round-trip）。规则逐条被钉：对象键按 UTF-16 码元排序并递归到每一层，整数键的插入序特权被抹掉（`{10:"x",2:"y"}` → `{"10":"x","2":"y"}`，`{b,B,_,0,中,a}` 的顺序是 `0 B _ a b 中`）；数组保持原序而元素内部照样规范化；对象里值为 undefined 的成员整键跳过、数组里的 undefined 记成 null（与 `JSON.stringify` 同语义）；标量交给 `JSON.stringify` 且不做定点化（`-0`→`"0"`、`1e21`→`"1e+21"`、`0.1+0.2`→`"0.30000000000000004"`）；字符串走 JSON 转义而非 ASCII 原样保留（`"中文😀"`）；只看自有可枚举属性（原型链上的键、`get` 访问器、`Date`/`Map`/`Set` 都被吃掉 ⇒ `new Date(0)`、`new Map([["a",1]])`、`new Set([1])` 都成 `{}`）。非 JSON 的基本值一律回落成 `"null"`（undefined、函数、symbol、NaN、±Infinity）——这是全函数性。**变体身份**也被钉住：`fnv1a` 输出恒为 8 位小写十六进制（空串与 4096 字符串都在内），偏移基数与质数由四个固定向量锁死（`""`→`811c9dc5`、`"a"`→`e40c292c`、`"hello"`→`4f9f2cab`、`"The quick brown fox"`→`ae4d67e2`）。`inputHash` 的可用性由此而来：同内容不同键序同串（`{a:1,b:2}`＝`{b:2,a:1}`、`{a:undefined}`＝`{}`），数组与对象永不混淆（`[1,2]`→`7d8e8676`，`{0:1,1:2}`→`9fbfb225`），规范化幂等（先规范化再哈希与直接哈希同串），并录了两个真实载荷的哈希（`{op:"glob",args:["*.ts"]}` 键序无关、`{x:[{y:"z"}]}`→`8d02ee00`、`"重跑"`→同 `fnv1a('"重跑"')`）。
- 错误语义：只有两条「不是干净返回值」的边界被逐字钉住：带环的对象让 `canonicalJson` 递归溢出为 `RangeError`；BigInt（裸值或藏在成员里）抛出、消息含 `BigInt`。合同不承诺对这两类输入给出兜底值，也不承诺谁先炸。**调用方必须在进哈希之前挡掉带环输入**：report item 的环探针排在序列化之前，因此那次失败是一次可读的 `DriverError` 而非爆栈（用例标题即此依据，细节归 B15）。除此之外三函数都不产错误码：`fnv1a` 不校验实参是串，`inputHash` 不校验实参是否纯 JSON；resume 的 `InputHashMismatch`（B7/B13）是调用方比较两个串的结果，不是哈希函数报的错。
- 时序与并发：全同步、单回合、无共享可变状态，因此没有重入、排队或跨调用可见的中间态。「同一份输入 ⇒ 同一串」是 replay 一致性的地基：resume 世拿本次输入重算串去比对行上记录的 `inputHash`，函数本身不知道自己处在第几世。事件与行的先后由 journal 的 `sequence` 决定（B7/B23），与哈希无关。
- 幂等：三条成立——纯函数、无副作用、无内部计数或缓存，重复调用既不去重也不改状态。反面同样重要：输入变一个码元即换一串，所以它只能当防御性一致性校验，不能当近似比较，也不能当身份（身份归 `(siteId, ordinal)`，B1）。
- 资源释放：不涉及。三函数不持资源、不设长度上限（4096 字符的输入照样进哈希，输入规模不进本条合同），也不做密码学用途——合同把它们定位为「一致性校验」，抗碰撞要求低是明确取舍，因此不引入任何哈希库依赖。
- 平台差异：两处，都被钉住。其一是编码：实现按 UTF-16 码元逐个喂哈希，每个码元拆成高低两字节各参与一次异或（因此 `String.fromCharCode(0x100)`≠`"\0"`、`"Ā"`≠`"\0"`、`"ā"`≠`"à"`——只取低字节就会撞，把高字节也折进来正是为了挡这个），这与「UTF-8 字节流上的标准 FNV-1a」**只在纯 ASCII 上逐字节一致**，非 ASCII 即分家（`"中文"`→`d52a5910`、`"😀"`→`efde461a`，且用例显式断言两者与标准实现不等）。其二是规范化：哈希不做 Unicode 规范化，预组合的 `"ā"` 与 `"a\u0301"` 是两个不同的串（前者与它的 NFC 形式同串）。代理对被当作两个码元各拆一次，被钉的只有那两个向量值；跨平台同一串靠的是「不依赖 locale、不依赖编码」这两条。
- 状态所有者：三个函数无状态。它们属于本包的公共面；「算哪个字段、何时算」归各自调用条目，「串存到哪」归存储与事件轨（节点行的 `inputHash` 列、mismatch 明细里的两侧值）。本包之外没有任何一方重算这些串，因此换实现必须换得出同样的字节，否则既有 run 行的 replay 判定全部错位。
- 日志级别：无——本包不写日志；哈希的可观察面就是它出现的那一列、那一个事件字段、那一条结构化 mismatch。

### B22 上限常量表

- 输入：无参数。都是根桶上的模块级常数，用例一次性取全：三张 caps 表（`WORLD_READ_CAPS` / `REPORT_CAPS` / `ARTIFACT_CAPS`）、产物 id 字符集 `ARTIFACT_ID_PATTERN`、引擎侧散常数（`WORLD_READ_INPUT_MAX_BYTES`、`INSTRUCTIONS_HEAD_MAX_CHARS`、`LAST_TOOL_NAME_MAX_CHARS`、`LAST_TOOL_TARGET_MAX_CHARS`、`REPAIR_ATTEMPTS`、`NUDGE_ATTEMPTS`、`FANOUT_EXPAND_CAP`、`HOST_BINDING`）、并发一族常数（`CONCURRENCY_*`）。另有两条「不是躺着不动」的观察用例：一条真跑一次引擎派发，一条把并发常数与 B24 的取值互认。

- 错误语义：本条不产错误——读常数不抛、不校验、不裁剪。失败通道一律在消费条目里，而且**方向按成员族分裂**：世界读入参越线是「有界化」而非错误（B12）；世界读结果超上限是节点级、脚本可 catch 的 `WorldReadCapExceeded`，run 仍活着（B11）；report 超限只能让 run 失败（`report` 返回 void，没有可拒绝的地方，B15）；产物侧按族分裂成 `ArtifactCapExceeded` / `ArtifactVersionCapExceeded` / `ArtifactPrimaryConflict`（B16/B17）。K8 把这条结构规则登记为既存事实：两个数字因此必须宽到讲道理的脚本永远碰不到。`FANOUT_EXPAND_CAP` 的执行方在 dw01 的 analysis 里，本条只钉它的值与「同一个数只有一份真相」，谁怎么用它合同不约束。

### B23 journal 内存端口

- 输入：`InMemoryJournalStore`——`JournalStorePort` 的内存实现，与生产侧的 SQLite 实现共用同一份端口语义（「一实现两处用」：fake-driver 测试、replay/resume 用它）。方法面十二个：`createRun(record)`、`getRun(runId)`、`updateRunStatus(runId, status, settlement?)`、`updateRunUsage(runId, spentTokens)`、`putActor/getActor/listActors`、`putNode/getNode/listNodes`、`appendEvent(runId, event)`、`listEvents(runId, {afterSequence?, limit?})`。actor/node 读方法按 `(runId, siteId, ordinal)` 三元定位。全部同步、无返回 promise 的方法。用例还直接构造 `NodeRecord`（`inputHash/kind/ordinal/runId/siteId/status` 六个必备键）与 `ActorRecord`，不经引擎。
- 输出：读侧一律给克隆。`createRun` 落一份克隆（调用方随后改自己的对象不影响行），并给该 runId 建齐三套桶。未知 runId 的不对称被逐条钉住：**写侧全抛、读侧全空**——`getRun`/`getActor`/`getNode` 返回 undefined，`listActors`/`listNodes`/`listEvents` 返回空数组（带分页选项同样空）。跨 run 完全隔离：同一 `(siteId, ordinal)` 在两个 run 下是两行，事件轨互不可见。行的身份是复合键 `(siteId, ordinal)`，同站点不同序号是两行；`putNode`/`putActor` 是**整行替换**而非补丁，第二次写没带的键就没了（`result`/`stats`/`messageBoundary` 三键从在场变缺席，而 `inputHash` 这类没在新实参里出现的必备键仍按实参写入）。`listNodes`/`listActors` 按写入顺序返回，与站点 id 的字典序无关。`appendEvent` 从 0 起按 run 各自单调分配 `sequence`，并填入追加时刻 `timeCreated`；返回值与存储都是克隆，形态为 `{sequence, timeCreated, event}` 三个键，端口**不解释事件内容**（进什么样、出什么样，用例逐字段 deepEqual）。`listEvents` 的 cursor 是「严格大于」而不是偏移量：`afterSequence: 1` 得到 `[2,3]`，`-1` 得到全部，等于最大序号或更大值得到空页；`limit` 在过滤之后生效，0 与负数得到空页，`{}` 等价于无选项；按 cursor 翻到底逐字节等于全量（不重叠、不漏）。结算袋的三种写入规则见「错误语义」前的两条：非终态清空、终态失败三件套整体改写、产物反向。
- 错误语义：两类端口级失败都是**同步抛普通 Error**，不是 `WorkflowError`、不返回错误对象：重复 `createRun` 同一 runId 抛（消息含 `already exists`）、未知 runId 的五个写方法各抛（消息含 `unknown run`）。用例用片段匹配，完整文案合同不约束。第三个失败点是「非纯数据进不了存储」：值为函数或 symbol 的行写入抛（用例只断言「抛」，具体错误类型与文案合同不约束）。深拷贝的形态也被钉住：端口用**结构化克隆而不是 JSON 往返**，因此「键在场但值是 undefined」这一形态两侧必须留住（`result: undefined` 与 `messageBoundary: undefined` 写进去还能读出来、键在清单里），而 `JSON.stringify` 往返会把它抹掉——这是端口两侧共用的语义而不是内存版的特点。
- 时序与并发：全部同步、单线程，没有锁也没有事务：端口面不提供事务性，两次写入之间的中间态由调用方负责（B8 的「先写 `spent_tokens` 列、再发同值事件」靠调用顺序成立，不靠原子性）。`timeCreated` 是同一次追加时的挂戳时刻，落在 `[before, after+1]` 内且第二次不早于第一次；它是存储层的观察面，不参与任何引擎判定（B7）。`sequence` 是顺序的唯一来源。
- 幂等：`createRun` 非幂等（第二次即抛）；`putNode`/`putActor` 按键 upsert，同键第二次只覆盖不新增，因此引擎整行重写终态不会长出第二行（B7）；`updateRunStatus` 与 `updateRunUsage` 都是**绝对写入**而非累加（同一数字重写两次结果一致，`0` 是合法写入值）；`appendEvent` 永不去重，每次调用都领一个新序号；`updateRunUsage` 只动用量列，绝不碰状态与失败（用例先写 errored+failure 再写用量，两者原样幸存）。结算袋的产物侧「缺席即不触碰」使补写幂等，而失败三件套「缺席即没有」使补写**不**幂等——这正是 K5 登记的不对称。
- 资源释放：端口上没有 close/dispose 方法，合同也不要求；四张桶随 store 实例而生、随其被回收。多个 run 共用一个 store 实例是设计允许的（分桶即隔离）。
- 平台差异：被钉的只有形态，没有平台分支：结构化克隆需要宿主提供该能力（Node 侧现成）；`timeCreated` 取的是宿主墙钟，跨平台只做「不早于前一条」这种单调断言，不锁具体数值；分页、复合键、写入序都与路径、编码、换行无关。测试侧要求 Windows 与 POSIX 同结果，本条不含平台特有取值。
- 状态所有者：`dwf_run` / `dwf_node` / `dwf_actor` 三类行与事件轨的**持久所有权**归这个 store（按 runId 分桶）；行内容与事件载荷的构造归引擎侧的各条目（B7/B12/B15/B16/B17），端口只搬运不改写（除结算袋的清空/改写规则外不做任何语义加工）；`sequence` 与 `timeCreated` 归端口实现自己。类型面声明的 unique(runId, actorActor…) 之类的复合约束在内存版不被校验（内存版只按 `(siteId, ordinal)` 存行），SQLite 侧的强制在本包之外——本条钉的是「两侧共用的语义」，不是 Map 的实现细节。
- 日志级别：无——端口不写日志；它的可观察面就是读回来的行与事件。

### B24 自适应并发控制器

- 输入：`ConcurrencyController(key, ceiling)`——一个 provider key 上的纯 AIMD 状态机（key 只用来填进变化事件，控制器自己对它无感；一个实例只服务一个 key，因此 key 是身份而不是参数；`ceiling` 既是初值也是上界）。信号面八个方法，每个都显式收 `now`（毫秒整数）：`snapshot()`、`canAdmit(now)`、`observe(now)`、`admitted(now)→epoch`、`succeeded(now, epoch)→changes[]`、`throttled(now, epoch, reason, retryAfterMs?)→changes[]`、`failedTransient(now)→changes[]`、`ended(now)→changes[]`、`waiters(now, count)→changes[]`。**控制器不读时钟、不做 I/O**：`now`、何时算停滞、退避多久一律由调用方（宿主的进程级治理器，本包之外）给。`epoch` 是准入时发给请求、请求结束时带回来比对的批次令牌。
- 输出：`snapshot()` 给固定键 `{key, ceiling, cap, epoch, inFlight, waiters, successStreak}` 加四个**有值才在场**的可选键 `cooldownUntil` / `lastRequestAt` / `lastGood` / `lastBad`（缺席即整键不存在，不是 undefined）。`admitted` 返回它所属的 epoch 并刷新 `lastRequestAt`。信号方法返回本次引起的 cap 变化数组，长度 0 或 1（一次信号里空闲重置与 cap 裁决互斥，类注释说的「会是 2 条」不可达，K6）。变化对象固定带 `{key, previous, next, reason}`，`lastGood` / `lastBad` / `cooldownMs` 只在有值时在场；`recovered` 与 `idle_reset` 这两个 reason 由控制器自己命名，三个限流 reason（`rate_limited` / `provider_overloaded` / `offpeak_queued`）由调用方给。核心数值规则被逐档钉住：乘性减少 `cap = max(1, floor(cap × 0.75))`（8→6→4→3→2→1→1）；加性递增在「当前 epoch 的连续成功满 K=4」且「有等待者」且「cap < ceiling」时 +1，兑现后 streak 归零；在 `lastGood` 之上探测被限流 ⇒ 退回 `lastGood`（`previous`/`next`/`lastBad`/`lastGood` 四值都写进事件），且退回那一档不证伪 `lastGood`；cap 恰在 `lastGood` 上则按系数减并清掉被证伪的 `lastGood`；`lastGood` 只由完成的 streak 设立（减 cap 不给自己发证书）。空闲重置条件为「在飞归零」且「`now - lastRequestAt ≥ 300000`（差 1ms 不算）」，效果是 cap 回天花板、清 streak/cooldown/lastGood/lastBad、翻 epoch、**保留 `lastRequestAt` 与 waiters**。
- 错误语义：这一族不抛错、不拒绝、没有失败通道。非法输入按取值消化而不报错：`retryAfterMs` 为 undefined / 0 / 负数 ⇒ 没有 cooldown（`cooldownUntil` 键缺席、闸门照开）；`waiters` 为负数 ⇒ 按 0 记；多余的终结信号（在飞已为 0 时再 `ended`）⇒ 停在 0 不写成负数；`reason` 只被搬运进事件，控制器不校验其词汇（词汇表外的取值合同不约束）；`ceiling` 为 0、负数或小数，以及 `now` 为小数/负数的取值合同不约束（用例只取 1、2、8 与正整数时刻）。陈旧令牌不是错误：旧 epoch 的 429 不动 cap、不发事件，但**仍然清 streak、仍然吃下 Retry-After**；旧 epoch 的成功不进 streak、不兑现 +1。
- 时序与并发：全同步、无往返。闸门 `canAdmit(now)` 是纯查询：`inFlight < cap` 且 cooldown 已到点，不碰任何状态、不做空闲检查（一小时后仍满员 ⇒ 仍 false 且快照逐字段不变）。冷却到点即放行：`T0+4999` 关、`T0+5000` 开。`admitted` 自己不做空闲检查——陈旧的一档要由 `observe` 或其它信号入口抬回天花板（用例钉住：`admitted(T0+IDLE)` 后 cap 仍是 6，紧跟的 `observe` 才产 `idle_reset`）。任何一个信号入口都顺带做空闲检查，不只是 `observe`。翻页规则：只有 429 裁决与空闲重置翻 epoch，升档不翻。cooldown 取更晚者，不被更早的 Retry-After 往回拉。
- 幂等：状态机本身不幂等（每个信号都推进状态），被钉的幂等性质有三条：①多余终结信号不二次扣减、在飞有下限 0；②干净复位后再来的空闲信号既不发事件也不翻页（已经回到天花板且状态干净 ⇒ no-op）；cap 已在天花板但状态脏 ⇒ 清状态、翻页，但因数值未变而**不发事件**；③**纯状态等价**：同一串信号（含同一串 `now`）重放两次得到逐字段相同的快照与相同的事件序列——这是这套测试能验收新实现的前提，也是「不读时钟」这条纪律的可观察证据。
- 资源释放：不持资源——无定时器、无句柄、无注销动作；实例随治理器按键持有、随其被回收。`inFlight` 的归还责任在调用方：每个准入必须最终落到 `succeeded` / `failedTransient` / `ended` 之一，否则闸门会一直关着（控制器不看请求是否真的结束，合同不约束调用方的配对纪律）。
- 平台差异：无。算术只有整数、一次 `floor(× 0.75)`（0.75 是精确二进制值）与整数比较；`now` 由调用方给，因此测试不需要墙钟，Windows 与 POSIX 上同一脚本必得同一结果。无路径、无编码、无 locale 分支。
- 状态所有者：`cap` / `epoch` / `inFlight` / `waiters` / `successStreak` / cooldown / `lastRequestAt` / `lastGood` / `lastBad` 全部归控制器实例自己，一世一份、不持久化（重启即从天花板重学，恢复逻辑在包外）。`now`、reason 词汇、`retryAfterMs`、等待者数归调用方喂；变化数组扇出成 `concurrency-changed` 事件由宿主做（B9，引擎对该载荷不解释、不裁剪）；cap 该是多少的**判据**归本包，什么时候该问它归宿主治理器。
- 日志级别：无——本包不写日志；控制器的可观察面是快照与变化数组，再往上是那条 `concurrency-changed` 事件。

### B25 lowering：facade 调用按站点身份改写

- 输入：两个入口。一站式 `lowerWorkflowScript(scriptText)`（内部建程序、取诊断、收站点、降级）；分步 `lowerWorkflow(workflow, table)` 吃 dw01 产的 `WorkflowProgram` 与 `SiteTable`（用例钉住两条路径产物逐字节相同，装配顺序本身就是合同）。实参是**脚本原文**：位置参数为行内文本的脚本片段，含 `agent` / `ask` / `report` / `artifact` / `world` / `git` / `files` / `phase` / `log` / `args` 这些 facade 名字。`HOST_BINDING` 常量（`"__host"`）是宿主绑定名，用例同时钉住「harness 绑定的自由标识符就是它」。
- 输出：`{ok, diagnostics, lowered?}`；`lowered` 为 `{code, siteIds}`。`code` 是 **async 函数体文本**（顶层 await 与末尾 return 合法）：语句之间一个换行、末尾一个换行，空脚本降级成空串。改写形状逐字节锁定：`agent("alice","researcher")` → `__host.createActor("actor#1", "alice", "researcher")`（站点 id 插到最前、其余实参原位）；`alice.ask("do it")` → `await __host.ask("ask#1", alice, "do it")`（receiver 移到第二位）；`report(item, tag?)` → `__host.report("report#1", item, tag?)`（预置标签原样跟着走）；产物两族同形不同名——内容族走 `__host.publishArtifact("artifact#N", op, [实参按位置打包])`，预置族走 `__host.declareArtifact(...)`，六个成员各得一条；世界读与 git 观察一律收成 `__host.worldRead("world-read#N", op, [实参])`，零实参的 op 也得一个空数组（`"git-diff", []`），元数与形状校验不归 lowering；`log` 走 checker 解析的名字而**不产站点**；`phase("  gate  ")` → `__host.enterPhase("gate")`（去两端空白），名字缺席（非字面量或全空白）退回 `void 0;`；`args` 的每个读数位改成 `__host.args`（下标、解构、展开、`typeof`、比较、三元、数组元素都算），但脚本自己的同名绑定不动（`function f(args) {...}` 保持原样），简写属性 `{ args }` 整条不改写（K2：改了会写出不同形状的语法，代价是留一个自由标识符，用例用 `new vm.Script` 证明它仍能解析）。类型擦除：`interface` / `type` 整条消失，类型实参丢弃（`ask<Plan>` 不留 `Plan` 文本、连被 schema 拒收的 `ask<Date>` 也照样降——**lowering 不看 schema**），`!` 与 `satisfies` 与 `<T>()` 泛型签名擦除，可选参数只留名、默认值保留，`enum`（含 `const enum`，不内联）与 `class` 留下可运行 JS。可选链短路保留：标识符 receiver 用守卫三目、不引入临时变量；非标识符 receiver 提升一个 `var _a`（多个复用同一批名字）并保证 receiver 恰好求值一次；receiver 自带的可选链原样留在守卫里；非可选链的直接调用不包守卫。`siteIds` 只含被打桩的五类（actor/ask/report/artifact/world-read 前缀），顺序即站点表的发现序（先撞 CallExpression 再下钻 receiver，故守卫一例里 `ask#1` 排在 `actor#1` 之前）；`log` 与 `phase` 不在其中。文本细节也进锁：注释三种形态都保留（`removeComments: false`）、原样保留的字面量不转义而 lowering 新建的字面量转义成 `\uXXXX`（阶段名 ⇒ `"\u9636\u6BB5"`）、`await(` 之间没有空格这类打印器怪癖照录。
- 错误语义：`ok === false` ⇒ 返回体**恰好两个键**（`diagnostics`、`ok`），`lowered` 键整个缺席（不是 undefined）。诊断是「行/列/码/文本」四字段、行列映射回脚本自身（1 基）。两类被钉的脏脚本：typecheck 失败（如 `log("done", 1)` ⇒ TS 诊断 2554 `Expected 1 arguments, but got 2.`）与 facade 引用逃逸 9001（取引用 `const f = agent`、解构提取 `const { ask } = a`、重打类型 `a as unknown as {ask(...)}`、计算成员调用 `a["ask"]("y")`，以及 `log` / `report` / `files.glob` 的引用——站点身份不只护 agent），9001 的消息按三种形态逐字钉住。`phase` 的名字质量不是 lowering 的地盘：同一份脚本 `lowerWorkflowScript` 返回 `ok: true` 且诊断为空、三处坏名字全成 `void 0`，而 `analyzeWorkflowScript` 返回 `ok: false` 加三条 9004（dw01 范围）。诊断码 2554/9001/9004 都不是 lowering 自己产的——本条只钉「脏脚本不降级、诊断原样带回归因位置」；lowering 自身是否可能产独占的诊断码，合同不约束。
- 时序与并发：一次调用一个回合、同步返回，不做 I/O、不读时钟、不起进程，也不能被 await。它发生在 run 开始之前（宿主编译期），因此 `siteIds` 与站点表决定的是「这个脚本有哪些调用点」，与运行期实例序号（B1）无关——两处序号各自从 1 起，靠同一个 `siteId` 文本对上。守卫的求值次序是运行期事实，用例把 lowered 代码真跑一遍来钉它：守卫命中时 receiver 与实参都不求值，`__host` 上一次调用都没发生（`calls` 为空数组、脚本返回 0）；守卫不命中时恰好一次 `createActor` 加一次 `ask`。
- 幂等：纯函数——同一份输入两次降级逐字节相同（用例直接对拍两次调用，含需要临时变量的样例），`siteIds` 亦然；重复调用不消耗任何东西。跨进程/跨机器也成立，因为输出不依赖插入序、不依赖 locale、换行被强制成 LF。非幂等面在别处：`phase` 的运行期 ordinal、实例序号（B9/B1）。
- 资源释放：`lowerWorkflowScript` 内部建的 TS 程序没有显式释放步骤，合同不约束其回收时机。产物侧没有需要注销的句柄。递进沙箱的就是那段文本——沙箱只需提供 ES intrinsics 加 `__host` 这一个绑定（用例正是按这个契约用 `new Function(HOST_BINDING, ...)` 跑的）。
- 平台差异：一条被钉住：打印器显式要求 LF 换行，因此 Windows 与 POSIX 产出同一份字节（golden 与 fixture 因此可以跨平台比对）。其余差异合同不约束：诊断的 `column` 按 UTF-16 码元计（ astral 字符的用例未覆盖）、脚本文件的行结束符形态由调用方给定、`await(` 这类排版怪癖与平台无关。
- 状态所有者：`code` 与 `siteIds` 是本条唯一产出，两者都归这次调用的返回值，没有任何跨调用状态。站点 id 的编号与发现序归 dw01 的 `collectSites`（本条只消费）；绑定名 `__host` 归本包；实际 supplying 该绑定的沙箱垫片归包外（`args` 由沙箱注入、引擎上没有它，K13）。「谁检查名字合法性」分三层：lowering 不检查、analyze 检查（9004）、引擎在运行期再 trim 一次（B9）。
- 日志级别：无——纯函数不写日志；它的可观察面是那段文本、那份站点表与那组诊断。

### B26 golden 回放（350 例 lowering + 26 例整轮运行）

- 输入：两份**由旧实现录制的**期望（`fixtures/golden/{lowering,engine-run}.json`）加一份共享语料（`fixtures/corpus.mjs`）。语料两个来源：dw01 的 324 条（相对路径 import，不复制第二份真相）+ 本包自有的 engine-run 族 26 条，合计 350 条 lowering 输入；每条是 `{id, script, expect}`，engine-run 族另带一份 drive 表且 `expect` 恒为 `clean`。回放只经公开入口（根桶），入口模式由 `KNORVIA_DW02_ENTRY` 决定（source / dist 两侧各跑一遍，标题里带 `entryLabel`）。录制载荷的构造函数与录制器共用同一份（`tests/harness.mjs`），因此「回放断言的形状」与「当初录下的形状」不可能分叉。
- 输出：两条清单类断言加两条族回放。清单断言：golden 目录里 `.json` 恰好是这两份；每族的语料 id 集合与录制 id 集合**双向无差**（有样例没录制、有录制没样例、条数不等，三种各一条断言）；录制条数不低于族下限（lowering ≥300、engine-run ≥25，防「悄悄缩水」）；`runSamples` 必须是 `samples` 的子集（同一批输入在两份录制里各管一半，不该有第三份清单）；重放条数最后等于录制条数。族回放：逐条 `deepEqual(现算载荷, 录制载荷)`，任一字节不同即失败，并先断言语料的 `expect` 分类等于录制值（防语料静默跑偏）。载荷形状：lowering 族是 `{id, expect, ok, diagnostics[{code,column,line,message}], siteIds, code}`（后两项在不过时是 null；实际分布 299 clean / 51 diagnostics，其中 33 例 `ok:false`），即「本包对外唯一的生产物就是这段代码文本」；engine-run 族是 `{expect, id, run{status, stopReason?, supersededBy?, failure?, result?, args?, spentTokens, caps}, events[{sequence, ...event}], nodes[], actors[], driver{emits, sessions, starts, replies, cancelled, worldCalls, artifactCalls, disposeCount?}}`——把一次完整 run 的结局、Boundary C 事件轨、三张 journal 行与 Boundary B 每一次效应调用都录了下来（26 例结局为 21 completed / 5 errored）。载荷整体经一次 JSON 往返归形，行的 `runId`（常量）被剥掉，事件只取 `sequence` + 载荷而不取挂戳时刻。
- 错误语义：本条不新增错误语义——它把 B1–B25 的语义固成字节。夹具错误必须响两声而不是被固化：engine-run 族要求样例能降下来，降不下来录制当场抛错；drive 表**缺席即失败**（没准备应答的站点/队列让该次效应以 `DriverError` 拒绝，同时记进 unprepared 并在结束前整体抛错，因为「静默补一个默认值等于把『引擎在这个点上收到了什么』从合同里抹掉」）。上游语料变动由 `dw01CorpusPin`（条数 + 逐条 `id\0expect\0script` 摘要）在 import 时抛，无环境开关可关——变了就逼一次重录与合同升版本，不许迁就改指纹。已登记的张力只有一处：engine-run 的 26 例把 21 处引擎错误 `message` 录进了载荷，与「流程判断一律用码、绝不匹配错误文本」相冲，K10 登记为待决（不放宽断言、不擅自裁掉），静态那一半不受影响。
- 时序与并发：engine-run 回放跑的是真 run：脚本 → lowered 体 → 只绑 `__host` 的 Boundary A 垫片（八个成员逐项 bind，外加冻结的 `args`）→ drive 应答。应答时刻是合同的一部分：一个 drive 条目在**派发之后**以及每次 **reject / nudge 裁决之后**被消耗，且经微任务投递（生产侧应答来自模型，同步回灌会让引擎在一次调用里重入自己），因此录下来的事件轨含真实的派发/结算交错。run 结束后 `await tick()` 排空。`unprepared` 检查在返回值之前，录制失败不会留下半成品。K13 登记过：早期草稿注释误写成「repair 时引擎会重新调 startAsk」，实测不重新派发，两处头部已按实测改对——本条的驱动语义以改后的为准。
- 幂等：这就是本条的存在理由——同一份输入在任何实现、任何入口模式、任何一次运行里都必须产出逐字节相同的载荷。因此它对「新实现能否被验收」是等价判据，而对录制本身，重录只在语料或实现真的变了时做，且 `record-golden.mjs` 显式拒绝 dist 入口（录制只属于旧实现/权威实现那一侧）。两条族的 `min` 下限保证「删样例」不能蒙混过关，但加样例必须重录并升合同版本。
- 资源释放：回放不持资源（读两份 JSON、跑内存端口、起一个引擎实例）。录制侧的纪律是「录完必须格式化」，且不落 volatile 字段（runId 用常量、事件不带挂戳时刻），否则回放必然假红。
- 平台差异：正因为载荷里是代码文本与事件序列，B25 那条「换行强制 LF」在这里兑现成跨平台可比；时间量一律不进录制（`timeCreated` 被排除、`spentTokens` 是记账数而非耗时），因此没有墙钟敏感性。测试侧要求 Windows 与 POSIX 同结果（README 的命令与 CI 双平台矩阵）；本条没有平台分支。
- 状态所有者：期望值的**唯一真源是这两份录制文件**（旧实现输出），语料只拥有输入；drive 表约定真源在 harness 的整轮装配与族文件头部两处，必须一致；`entry-exports.json` 与本条无关（那是 B30 读的 dw01 资产）。跨合同复用是有意的：代价是 dw01 语料被本包测试依赖，因此有那枚硬校验兜住。任何断言强度或语料变化都要升 README 首行的合同版本并在 `acceptance.md` 追加一节。
- 日志级别：无——golden 不写日志；它就是「逐字节回放」这一道门槛本身（计划书选定的核心门）。

### B27 schema 合成

- 输入：类型面来自**同一次编译的三件产物**：`createWorkflowProgram(scriptText)` → `collectSites(workflow)` → `synthesizeAskSchemas(workflow, table)` → `buildAskSpecs(table, schemas)`，这条拼装顺序本身是合同（用例显式按它手工拼装，并钉住手工 == 一站式 `synthesizeWorkflowSchemas(scriptText)`）。发射只针对 `ask<T>()` 的 `T` 位：类型由 checker 解析，schema 结构透传给引擎（引擎不解读，只交给注入的校验器与 `startAsk` 载荷，B4）。约束提取读属性与顶层类型的 JSDoc 标签。profile 面另收一份站点图（`deriveActorSubmitProfiles(graph, askSpecs)`，可手工构造分析给不出来的图）或一份真实 workflow+table+askSpecs（`deriveActorSubmitProfilesFor`）。序列化面 `serializeSchema(schema)` 只吃已合成的 schema。
- 输出：五族形状。其一 typed 判定：显式类型实参且 checker 展开后**不是原始 string** 才发射，按站点 id 归档（键集合即 `["ask#N"]`）；`ask()`（facade 默认 `T = string`）、`ask<string>()`、别名到 `string` 的 `ask<Text>()` 三个都是 untyped；字面量类型、条件类型结果、括号包裹的联合都算 typed。站点 id 按源码顺序编号，诊断定位在 `ask` 标识符处。其二 发射器：标量 `{type:"number"/"boolean"/"null"}`、`unknown` ⇒ **许可式空 schema `{}`**、字面量 ⇒ `const`；`string[]` 与 `readonly string[]` ⇒ `{items,type}`；索引签名 ⇒ `additionalProperties: <值 schema>`（`Record<string, unknown>` ⇒ `additionalProperties: {}`）；对象 ⇒ `additionalProperties:false` + `properties` + `required`，`required` 按**声明顺序**且只收非可选属性，可选属性既不在 required 也不带 undefined，只有可选属性时 `required` 整键缺席，空接口只剩两键；嵌套对象与数组元素继续递归；闭合对象对多余键出违规而索引签名对象放行任意键。union：成员全为字面量 ⇒ `enum`，**顺序取 checker 规范化的顺序而不是书写顺序**、重复成员折叠；混入非字面量 ⇒ 整体退化 `anyOf`，字面量成员被子类型吸收（成员数是 checker 的）；模板字面量类型展开成有限 `enum`（笛卡尔积）。tuple ⇒ `prefixItems` + `minItems`/`maxItems`（可选元素压 max、rest 元素进 `items`、定长两者相等），元素递归。intersection：品牌类型按其原始标量发射，纯对象 intersection 合并成一个 object。递归类型提升为 `$defs` + 根 `$ref`，def 名取符号名；非递归的具名类型即使被用三次也**就地内联**；互递归只为真正被再次进入的类型建 def；同名泛型的第二个实例化按 `Schema2` 递增去重；数组类型自身的递归也建 def（名取 `Array`）。其三 JSDoc：`@minimum`/`@maximum`/`@exclusiveMinimum`/`@exclusiveMaximum`/`@default`/`@minLength`/`@maxLength`/`@pattern`/`@format`/`@minItems`/`@maxItems` 进对应关键字，文档正文进 `description`；`@default` 先按 JSON 解析（`[1,"a"]` ⇒ 数组、`"quoted"` ⇒ 串），解析不了当裸串，标签只有名字没值则不写关键字，`@default` 空 ⇒ `""`；非数值的数值标签与子集外的标签（`@example`、`@deprecated`）一律静默忽略；顶层具名类型/具名 union 的文档挂到根 schema（与 `$defs` 共存），匿名内联类型没有 `description` 键；泛型实例化的根 `description` 取类型自己的 aliasSymbol ⇒ 拿到的是**库符号**的英文注释，脚本写在别名上方的注释抢不到（K3，登记为版本敏感）。其四 装配：`buildAskSpecs` 按站点表逐站点给条目——有 schema 记 `{schema, typed:true}`，没有就显式 `{typed:false}`；schemas 站点内容相同（按规范化内容去重，不是引用相等，且返回的 schema 是一份副本而非原引用）记 mono，出现第二种内容退 generic；untyped ask 混在 mono 里不影响判定；没有 ask 落到某 actor 记 untyped；表覆盖图里每个 actor 且顺序即图序；条件 receiver 的一个 schema 计入每个可能落到的 actor；任何一个 ask 的 actor 集为空或 askSpecs 缺该站点 ⇒ 整表 generic 且立即返回（不猜）；非 ask 节点跳过；图里未登记的 actor id 被补桶而不静默跳过；generic 复用同一个常量对象而不是每次新建。`serializeSchema` 给递归排序对象键后的 2 空格缩进 JSON 加**恰好一个末尾换行**，数组保持原序（`required` 的声明序、`enum` 的成员序都被保留而 `properties` 被重排），`$defs`/`$ref` 一起排序而 ref 字符串不动，序列化只重排键不改内容（parse 回来与原值深相等，两个插入序不同的对象序列化后逐字节相同）。
- 错误语义：两条通道必须分得开。**typecheck 不过 ⇒ 不合成**：一站式入口只带回归因诊断（`schemas` 为 `{}`，诊断是 TS 自己的码/行列/文本，如 2322、2554），短路条件与手工拼装一致——「脚本本身有病」不该和「类型落不进 JSON 子集」混成一种失败。**子集拒绝 ⇒ 码 9002**（`SCHEMA_DIAGNOSTIC_CODE`）加消息前缀 `unsupported ask result type:` / `unsupported report item type:`，该站点**不留 schema**、不拖累同脚本其他站点（一次合成的诊断可以只有它一条）。被钉的拒绝清单：`any`（提示改用 `unknown` 或具体类型——注意 `unknown` 是放行的一端）、`never`、`bigint`/`symbol`/函数/`Date`/`Map`/`Set`/`Promise`/`Error`/`Uint8Array`/thenable、必填属性带 `undefined`、union 成员里有 `undefined`、class 实例；嵌套不可序列化成员定位到路径（对象路径 `$.o.p`、数组元素用 `$.list[]` 而不是 `$.list[0]`——诊断定位的是类型路径不是某个值的下标、union 变体用 `$.v|1`），class 与顶层路径不带 `(at $)`。规模上限：union 成员超过 `MAX_UNION_MEMBERS`（100）即拒（`union has too many members (101 > 100)`，字面量形与对象形都拒，模板字面量笛卡尔积是现实中越界的那条路 ⇒ 144 > 100），恰好 100 放行（闭区间）。`report` 不产出 schema，只贡献同一条诊断通道：类型取自实参表达式，`unknown` 与纯 JSON 形状放行，函数/类实例/Promise 在调用点被拒；`report()` 实参缺席不是 9002 而是 typecheck 的 2554。校验侧的失败形态（违规数组）归 B28。
- 时序与并发：编译期、同步、不读时钟、不做 I/O，因此同一次 run 里引擎拿到的 `askSpecs` 是常数。合成与降层的先后无关（两条通道互不查询：lowering 不看 schema，B25；合成不看 lowering）。发射与校验是同一个子集：合成器发出的自引用 `$ref`/`$defs` schema 能被 B28 校验器吃下（用例把这条闭合性当断言）。三件产物必须出自同一个 program：换一份 table 配另一份 schemas 只按 id 对齐（这既是被钉的装配规则，也是「两份编译产物被拼在一起」会在运行期变成 `MissingAskSpec` 的原因，B3）。
- 幂等：同一脚本两次编译逐字节相同（用例对拍 `serializeSchema` 输出）；手工拼装与一站式入口产出相同的 schema 与诊断；序列化与对象插入序无关。诊断顺序按站点/调用点出现顺序输出，是确定的。非幂等面在别处：mono 去重按内容而不是按调用次数，`@default` 的 JSON 解析失败会静默退化成裸串（同一标签两种解释，取决于文本）。
- 资源释放：无显式释放。程序对象与 checker 随调用结束被回收，合同不约束其生命周期；`$defs` 表与 ref 字符串是纯数据，没有需要注销的句柄。递归类型的展开受 100 成员上限与「只为真正被再次进入的类型建 def」两条约束，但**没有深度上限参数**——更深的递归如何收敛合同不约束。
- 平台差异：无被钉的平台分支：输出文本不含换行差异（序列化只用 2 空格缩进加一个 `\n`），排序是 `Object.keys().sort()` 的码元序，与 locale 无关。真正的敏感性是**版本而不是平台**：根 `description` 抢的是已安装 typescript 版本的 lib 注释原文（K3，升级 TS 若改该注释本条会红）；成员序、`const` 吸收、字面量折叠都由 checker 的规范化结果决定，因此换 TS 大版本可能需要重录 B26 的 golden。
- 状态所有者：schema 表的构造归本包发射器；站点身份与编号归 dw01 的站点表（合成侧只按 id 归档）；JSDoc 文本与类型结构归脚本作者与 checker；`askSpecs` 是装配产物、由调用方在构造时注入引擎、引擎只读且从不补全（B3/B4/B5）；profile 表归宿主（发给模型的 submit 工具描述），不在引擎判定面上——引擎判定 typed 与否只看注入的 `askSpecs`；序列化文本归快照/回放消费方。四个零消费者的再导出（`artifactFamilyOf`、`formatViolations`、`serializeSchema`、`synthesizeWorkflowSchemas`）按 K11 保留在册、由兼容面断言钉住，不因无人用而删。
- 日志级别：无——诊断是结构化 `{code,line,column,message}` 返回体，不进日志；schema 的可观察面是 `startAsk` 载荷与校验结果（B4/B28）。

### B28 schema 校验器与违规模型

- 输入：`validate(schema, value)`——`schema` 是本包 `JsonSchema` 子集的字面量对象（既可以是 B27 发射器的产物，也可以是测试手写的形状），`value` 是任意 unknown。它就是注入给引擎的那个校验器（B4 的 `validate` 实参、`askSubmitAttempted` 的 payload 判据），引擎不解读 schema 结构本身。`formatViolation(violation)` 吃一条违规、`formatViolations(list)` 吃一个违规数组（只读，不写回 schema 或值）。无状态参数、无选项对象、无 locale/编码入参。
- 输出：`validate` 恒返回违规数组（空数组即通过），从不返回布尔、从不抛（除下述 `pattern` 一条）。关键字优先级 `$ref > const > enum > anyOf > type`——**命中即返回，不再叠加检查**（`{type:"string", const:"a"}` 对 `"b"` 报的是 type 那条，`{const:"a", minLength:99}` 对 `"a"` 通过）。没有 `type` 时 object/array 关键字惰性（`{properties,required}` 对 `{a:1}` 通过、`{items,minItems}` 对 `[1]` 通过），而 string/number 约束只看实得值类型（`{minLength:5}` 对 `"abc"` 报、`{minimum:2}` 对 1 报）。`type` 可以是数组，违规文本用 `|` 连接。`integer` 的类型匹配放过任何有限数、整数性单独检查；`NaN` 与 `±Infinity` 不算 number；`null` 只匹配 null、`undefined` 谁都不匹配。对象侧：`required` 先报（按 required 数组顺序），属性按**实得键的顺序**报；`additionalProperties` 三态——`false` 报多余键、schema 递归校验、`true` 放行。数组侧：长度约束在元素检查**之前**，数组在 `got` 里用 `array(N)` 表述；`prefixItems` 覆盖前缀、`items` 从前缀之后接管；只有 `prefixItems` 的 tuple 由 `maxItems` 挡多余下标、前缀内照常检查。字符串三条约束可同时命中（长度与 pattern 各一条）。数值四条边界各自独立成条。`const`/`enum` 用 JSON 深相等：键序无关、值严格相等（`1` 与 `true` 不互等、`null` 与 `0` 不等）。`anyOf` 只报「不匹配任何一个变体」（`expected one of N variants`），**内层违规不外泄**。`$ref` 只在**根 `$defs`** 内解析、只认 `#/$defs/<名>` 这一种形态：`#/definitions/…`、带子路径的都算未解析（报 `expected schema <ref>, got unresolved $ref`）；嵌套 schema 里的 `$ref` 仍按根解析（局部 `$defs` 不被采用）；经由 def 递归出的违规**保持原路径**；def 内部指向另一个未解析 def 也报在传入路径上。注解类关键字 `format` / `description` / `default` 校验器一律不看。`formatViolation` 的文本形状是 `<path>: expected <expected>, got <got>`，违规对象就是 `{path, expected, got}` 三键；`formatViolations` 一条一行、`\n` 连接，**空列表是空串而不是空行**。`got` 的表述是有界的：长字符串截到 20 个字符加省略号、数组报长度不报内容（`array(3)`）、对象只报 `object`、`undefined` / `null` 直接给词、enum 的期望值用 `boolean true, boolean false` 这样逗号连接。
- 错误语义：校验失败**不是异常**——它是数据（违规数组），进而是 B4 的 `reject` 裁决与 `node-repairing` 载荷，最多到节点级 `ValidationFailed`，从不让 run 失败。唯一被钉的抛出是「schema 自己有病」：`pattern` 是非法正则时把 `SyntaxError` 直接抛出去（`Unterminated group`），不转成违规——调用方（引擎）因此不能假设 `validate` 是全函数性的。空 schema `{}` 是许可式的：放行任意值包括 `undefined`、函数、数组与对象（这就是 `unknown` 那一端的语义，B27）。空 `enum` 谁都拒（`expected one of ,`）。校验器不校验 schema 本身、不识别子集外的关键字（未知关键字惰性），也不做 `$schema`/`$id` 处理——更复杂的 JSON Schema 特性是否在合同内，合同不约束。
- 时序与并发：全同步，无时钟、无 I/O；B4 的裁决判定「即判即发」正是靠这个。返回数组内的顺序是确定的（required → 属性/元素按实得顺序；数值边界按 minimum→maximum→exclusive 的顺序成条），因此喂给模型的修复文本可以逐字节稳定。违规与引擎的 repair 计数之间没有耦合：校验器不记次数，预算归引擎（B4）。
- 幂等：纯函数——同一 `(schema, value)` 重复调用给出深相等的数组，不缓存也不改变状态；`formatViolations` 对同一数组重复调用同串。非幂等面在调用侧：每次违规消耗一格 repair 预算（B4），因此「重复回报同一非法 payload」整体上不是幂等的。
- 资源释放：不涉及。没有定时器、没有句柄、没有需要注销的订阅；`got` 的截断是为了文本有界，而不是为了释放什么。
- 平台差异：被钉的取值形态都与平台无关（数字字面量文本、`JSON.stringify` 式深相等、逗号分隔）。长度类关键字（`minLength`/`maxLength`）与 `got` 的 20 字符截断按 JavaScript 字符串长度（UTF-16 码元）计，用例只用 ASCII 与非 ASCII 短文本覆盖，astral 字符与代理对切分合同不约束；正则由宿主 `RegExp` 引擎执行，其 Unicode 行为不进合同（`pattern` 只用 `^a` 这类 ASCII 锚定）。无路径、无 locale 分支。
- 状态所有者：校验语义归本包（与 B27 发射器是同一个子集，两侧必须同时改）；违规模型三字段形状归本包类型面，载荷文本的上限归本包；「看到违规后怎么办」归引擎与 driver——预算计数、`node-repairing` 事件、`respondToSubmit` 的 reject 裁决与最终 `ValidationFailed` 都在 B4；把文本喂给模型、模型是否再试一次归宿主与模型。schema 内容的所有者是脚本作者（经 B27 发射）与调用方注入（引擎只透传）。
- 日志级别：无——本包不写日志；违规模型的可见面是事件里的 `violations` 与下发给 driver 的裁决记录。

### B29 facade 资产与两张注册表

- 输入：三个根桶值——`FACADE_DTS`（生产 facade 文本）、`SNIPPET_FACADE_DTS`（片段子集）、`FACADE_FILE_NAME`；以及深路径 `facade/registry.js` 的十一项导出（两张表 + `SITE_MEMBER_NAMES` + 七个查询函数）。文本面的锁用**唯一一份抽取方式**（`tests/facade-text.mjs` 的去注释打印器：`ts.createPrinter({ removeComments: true })`），录制侧与回放侧共用，与 `fixtures/facade/{production,snippet}-declarations.txt` 比对。身份面用真实脚本：`createWorkflowProgram(script, {facadeDts?})` 走一遍 checker，再对每个 CallExpression 的 symbol 查询注册表。

- 时序与并发：全部在编译期、同步、无 I/O。两份文本在程序构造时注入（默认生产文本，可显式换 snippet），文件名词符匹配发生在声明解析之后、调用点收集之前；「先按裸名取候选、再按声明验身份」是两段式判定，裸名集合不可单独作为身份依据（`"log"` 同时在候选集与「不产站点」的答案里）。包内三个消费方（站点收集 / facade-misuse 诊断 / lowering）读同一张表，因此不存在「某一处多一个 op」的窗口；引擎运行期不再查这两张表。
- 幂等：文本与表都是模块级常量，反复读取同值；无 g 标志的正则没有 `lastIndex` 残留，同一 id 连测两次答案一致；族别与身份查询是纯函数（同一 symbol 声明 ⇒ 同一行）。非幂等面在录制而不是查询：重录只在实现或语料真变了时做，且录前必须确认「注释怎么写都不碰锁」四条通过（新注释是自由面，声明面必须与录制逐字节相同）。
- 资源释放：无。两份文本是常量字符串；注册表是只读数组/集合；程序对象随调用回收，合同不约束其细节。
- 平台差异：无平台分支。真正的版本敏感性被登记在 README 与 K9：声明锁依赖 `ts.createPrinter` 的输出形态（换 TS 大版本时打印器排版一变，锁就要求一次重录），而注释文字不进锁正是为了不把旧实现的 16 KB 散文写进合同（原文 19,067 字符里声明部分只有 2,777 / 1,063）。路径、编码、换行不参与本条。
- 状态所有者：`facade/dts.ts` 拥有两份 `.d.ts` 文本与那个文件名常量（文件名同时是身份判定的锚点）；`facade/registry.ts` 拥有 op 词汇表、族别与裸名候选集，是三处消费方的唯一真源；「按声明解析身份」的构造归声明本身与容器上溯规则，谁都不另建一张影子表；录制文件归合同资产、由 `record-facade.mjs` 生成；诊断码 9001/9004 与站点表的产生归 dw01；`askSpecs` 里 typed/schema 的最终装配归 B27。
- 日志级别：无——facade 是脚本作者与模型唯一能看见的 API 面，它的可观察面就是编译产出的站点表、诊断与那段 lowered 代码。

### B30 projections 桶：浏览器安全子集

- 输入：两个入口桶文件本身（`src/index.ts` / `src/projections.ts`，dist 模式为对应的 `dist/*.js`）与它们的**传递 import 图**（按说明符逐文件展开：静态 import/export、`require(...)`、动态 `import(...)` 都算边；行锚定并跳过 `import type`，不吃正文里的引号；`./x.js` 这一类相对说明符按当前入口模式解析扩展名）。对照资产是 dw01 的 `fixtures/entry-exports.json`（只读那一份，不复制）。两种入口模式（source / dist）各跑一遍同名断言。
- 输出：三条不变式加一条对照。其一 `projections` 的传递图里**没有任何裸包说明符**（bare 集合排序后为空数组），且图里至少两个文件（否则说明抽取没跑起来、断言空转），且图中每个文件都落在包目录内（不许跑到包外）。其二 对照组：根桶的传递图**确实**拖入 `typescript`——这条存在的唯一理由是把上一条坐实为非空断言。其三 两个入口桶的运行时键集合（`Object.keys` 按 `localeCompare("en")` 排序）与 dw01 录制的 `index` / `projections` 两个数组逐字一致，条数分别钉死为 84 与 32。声明面与运行时面的差额被 B20 解释为「纯类型」：`projections.ts` 声明 86 项（按语法 70 运行时 / 16 纯类型），而运行时面上只有 32 个值——没写 `type` 关键字的类型再导出照样被擦除，因此本条的判据取运行时集合而不是声明条数。整体形状是「projections 只再导出 analysis 投影」（那属于 dw01 的范围文件），本包对它的合同就是这一条不变式加上导出集合本身。
- 错误语义：本条不产错误也不测错误——被测面是模块图与导出集合。失败形态只有断言红：多一个裸包说明符（`typescript` 一旦出现在 projections 的图里，等于把整个编译器拖进浏览器包，而那两个调用文件绕道 `/projections` 子路径要避免的正是这件事）、少一个运行时导出、名字被改、集合里多出一个录制没有的名字，四种都各撞一条断言。改名/删名必须显式记进 `known-differences`，不能静默发生（用例的失败信息即此措辞）。深路径可用性不属于本条（那是 B20 的「深层模块路径逐个可解析」）。
- 时序与并发：无运行期时序——图是在测试进程里按文件文本静态抽取的，导出集合是在 `entry.mjs` 顶层 `await import` 之后读到的。模块导入本身有循环依赖禁忌（本包架构检查约束），但本条不判它。两种入口模式之间不得有差异：dist 侧红一次就说明编译产物与源码的公开面不一致。
- 幂等：同一棵树重复抽取同结果（`seen` 集合让图对环安全，重复说明符不重复展开）；同一模块二次 import 走模块缓存，键集合不变。录制文件是只读对照，任何一次变更它都得同时变更桶，否则本条与 B20 一起红。
- 资源释放：无。只读文件文本与模块命名空间对象，不起句柄、不起进程、不写盘。
- 平台差异：图解析用 `node:path` 的 `resolve` 与 `existsSync`，因此 Windows 与 POSIX 都得跑通（README 要求测试在路径、大小写、主目录上双向兼容）；排序显式指定 `localeCompare(…, "en")`，避免宿主 locale 改变集合比较结果。除此之外合同不约束平台分支——本包运行期不碰终端或进程。
- 状态所有者：包配置（`package.json` 的 exports map）拥有「能按哪两个子路径 import」——只有这两项，包外无法按其他子路径取符号；`projections.ts` 这个桶文件本身归本包（scope 的 `""` 桶两个文件之一），它必须继续不引入 `typescript`；被再导出的**符号**有 40 项定义在 dw01 范围文件里（口径差异记在 known-differences 第 1 节），因此那条不变式的另一半由 dw01 维持；`entry-exports.json` 这份冻结集合的唯一所有者是 dw01（本包读它而不复制它，否则两份冻结集迟早分叉、分叉那天只有侧的 gate 报警）。两个调用文件（浏览器侧的图边界与折叠工具）是这条边界的服务对象，它们在包外。
- 日志级别：无——它是一个静态兼容面，既不在运行期产事件也不写日志。
