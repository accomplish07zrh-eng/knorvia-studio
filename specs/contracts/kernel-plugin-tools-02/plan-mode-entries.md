# 计划模式提示词：条目整理（重写依据）

> **用途**：`kernel-plugin-tools-02` 的 `plan-mode` guidance 重写依据。
>
> **本文件只记「语义条目」，不抄旧文本原句。** 旧实现
> （`core/src/tool/handlers/plan-mode-prompts.ts`，130 行）作只读对照。
>
> **用户裁决**：按 7 类、源码为准全部覆盖；例子本身重写；
> 退出说明要与 DSH `exit_plan_mode` 的实际行为一致。

---

## 一、进入计划模式：7 类触发条件

**每条记「判断标准」+「情形类别」**（情形的话术在重写时自拟）。

|  #  | 判断标准                                                           | 情形类别（用于写示例）                                                                                  |
| :-: | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
|  1  | **新增有意义的功能** —— 不是修修补补，而是加一块用户能感知的新能力 | 新增一个交互入口；新增一类校验规则                                                                      |
|  2  | **多种可行方案** —— 同一目标有几条都说得通的路                     | 引入缓存层（内存/文件/外部服务）；提升性能（多种优化策略）                                              |
|  3  | **改动既有行为或结构** —— 会改变现有语义，或需要重排结构           | 调整既有流程的判定条件；重构一个组件的边界                                                              |
|  4  | **架构决策** —— 需要在模式或技术之间选一个                         | 实时更新机制的选择；状态管理方案的选择                                                                  |
|  5  | **多文件改动** —— 会触及 2–3 个以上文件                            | 重构一个横切子系统；新增一条带测试的接口链路                                                            |
|  6  | **需求不清晰** —— 必须先探索才能理解范围                           | 「让应用快一点」；「修一下结账的 bug」                                                                  |
|  7  | **用户偏好重要** —— 实现方式合理可多种，**本该问用户**             | **判据：如果你正想用 AskUserQuestion 澄清做法，就该改用 EnterPlanMode** —— 先探索、再带着上下文呈现选项 |

**⚠️ 第 7 类与 AskUserQuestion 的关系是判据本身**，不是补充说明：
「想问用户怎么做」→ 说明方案不唯一 → 先进入计划模式探索，再带上下文问。

## 二、何时**不用**进入计划模式（4 条反例）

|  #  | 判断标准                                        | 情形类别                                             |
| :-: | ----------------------------------------------- | ---------------------------------------------------- |
|  1  | 单行或几行修复 —— 拼写、显而易见的缺陷、小调整  | 改文档里的错字                                       |
|  2  | 加一个需求已明确的函数                          | 加一个参数已定、行为已定的工具函数                   |
|  3  | 用户已给出非常具体、详细的指令                  | 用户直接说明了要改哪一行、改成什么                   |
|  4  | 纯研究 / 探索任务 —— 只需要查清事实，不产出改动 | 「哪些文件处理路由？」（该用子 Agent，不是计划模式） |

**⚠️ 第 4 条的关键区分**：**「研究」与「实现规划」是两件事**。
只是查信息 → 不用计划模式；要写代码 → 才规划。

## 三、进入计划模式后做什么（6 步）

1. 用搜索与读取工具彻底探索代码库（Glob/Grep/Read；启用内嵌搜索时也可用 find/grep）；
2. 理解既有模式与架构；
3. 设计实现方案；
4. 把计划呈现给用户审批；
5. 需要澄清时用 AskUserQuestion；
6. 准备好实现时用 ExitPlanMode 退出。

## 四、示例要覆盖的情形（5 正 + 3 反，**话术重写**）

### 5 个正例覆盖的情形

|  #  | 情形类别                                     | 为什么该规划                                   |
| :-: | -------------------------------------------- | ---------------------------------------------- |
|  1  | 需要架构决策的功能（如用户认证）             | 存储方式、令牌位置、中间件结构都要选           |
|  2  | 需先剖析再优化的性能问题                     | 多方案、要先定位瓶颈、影响面大                 |
|  3  | 影响多组件的主题/样式系统                    | 主题系统本身是架构决策                         |
|  4  | 看似简单但涉及多环节的功能（如一个删除入口） | 位置、确认、接口调用、错误处理、状态更新都要定 |
|  5  | 跨文件的错误处理改造                         | 影响多个文件，做法应经用户同意                 |

### 3 个反例覆盖的情形

|  #  | 情形类别               | 为什么不必规划         |
| :-: | ---------------------- | ---------------------- |
|  1  | 改文档里的错字         | 直接改，无需方案       |
|  2  | 加一行调试输出         | 实现方式唯一           |
|  3  | 问「哪些文件处理路由」 | 研究任务，不是实现规划 |

## 五、注意事项（3 条）

1. **这个工具需要用户批准** —— 进入计划模式要用户同意；
2. **不确定时倾向规划** —— 先对齐比返工好；
3. **用户希望在重大改动前被咨询**。

## 六、退出说明（`ExitPlanMode`）—— 按 **DSH 实际行为**重写

> ⚠️ 旧说明（27 行）是基于旧实现的；DSH 的 `exit_plan_mode` 有**计划审查交互**
> 与**6 种失败模式**，旧说明完全没提。以下是按 DSH 实测行为整理的条目。

### 6.1 何时用

**只在一个任务需要「规划实现步骤」且「要写代码」时用**。
**纯研究任务**（查信息、读文件、理解代码库）**不用这个工具**。

### 6.2 `plan` 参数格式（DSH 硬要求）

- 传**完整计划**，markdown 格式；
- **必须以 `# ` 开头的标题**（否则 DSH 拒绝：`requires a non-empty markdown plan starting with a # heading`）；
- 用户在审查时看到的就是这段内容。

### 6.3 前提

- 必须**处于计划模式**（否则拒绝：`is only available in plan mode`）；
- 需要 **user-questions 通道**（没有时拒绝并提示「让用户切换会话模式」）。

### 6.4 用户批准时

离开计划模式，**从下一步开始执行计划**。

### 6.5 用户选择「继续规划」时 —— **这不是失败**

DSH 会抛错（`The user chose to keep planning; revise the plan and present it again.`，
若用户带反馈则追加 `their feedback: <内容>`）。

**模型应理解为**：用户要改计划，**不是工具坏了** → 修改后重新提交。

### 6.6 用户取消（打断去说话）时

DSH 抛错（`The user dismissed the plan review to speak instead; stay in plan mode,
stop here, and wait for their message.`）。

**模型应理解为**：**留在计划模式，停下等用户消息**，不要重试。

### 6.7 服务重载时

DSH 抛错（`the plan-mode service was reloaded while the plan was under review;
present the plan again`）→ **重新呈现计划**。

### 6.8 成功只有一种结果

DSH 的输出 schema 是 `{ approved: { const: true } }` ——
**成功恒为 `approved: true`；其余情况全是抛错**。
所以「判断是否成功」看有没有抛错，而不是看某个字段。

## 八、场景集设计（7 类正例 + 反例）

**用途**：新旧文本用真实模型对比触发率（并入 `kernel-switch` 前的真实模型冒烟）。

### 正例场景（7 个，每类触发条件一个）

|  #  | 场景（自拟话术）                     |     期望：应触发 EnterPlanMode      |
| :-: | ------------------------------------ | :---------------------------------: |
| P1  | 「给应用加一个用户认证入口」         |            ✅ 类别 1 + 4            |
| P2  | 「给接口加一层缓存」                 |              ✅ 类别 2              |
| P3  | 「把现有的审批流程改成两段式」       |              ✅ 类别 3              |
| P4  | 「加实时更新：轮询还是推送？」       |              ✅ 类别 4              |
| P5  | 「重构整个权限子系统」               |              ✅ 类别 5              |
| P6  | 「让应用快一点」                     |              ✅ 类别 6              |
| P7  | 「给删除操作加个二次确认，你看着办」 | ✅ 类别 7（本该问用户，改为先规划） |

### 反例场景（4 个，对应 4 条「何时不用」）

|  #  | 场景                                               | 期望：**不**触发 |
| :-: | -------------------------------------------------- | :--------------: |
| N1  | 「README 里有个错字，改一下」                      |   ❌ 单行修复    |
| N2  | 「加个函数：输入字符串返回它的长度」               |   ❌ 需求明确    |
| N3  | 「把 src/app.ts 第 42 行的 timeout 从 30 改成 60」 |   ❌ 指令具体    |
| N4  | 「哪些文件处理路由？」                             |    ❌ 纯研究     |

### 判据与记录方式

| 项            | 内容                                         |
| ------------- | -------------------------------------------- |
| **主判据**    | 正例触发率（新文本 vs 旧文本，按类逐条对比） |
| **次判据**    | 反例不触发率（避免「什么都触发」）           |
| **记录**      | 每类一行：旧文本触发 / 新文本触发 / 是否一致 |
| **无 key 时** | **如实标注「未验证」**，不写「已验证」       |

**⚠️ 关键：要按类对比，不是只看总体触发率** ——
因为「总体 7/7」可能是「第 7 类触发、第 1 类没触发」的巧合。
