# services-02 目标架构（`studio-runtime` 契约层）

## 一、目标形态

本包是 `studio-runtime` 分层架构的**最底层**，只承载**契约**（类型声明 + 端口接口 + 装配入口），
不含任何运行时业务逻辑。

```
                  ┌──────────────────────────────┐
                  │   services-07/08  adapters   │   进程 / 数据库 / 文件系统
                  └───────────────┬──────────────┘
                                  │ 实现端口
                  ┌───────────────▼──────────────┐
                  │   services-04/05/06  app     │   运行时编排
                  └───────────────┬──────────────┘
                                  │
                  ┌───────────────▼──────────────┐
                  │      services-03  domain     │   策略计算（纯函数）
                  └───────────────┬──────────────┘
                                  │
                  ┌───────────────▼──────────────┐
                  │   ★ services-02 contracts    │   类型 + 端口 + 入口
                  └──────────────────────────────┘
```

**依赖只能向下**：`adapters → app → domain → contracts`。本包不得向上依赖任何一层。

## 三、端口下沉的迁移策略

### 为什么保留旧路径的 re-export 壳

4 个端口共 **94 处引用**，其中 `packages/services/test/` 有 5 处。虽然下沉技术上只是路径替换，
但一次性改 94 处会让替换 PR 的 diff 难以审查（路径改动淹没实现改动）。

**因此替换阶段采用两段式**：

| 阶段    | 动作                                                                                                   | 结果                       |
| ------- | ------------------------------------------------------------------------------------------------------ | -------------------------- |
| 第 1 段 | 端口实现移到 `studio-runtime/{name}.ts`；旧位置 `studio-runtime/app/{name}.ts` 保留**纯 re-export 壳** | 94 处存量引用零改动即通过  |
| 第 2 段 | 按包逐步把引用改为新路径（`services-03`～`services-08` 各自的 PR 顺手改）                              | 壳逐渐失去使用者，最后删除 |

**壳的约束**：只许 `export *` / `export type *`，**不得有任何逻辑、不得有任何本地声明**。
这条由 `ports.test.mjs` 断言（B8）。

### 为什么不是「一次性全改」

- 94 处里 5 处在测试文件——改测试文件的 import 会让「测试是否被改动」的审查变得模糊；
- 两段式让第 1 段的 diff 只含「新增端口文件 + 壳」，语义清晰。

## 四、状态所有者

本包**不持有任何运行时状态**。唯一的模块级可变值在：

- `storePort.ts` / `ports.ts` 等端口文件里**没有**模块级 `let`（B9 断言）；
- 端口只有接口声明与纯函数。

**状态全部属于上层**：`app` 层持有编排状态、`adapters` 层持有 IO 状态。

## 五、关键不变量（可执行）

| 不变量                                    | 断言位置                | 违反后果                       |
| ----------------------------------------- | ----------------------- | ------------------------------ |
| 契约层不 import `app`/`adapters`/`domain` | `dependencies.test.mjs` | 分层崩塌，出现循环依赖         |
| 6 个纯类型文件零运行时导出                | `surface.test.mjs`      | 纯类型依赖变成运行期依赖       |
| 端口的旧路径壳零逻辑                      | `ports.test.mjs`        | 壳退化成实现副本，产生双份真相 |
| 导出面与 `interface.md` 双向一致          | `surface.test.mjs`      | 合同文档腐化                   |
| 示例文件可编译                            | `typecheck.test.mjs`    | 契约类型之间已不自洽           |

## 六、与其余 6 个包的接口

| 下游包                       | 从本包取什么                                    |
| ---------------------------- | ----------------------------------------------- |
| `services-03`（domain）      | 全部 10 个声明文件的类型                        |
| `services-04/05/06`（app）   | 声明文件类型 + 4 个端口接口（实现者的契约）     |
| `services-07/08`（adapters） | 声明文件类型 + 4 个端口接口（**实现**这些端口） |

**`adapters` 实现端口、`app` 消费端口** —— 这就是 Ports & Adapters 的方向：
抽象（端口）在最底层，实现（adapters）在最上层。下沉前这个方向是反的（`adapters → app`），
下沉后成为单向的 `adapters → contracts`。
