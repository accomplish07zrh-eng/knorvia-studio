# 创作历史、确定性重试与视频首尾帧（T2.5）

2026-09-25。延续 `knorvia-creation.md` 的本机 Host 状态所有者、凭据隔离与单页设计。新增能力不建立成果页，不调用真实生成服务。

## 产品规则

- 图片／视频按钮只切换创作表单；任务历史另有类型、模型、状态三个过滤器，默认均为“全部”。过滤只改变 Renderer 展示，不删除或修改 Host 记录；模型被删除时历史仍能以已保存模型 ID 出现。列表始终以 Host 返回的最近时间顺序排列。
- 已知失败的任务可一键按原参数重试，包含提示词、模型和参考图。每个失败任务只派生一个固定 `retry-<jobId>` 请求编号；回执丢失、重开页面和双击都返回同一新任务。新任务失败后可再由其任务 ID 重试。运行中、已取消、已中断（远端结果未知）和成功任务不能用一键重试；中断须先检查供应商状态，再手动决定是否重新创建。重试会新发供应商请求，可能计费；界面明确提示。
- 视频可配置首帧和尾帧参考图。只有 JSON API 请求模板显式含 `{{firstFrameBase64}}`／`{{firstFrameDataUrl}}`、`{{lastFrameBase64}}`／`{{lastFrameDataUrl}}`，或 ComfyUI 工作流含 `{{firstFrame}}`／`{{lastFrame}}` 时，页面才分别显示对应附件操作。两张图各限 PNG/JPEG/WebP、10 MiB。OpenAI Images 只接图片参考，不接视频；未知占位符不默许。Host 校验模型能力，不信任 Renderer 的显示判断。
- 每个视频帧仅存入任务私有参考文件，任务列表和模型列表不回传原始字节或路径。可见任务只显示文件名。重复请求须匹配两帧的内容散列；重试读回 Host 自己保存的参考文件，不要求用户再次选择。ComfyUI 分别上传两张图，工作流替换为对应上传名；JSON API 将两张图填入所配置的占位符。旧任务和旧配置不受影响。
- 明确区分供应商已知失败与结果未知。可判定的 4xx 拒绝、协议声明失败或无效输出记录失败；已经启动提交而遭遇 5xx、网络传输丢失或超时则保守记为中断，保留“可能继续计费”的说明且不提供一键重试。取消只停止本地等待，供应商可能继续执行。只有 Host 收到可用文件并成功保存才标为成功。

## 接口与事件顺序

`CreateCreationJobInput` 新增可选 `firstFrame`、`lastFrame`；`CreationJob` 只新增两帧文件名。`ICreationService.retryJob(id)` 由 Host 自行构造固定新请求编号，读取原私有附件并调用既有 `createJob` 接纳路径。不得让 Renderer 复制私有参考路径或模型密钥。原始 `createJob` 的 requestId 幂等合同不变。

```text
模型配置保存 → Host 校验占位符与协议 → 页面仅显示支持的帧入口
选择参考图 → Host 校验类型/大小/模板 → 固定请求编号接纳并持久化附件
供应商提交 → 已知成功保存文件 / 已知失败 / 未知结果中断 / 用户取消
失败卡点击重试 → Host 使用 retry-<旧任务 ID> 找到或接纳唯一新任务 → 列表刷新
```

## 验收

2026-09-27 补充超时落盘边界：CreationService 独占任务状态写入。运行状态或成果文件落盘期间触发截止时间，也必须经同一失败路径保存终态，不能直接返回并遗留 running。尚未进入供应商提交的超时记为明确失败；已经进入提交的超时保持结果未知。用户取消已经保存的 cancelled 不得被迟到的超时或成功覆盖；截止后新创建的孤立成果文件须清理。测试以受控写盘门闩和虚拟时钟重现两处边界，不延长业务超时来掩盖问题。

2026-09-28 补充提交阶段的测试时序：验证“提交后超时结果未知”的用例必须先等待模拟供应商确实收到提交，再推进虚拟截止时间；不能用极短的真实计时器假定磁盘和凭据读取已经完成。未提交超时的明确失败、已提交超时的未知结果，以及用户取消的终态应分别断言，不放宽幂等性或一键重试限制。用例恢复真实时钟后仍须等待真实状态文件落盘；取消分支冻结截止时间，避免它与被验证的用户取消竞速。

2026-09-29 补充已知失败与重试的测试时序：三协议组合用例从首个任务起控制业务截止时钟，已知失败阶段须同时断言模拟供应商返回 HTTP 400、提交数为 1；重试成功后提交数为 2。终态轮询仍使用独立真实计时器和原来的 1000ms 预算，不能随业务时钟冻结。之后等待提交到达才推进原来的 500ms 截止，取消阶段仍要求总提交数恰为 4。这样提交前的超时不会只因状态也是 failed 而冒充供应商已知拒绝；生产服务的截止时间、分类和重试规则均不改变。独立的提交前截止用例继续验证真实业务边界。

2026-09-29 补充异步 JSON 测试超时证据：原 Windows run `36520626246` 与 `36522980492` 在1000ms终态预算后分别仍读到 running、queued，尚不能确认云端首因。只在测试的模拟供应商边界记录四阶段 submit/poll 的进入及返回计数，每个分支保留最多16个单调时间事件；错误同时给出当前固定 prompt、getJob 已完成读取数与最长读取耗时。进入 poll 只能见证之前的 providerTaskId checkpoint await 已完成，未见 poll 标为 unobserved，不推断未落盘，也不读取私有文件。超时上下文是同步内存投影，其自身出错不能覆盖原超时证据。四分支顺序与状态断言、真实 IO、35ms供应商截止、2ms供应商轮询、1000ms终态等待、10ms终态轮询均不变；不以扩大预算或重跑声称故障修复。

```text
接纳并落盘 → 标为 running → 提交供应商 → 写成果 → 保存成功
                   └── 任一 await 期间截止 → 原失败分类/串行写入 → 终态
用户取消 → 保存 cancelled ────────────────┘（终态写入不得覆盖取消）
```

## 幂等测试的后台写入收尾（2026-09-29）

原 Linux run `36562935638` 在创作 requestId 幂等用例清理临时目录时报告 ENOTEMPTY。接纳回执不表示供应商请求、成果写入和终态持久化已完成；该用例原来在检查冲突拒绝后直接删目录。受控供应商门闩确认：原清理入口仍能观察到 running、零成果和恰好一次提交。它证明测试缺少收尾，不声称复现云端当次的精确文件系统调度。

该测试必须先等模拟供应商收到提交，再在响应未放行期间验证相同请求幂等、不同内容/来源被拒绝、提交数为一以及任务仍运行。finally 放行响应后，通过已有公共 getJob 等待成功与成果写入，再清理唯一自有临时目录。即使某条断言失败也先放行并等待已接纳任务；不增加删除重试、吞掉清理错误、延长原有终态等待预算或改产品代码。

```text

  → 测试放行响应 → Service 写成果与成功终态 → 公共状态确认 → 删除测试目录
```

## Windows 打包媒体交接验收（2026-09-27）

- `scripts/studio-media-acceptance.mjs <exe>` 在真实打包程序中验证创作供应商配置、工作流提交、人工批准、上游 PNG 作为下游创作参考图、历史展示和同一数据根重启。配置与运行从现有页面进入，不替换 CreationService、运行时或 RPC，不新增产品状态。
- 验收进程和每次窗口 Host 的数据、凭据、项目均属于独立临时根；正式便携包的 `data` 不可读取或写入。Windows 的 `APPDATA`、`LOCALAPPDATA` 目录先创建再启动，窗口始终隐藏。
- 供应商只监听 `127.0.0.1`。验收引导在 Main 与 Host 的网络出口拒绝非回环连接，Renderer 同样拒绝外部 HTTP；不调用真实模型、CLI、ACP、SSH 或生产服务。图像为两份可逐块 CRC 校验及解压的 PNG，不用文本伪装图片。
- 创建工作流定义可在应用关闭时向隔离数据库写入种子；运行、批准和历史查看必须通过 UI。第一张图成功后停在人工批准节点，批准前禁止第二次生成；下游必须走图片编辑协议，实际 multipart 请求含上游完整 PNG，不能拿同名项目诱饵替代。

- 重启前记录供应商请求数；真正退出进程后用同一隔离根重开，历史和图片仍可显示，整个重启和历史加载阶段不得产生新请求。失败报告保留已经完成的检查，不把脚本中途退出视为通过。


## 仅调度业务截止的内部依赖（2026-09-29）

原生安排/取消实现位于同模块的私有 `creationRunDeadline.ts`，服务只选择注入或默认调度器；该提取遵守单文件400行限制，不新增状态、公开RPC或第二条运行路径。

本项替代三协议组合用例中恢复/冻结全局setTimeout的接线说明。有限合成EPERM已证实：冻结全局setTimeout会冻结持久化25ms退避，而真实1000ms终态计时仍前进；这不是原CI当次首因证明。CreationServiceOptions新增可信内部可选scheduleRunDeadline(callback, delayMs)，同步登记、返回取消函数，不同步触发callback或抛错；取消无异常并可重复。它只安排已有run watchdog，不成为新任务或存储状态所有者，不进入RPC/用户设置。

```text
queued持久化 → run入口安排同一deadline → running写盘 → 提交
  → 同一mutate保存终态 → finally取消该次deadline → 删除controller
用户cancel → 同一mutate保存cancelled → abort；迟到结果不可覆盖
```

默认仍在原try前使用原生setTimeout、同一runTimeoutMs或16分钟、立即unref，并在原finally clearTimeout；不改变await、catch、abort理由、终态或写入顺序。测试只记录该端口回调，不根据延迟数值/堆栈过滤timer，不冻结存储、供应商、Date或终态轮询。三协议400/提交1、retry成功/提交2、确认提交后推进500ms得到interrupted、用户取消后总提交4及禁止不确定结果重试均保持；真实1000ms/10ms终态预算保持。新增验收覆盖端口调用/取消、499+1精确截止及一次自有failed-terminal EPERM在原预算内完成25ms真实退避。仅匹配自有临时jobs文件和任务，不访问真实用户数据；既有默认计时持久化用例继续验证。原服务来源分类不因此改为MIT或独立替换。
